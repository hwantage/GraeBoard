# 사본을 행 단위 레코드로 동기화 (프로토콜 5)

[동기화 규약](../SYNC_PROTOCOL.md) · [데이터 형식](../DATA_FORMAT.md) · [DB 변경 지침](../DATABASE_CHANGES.md)

2026-11-13 사용자 승인(동기화 형식 구현), 2026-11-14 사용자 승인(외부 서버의 사본 저장 방식 변경 구현). 운영 전환 실행과 운영 DB 변환은 별도 승인이 필요하다.

## 이유

프로토콜 3은 사본(`sheetClone`) 하나를 레코드 하나로 둔다. 셀 하나를 고쳐도 명령이 사본 전체를 수정 전·후로 싣는다(운영 사본 기준 1.79MB × 2). 2026-11-13 하루에 이 구조로 세 번 멈췄다.

- 사내가 30초에 7번 고친 사본 명령이 26.6MB 이벤트가 되어 외부 서버 수신이 실행 한도(메모리 256MB·CPU 2초)로 정지
- 외부의 미전송 63건(사본 만들기 3.3MB 포함) 게시가 CPU 한도로 정지
- 사본 충돌을 담은 충돌 보관함 목록이 한도 초과로 열리지 않음

기존 구조를 유지하는 대안은 한도에 걸릴 때마다 줄이고, 막히면 운영자 PC로 대신 처리하는 것이다(#157). 재발을 막지 못한다.

코드에 있는 프로토콜 4(행·셀 분할)는 그대로 쓸 수 없다. 운영 사본(행 454개)으로 재면 레코드 26,994개·55.84MB가 된다. 행마다 서식 전체(120.5KB)를 반복하고 셀마다 레코드를 만들기 때문이다. 또 외부 서버는 프로토콜 3이 아니면 부분 경로를 쓰지 않아(`worker/sync/sync-store.mjs`) 커밋마다 팀 전체를 읽는다.

## 범위

- 동기화 프로토콜 5(reducer 5)를 추가한다. 4는 번호를 다시 쓰지 않고 읽기만 유지한다.
- 공유 기준본(`sync_entities`)·명령·충돌·receipt의 사본 형식이 바뀐다.
- 로컬 DB 스키마는 바뀌지 않는다. 사내 `sheet_clones.data`와 외부 `site_entities`의 사본 행, 앱·API 응답은 지금 형식 그대로다.
- 운영 버전: 사내·외부 모두 프로토콜 3. 목표: 프로토콜 5.

## 레코드

| 레코드             | 키                   | payload                                                                                                                        |
| ------------------ | -------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `sheetClone`       | `[사본 ID]`          | `{year, name, referenceDate, createdBy, createdAt, data: {users, view, settings}, order: [행 ID…], formats: {행 ID: 서식 ID}}` |
| `sheetCloneFormat` | `[사본 ID, 서식 ID]` | `{data: {revision, rules}}`                                                                                                    |
| `sheetCloneTask`   | `[사본 ID, 행 ID]`   | `{data: 셀·서식을 뺀 행 정보, cells: {셀 키: {value, style, version}}}`                                                        |

- 서식 ID는 서식 값 canonical JSON의 SHA-256 앞 32자다. 같은 서식은 사본 안에서 레코드 하나다. 행마다 서식이 다를 수 있으므로(외부에서 만든 사본, 사본 안 서식 변경) 사본당 하나로 고정하지 않는다.
- 서식 레코드는 바뀌지 않는다(만들기·삭제·복원만). 사본을 지울 때 함께 지우고, 쓰는 행이 없어져도 따로 지우지 않는다.
- 행이 쓰는 서식은 부모의 `formats`가 갖는다(서식 없는 행은 항목이 없다). 행에 두면 서식을 전체 행에 바꿀 때 모든 행이 통째로 실린다(운영 사본 기준 약 5.7MB). 부모에 두면 서식 레코드 하나와 부모만 실린다.
- 행 순서는 부모의 `order`가 갖는다. 행에 순번을 두면 행 하나를 넣을 때 뒤의 모든 행이 바뀐다.

운영 사본 기준 예상: 레코드 약 456개, 사본 만들기 약 2.5MB, 셀 하나 수정 약 11KB(행 하나의 수정 전·후).

## 병합 (reducer 5)

- 행의 `data`: 필드별 3-way(프로토콜 4의 `mergeSheetCloneTask` 그대로, `updatedAt`은 큰 값).
- 행의 `cells`: 셀 키별 3-way. 서로 다른 셀은 합치고, 같은 셀을 다르게 고치면 충돌이다.
- 부모의 `formats`: 행 ID별 3-way. 서로 다른 행의 서식 변경은 합친다.
- 부모의 `order`: 필드 전체 3-way. 양쪽이 동시에 행을 넣거나 지우면 충돌이다.
- 살아 있는 사본의 `formats`는 살아 있는 서식 레코드를 가리켜야 한다.
- 문서 차이 탐색 상한은 프로토콜 4와 같은 2,000이다.

## 변환 (3 → 5)

사본마다 평문으로 풀고, 서식 값별로 서식 레코드를 만들고, 행마다 레코드를 만든다. 결정적이며 generation·version 토큰은 프로토콜 4 전환과 같은 방식(새 라벨)으로 유도한다. 검증 조건: 변환한 상태를 다시 조합한 사본이 모든 사본에서 프로토콜 3 사본과 같아야 한다(서식 없는 행, 행 순서, 삭제된 사본 포함).

전환 절차는 프로토콜 4의 명시 전환과 같다. 양쪽에 같은 릴리스, 양쪽 일시정지, 미전송 0, 미해결 충돌 0, 같은 head·hash에서 한 번 실행하고, 전환 커밋에 프로토콜 3 백업 snapshot과 프로토콜 5 snapshot을 함께 남긴다. 전환 전에 DB·이미지 백업을 만든다. 전환 뒤에는 구버전 코드로 되돌리지 않는다. 프로토콜 5를 모르는 릴리스는 전환 커밋에서 위치를 옮기지 않고 멈춘다.

## 구현 순서

1. `server/sync/core/protocol.mjs`: 프로토콜 5 상수, 엔티티·payload 필드·키 길이·검증, `supportedVersion`.
2. `server/sync/core/versions.mjs`: 분해·조합·`upgradeState`(3 → 5). 건드린 사본만 조합하는 옵션.
3. `server/sync/core/reducer.mjs`: `cells` 병합, 서식 참조 검사.
4. `operations.mjs`·`projection.mjs`·`retention.mjs`·`node-background.mjs`: 행 → 서식·부모 참조.
5. `service.mjs`·`checkpoint.mjs`·upgrade 경로·CLI: 전환을 3 → 5로 일반화, `maxProtocol` 5.
6. 사내: `capture.mjs`·`entities.mjs`·`background-worker.mjs`·`maintenance-sqlite.mjs`.
7. 외부: `sync-store.mjs`(프로토콜 5에서 부분 경로 허용), `sync-partial.mjs`(행의 부모·서식만 포함), `materialize.mjs`(건드린 사본만 조합), `data.mjs`(바뀐 행만 캡처), `recovery.mjs`.
8. `shared/sync/conflict-diff.js`: 서식 레코드 이름, 행 충돌의 셀별 비교.
9. 문서(`SYNC_PROTOCOL.md`·`DATA_FORMAT.md`·`OPERATIONS.md`·`DEVELOPMENT.md`)와 성능 스크립트.

## 검증

- 프로토콜 4 형식을 고정한 테스트(`tests/sync/protocol/sync-protocol-v2.test.mjs` 등)에 대응하는 프로토콜 5 테스트.
- 셀별 병합과 같은 셀 충돌, 끊긴 서식 참조, 양쪽이 같은 서식을 만든 경우.
- 행 넣기·지우기는 `order`와 해당 행만, 서식 변경은 해당 행과 서식 레코드 하나만 바꾸는지.
- 사내 방식·외부 방식·서식 없는 사본의 왕복 변환.
- 프로토콜 5를 모르는 reader가 전환 커밋에서 멈추는지.
- 실제 PostgreSQL에서 셀 하나 수정이 부분 경로로 처리되고 읽는 레코드 수가 한정되는지.
- 행 454개 사본의 크기(만들기·셀 수정·충돌).
- 운영 `sync-v1` 사본으로 전환 리허설: 외부 서버의 전환 수신이 실행 한도 안인지.

## 외부 서버의 사본 저장 (2단계)

외부 서버는 사본을 화면용 저장소(`site_entities`)에 한 덩어리로 둔다. 외부 화면에서 셀 하나를 고쳐도 사본 전체를 읽고 다시 쓰고, 사내에서 온 사본 변경을 받을 때마다 덩어리를 다시 조립한다. 사본 하나 크기라 지금은 한도 안이지만 사본이 커지면 다음 병목이다.

- 화면용 저장소도 동기화와 같은 단위(사본 정보·서식·행)로 저장한다.
- 셀 수정은 그 행만 읽고 쓴다. 사본을 열 때만 행을 모아 조립한다.
- 수정 충돌 검사는 사본 전체 해시 대신 사본별 변경 번호를 쓴다.
- 외부 PostgreSQL의 저장 형식이 바뀌므로 기존 사본의 변환과 site migration이 필요하다. 사내 SQLite(`sheet_clones.data`)는 실행 한도가 없어 그대로 둔다. 화면 동작은 양쪽이 같다.
- 상세 설계(스키마·변환·배포 순서)는 프로토콜 5 구현 뒤 이 문서에 추가하고, 운영 변환 실행 전에 승인을 받는다.

## 남는 한계

- 2단계 전까지 외부 서버는 사본을 받은 커밋마다 그 사본의 사이트 행(한 덩어리)을 다시 조합해 쓴다.
- 양쪽이 동시에 행을 넣거나 지우면 `order` 충돌이 된다.
- 전체 행을 한 번에 바꾸는 수정(전체 붙여넣기 등)은 모든 행을 싣는다(운영 사본 기준 약 5.7MB). 이벤트 한도(32MiB) 안이고, 연속 수정은 게시 묶음 상한(1MiB)으로 한 이벤트에 쌓이지 않는다.
