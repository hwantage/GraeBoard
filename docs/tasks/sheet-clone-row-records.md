# 사본을 행 단위 레코드로 동기화 (프로토콜 5)

[동기화 규약](../SYNC_PROTOCOL.md) · [데이터 형식](../DATA_FORMAT.md) · [DB 변경 지침](../DATABASE_CHANGES.md)

2026-11-13 사용자 승인(동기화 형식 구현), 2026-11-14 사용자 승인(외부 서버의 사본 저장 방식 변경 구현). 운영 전환 실행과 운영 DB 변환은 별도 승인이 필요하다.

## 이유

프로토콜 3은 사본(`sheetClone`) 하나를 레코드 하나로 둔다. 셀 하나를 고쳐도 명령이 사본 전체를 수정 전·후로 싣는다(운영 사본 기준 1.79MB × 2). 2026-11-13 하루에 이 구조로 세 번 멈췄다.

- 사내가 30초에 7번 고친 사본 명령이 26.6MB 이벤트가 되어 외부 서버 수신이 실행 한도(메모리 256MB·CPU 2초)로 정지
- 외부의 미전송 63건(사본 만들기 3.3MB 포함) 게시가 CPU 한도로 정지
- 사본 충돌을 담은 충돌 보관함 목록이 한도 초과로 열리지 않음

기존 구조를 유지하는 대안은 한도에 걸릴 때마다 줄이고, 막히면 운영자 PC로 대신 처리하는 것이다(#157). 재발을 막지 못한다.

코드에 있는 프로토콜 4(행·셀 분할)는 그대로 쓸 수 없다. 운영 사본(행 454개)으로 재면 레코드 26,994개·55.84MB가 된다. 행마다 서식 전체(120.5KB)를 반복하고 셀마다 레코드를 만들기 때문이다. 또 외부 서버는 프로토콜 3이 아니면 부분 경로를 쓰지 않아(`worker/sync/sync-store.mjs`) 커밋마다 팀 전체를 읽는다.

## 범위

- 동기화 프로토콜 5(reducer 5)를 추가한다. 4는 번호를 다시 쓰지 않고 읽기만 유지한다.
- 공유 기준본(`sync_entities`)·명령·충돌·receipt의 사본 형식이 바뀐다.
- DB 스키마는 바뀌지 않는다. 사내 `sheet_clones.data`와 앱·API 응답은 지금 형식 그대로다. 외부 `site_entities`의 사본 행은 프로토콜 5 팀에서 세 레코드로 바뀐다(아래 2단계).
- 운영 버전: 사내·외부 모두 프로토콜 3. 목표: 프로토콜 5.

## 레코드

| 레코드             | 키                   | payload                                                                                                       |
| ------------------ | -------------------- | ------------------------------------------------------------------------------------------------------------- |
| `sheetClone`       | `[사본 ID]`          | `{year, name, referenceDate, createdBy, createdAt, data: {users, view, settings}, formats: {행 ID: 서식 ID}}` |
| `sheetCloneFormat` | `[사본 ID, 서식 ID]` | `{data: {revision, rules}}`                                                                                   |
| `sheetCloneTask`   | `[사본 ID, 행 ID]`   | `{data: 셀·서식을 뺀 행 정보, cells: {셀 키: {value, style, version}}}`                                       |

- 서식 ID는 서식 값 canonical JSON의 SHA-256 앞 32자다. 같은 서식은 사본 안에서 레코드 하나다. 행마다 서식이 다를 수 있으므로(외부에서 만든 사본, 사본 안 서식 변경) 사본당 하나로 고정하지 않는다.
- 서식 레코드는 바뀌지 않는다(만들기·삭제·복원만). 사본을 지울 때 함께 지우고, 쓰는 행이 없어져도 따로 지우지 않는다.
- 행이 쓰는 서식은 부모의 `formats`가 갖는다(서식 없는 행은 항목이 없다). 행에 두면 서식을 전체 행에 바꿀 때 모든 행이 통째로 실린다(운영 사본 기준 약 5.7MB). 부모에 두면 서식 레코드 하나와 부모만 실린다.
- 행 순서는 레코드로 두지 않는다. 각 행의 `data.position`(같으면 `createdAt`, 행 ID 순)으로 정하며 화면의 기본 정렬과 같다. 처음에는 부모에 `order` 배열을 두었으나, 화면이 실제로 쓰는 순서는 `position`이었고 `order`는 양쪽이 동시에 행을 넣으면 충돌했다. 행을 사이에 넣거나 옮길 때는 그 행만 앞뒤 행 사이의 값을 받는다(`shared/sheet-clones/sheet-clone-editing.js`의 `positionsBetween`). 사이에 값이 더 들어갈 수 없을 때만 모든 행의 순번을 다시 매긴다.

운영 사본 기준 예상: 레코드 약 456개, 사본 만들기 약 2.5MB, 셀 하나 수정 약 11KB(행 하나의 수정 전·후).

## 병합 (reducer 5)

- 행의 `data`: 필드별 3-way(프로토콜 4의 `mergeSheetCloneTask` 그대로, `updatedAt`은 큰 값).
- 행의 `cells`: 셀 키별 3-way. 서로 다른 셀은 합치고, 같은 셀을 다르게 고치면 충돌이다.
- 부모의 `formats`: 행 ID별 3-way. 서로 다른 행의 서식 변경은 합친다.
- 행 넣기·지우기: 행 레코드의 생성·삭제라 양쪽이 동시에 해도 충돌하지 않는다. 같은 행을 양쪽이 다른 자리로 옮기면 그 행의 `position` 충돌이다.
- 살아 있는 사본의 `formats`는 살아 있는 서식 레코드를 가리켜야 한다.
- 문서 차이 탐색 상한은 프로토콜 4와 같은 2,000이다.

## 변환 (3 → 5)

사본마다 평문으로 풀고, 서식 값별로 서식 레코드를 만들고, 행마다 레코드를 만든다. 결정적이며 generation·version 토큰은 프로토콜 4 전환과 같은 방식(새 라벨)으로 유도한다. 검증 조건: 변환한 상태를 다시 조합한 사본이 모든 사본에서 프로토콜 3 사본과 같아야 한다(서식 없는 행, 행 순서, 삭제된 사본 포함).

전환 절차는 프로토콜 4의 명시 전환과 같다. 양쪽에 같은 릴리스, 양쪽 일시정지, 미전송 0, 미해결 충돌 0, 같은 head·hash에서 한 번 실행하고, 전환 커밋에 프로토콜 3 백업 snapshot과 프로토콜 5 snapshot을 함께 남긴다. 전환 전에 DB·이미지 백업을 만든다. 전환 뒤에는 구버전 코드로 되돌리지 않는다. 프로토콜 5를 모르는 릴리스는 전환 커밋에서 위치를 옮기지 않고 멈춘다.

## 구현 순서

1. `server/sync/core/protocol.mjs`: 프로토콜 5 상수, 엔티티·payload 필드·키 길이·검증, `supportedVersion`.
2. `server/sync/core/versions.mjs`: 분해·조합·`upgradeState`(3 → 5). 건드린 사본만 조합하는 옵션.
3. `server/sync/core/reducer.mjs`: `cells` 병합, 서식 참조 검사.
4. `operations.mjs`·`projection.mjs`·`retention.mjs`·`node-background.mjs`: 행 → 서식·부모 참조.
5. `service.mjs`·`checkpoint.mjs`·upgrade 경로·CLI: 전환을 3 → 5로 일반화, `maxProtocol` 5.
6. 사내: `capture.mjs`·`entities.mjs`·`background-worker.mjs`·`maintenance-sqlite.mjs`.
7. 외부: `sync-store.mjs`(프로토콜 5에서 부분 경로 허용), `sync-partial.mjs`(행의 부모·서식만 포함), `materialize.mjs`(건드린 사본만 조합), `data.mjs`(바뀐 행만 캡처), `recovery.mjs`.
8. `shared/sync/conflict-diff.js`: 서식 레코드 이름, 행 충돌의 셀별 비교.
9. 문서(`SYNC_PROTOCOL.md`·`DATA_FORMAT.md`·`OPERATIONS.md`·`DEVELOPMENT.md`)와 성능 스크립트.

## 검증

- 프로토콜 4 형식을 고정한 테스트(`tests/sync/protocol/sync-protocol-v2.test.mjs` 등)에 대응하는 프로토콜 5 테스트.
- 셀별 병합과 같은 셀 충돌, 끊긴 서식 참조, 양쪽이 같은 서식을 만든 경우.
- 행 넣기·옮기기·지우기는 해당 행만, 전체 행 서식 변경은 부모와 서식 레코드만 바꾸는지.
- 사내 방식·외부 방식·서식 없는 사본의 왕복 변환.
- 프로토콜 5를 모르는 reader가 전환 커밋에서 멈추는지.
- 실제 PostgreSQL에서 셀 하나 수정이 부분 경로로 처리되고 읽는 레코드 수가 한정되는지.
- 행 454개 사본의 크기(만들기·셀 수정·충돌).
- 운영 `sync-v1` 사본으로 전환 리허설: 외부 서버의 전환 수신이 실행 한도 안인지.

## 외부 서버의 사본 저장 (2단계)

프로토콜 3에서 외부 서버는 사본을 화면용 저장소(`site_entities`)에 한 덩어리로 둡니다. 셀 하나를 고쳐도 사본 전체를 다시 쓰고, 사내에서 온 사본 변경을 받을 때마다 덩어리를 다시 조립합니다.

프로토콜 5 팀은 화면용 저장소에도 동기화 기준본과 같은 세 레코드(사본 정보·서식·행)를 둡니다.

- 스키마는 바뀌지 않습니다. 같은 `site_entities` 테이블에 행의 내용만 다릅니다. 저장 형식은 프로토콜 전환 커밋을 반영하는 트랜잭션의 전체 반영(`materialize`)에서 바뀝니다. 별도 site migration과 변환 명령이 없습니다.
- 공통 저장 계층 `DataSession`(`worker/storage/data.mjs`)이 처리합니다. 사본을 읽을 때(`composed`) 행을 모아 기존 형식으로 조합하고, 저장할 때(`putCopy`) 분해해 저장된 레코드와 다른 것만 씁니다. 화면용 사본 코드(`postgres-sheet-clones.mjs`)·이력·이관·문서 코드는 기존 형식을 그대로 읽고 씁니다.
- 동기화 명령은 바뀐 레코드만 싣고, 명령을 만들 때 기준본에서 읽는 것도 바뀐 행·부모·서식뿐입니다.
- 사내에서 온 변경은 부분 경로로 받아 바뀐 레코드만 화면용 저장소에 씁니다. 사본을 다시 조립하지 않습니다.
- 사본의 `revision`은 그 사본의 어느 레코드가 바뀌어도 올립니다. 화면의 변경 감지가 이 값을 봅니다.
- 감사 이력은 바뀐 행만 기록합니다. 이력의 행 복구는 지워진 행만 쓰므로 동작이 같습니다.
- 사내 SQLite(`sheet_clones.data`)는 실행 한도가 없어 그대로 둡니다. 화면 동작은 양쪽이 같습니다.

함께 고친 것: 외부의 사본 수정은 문서가 없는 행에 표시용 빈 문서("문서 1")를 붙여 저장했습니다. 사본을 처음 고칠 때 모든 행에 문서가 하나씩 생기고 모든 행이 다시 쓰였습니다. 표시용 항목은 저장하지 않습니다.

## 사본 수정 요청 (3단계)

저장을 행 단위로 바꾼 뒤에도 외부의 사본 수정 요청은 사본의 모든 행을 읽었습니다. 수정 전 확인이 사본 전체의 해시였고 응답이 사본 전체였기 때문입니다. 행을 사이에 넣거나 옮기면 뒤 행의 순번을 모두 다시 매겨 행 수백 개가 다시 쓰였습니다. 함께 고쳤습니다.

- 수정 전 확인: 프로토콜 5 팀의 사본 `revision`은 부모의 `data`·`formats`와 각 행의 사이트 revision 목록의 해시입니다(`DataSession.copyRevision`). 행의 내용을 읽지 않고 계산합니다. 조회와 수정이 같은 값을 냅니다.
- 읽기: 요청이 이름을 든 행만 읽습니다(`getCopyRows`). 셀 수정은 그 행, 삭제는 지울 행, 서식은 범위에 든 행입니다. 행을 넣거나 옮길 때는 나머지 행의 ID·순번·생성 시각만 SQL로 꺼내 자리 계산에 씁니다(`copyRowIndex`). 행의 문서도 읽은 행 것만 읽습니다.
- 모든 행을 읽는 경우: 전체 행 서식(`rows: null`)과, 순번을 다시 매겨야 해서 이름을 들지 않은 행이 바뀌는 경우입니다. 뒤의 경우는 쓰기 전에 감지해 모든 행을 읽고 다시 적용합니다.
- 응답: 화면이 `PATCH /api/sheet-clones/:id?changes=1`로 요청하면 두 서버 모두 사본 전체 대신 요약과 `changes: {tasks: 바뀐 행, removed: 지워진 행 ID}`를 답합니다. 화면은 수정 전 사본에 합칩니다(`useSheetCloneDraft.ts`의 `savedSheetClone`). `changes=1`이 없으면 이전처럼 사본 전체를 답합니다. 외부 서버가 요청별 응답을 보관하는 `site_operations` 행도 그만큼 작아집니다.
- 전체 행 서식: 자기 스타일에 그 속성이 있는 셀만 바꾸고 그런 셀이 있는 행만 `updatedAt`을 올립니다. 이전에는 범위의 모든 셀 버전과 모든 행의 `updatedAt`을 올려 모든 행이 다시 쓰였습니다.
- 행 이동: 옮긴 행만 `position`·`updatedAt`이 바뀝니다. 이전에는 모든 행이 바뀌었습니다.
- 사본을 읽지 않게 된 다른 경로: 사본 행 문서의 조회·저장·이미지 올리기(행이 있는지만 확인, 이전에는 요청마다 사본을 두 번 읽음), 여러 행 문서 일괄 조회, 사본 화면의 변경 감지 폴링(부모의 revision만 조회), 사본 이름 변경.
- 공용 편집 규칙(`sheet-clone-editing.js`)이 바뀌었으므로 프로토콜 3 팀과 사내 서버도 행 넣기·옮기기·전체 서식에서 바뀌는 행이 줄어듭니다.

## 남는 한계

- 사본을 여는 조회(`GET /api/sheet-clones/:id`)는 모든 행을 읽습니다. 다른 사람이 사본을 고치면 같은 사본을 보던 화면이 이 조회로 갱신합니다.
- 사본 삭제, 이력의 행 복구, 가져오기로 사본에 행 추가, 내보내기는 사본 전체를 읽습니다.
- 전체 행을 한 번에 바꾸는 수정(전체 붙여넣기 등)은 모든 행을 싣습니다(운영 사본 기준 약 5.7MB). 이벤트 한도(32MiB) 안이고, 연속 수정은 게시 묶음 상한(1MiB)으로 한 이벤트에 쌓이지 않습니다.
- 서식 레코드는 쓰는 행이 없어져도 사본을 지울 때까지 남습니다.
