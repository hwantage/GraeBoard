# 데이터 동기화 개선 작업 완료 보고 및 잔여 사항

작업 기준은 `draft/data-sync-review-handoff-20261029.md`입니다. A2·A3·A4 인덱스/정리·A6은 사용자가 승인한 `draft/data-sync-review-design-20261029.md` 전체 설계에 따라 구현했습니다. 운영 DB 변환·삭제·배포는 실행하지 않았습니다.

전체 50개 항목 중 **49개 완료, C11 1개 보류**입니다. C11 측정기와 요구 시나리오는 구현·실행했고 사본 편집과 실제 브라우저 30개의 재조회 기준을 통과했습니다. 연결 유휴 저장 p95는 미연결 대비 32.670% 증가하여 10% 이내 목표를 충족하지 못했습니다. 입증된 추가 개선 없이 통과로 처리하거나 측정 기준을 완화하지 않았습니다.

수신 대상은 원 핸드오프를 작성한 Claude의 **내부망 외부망 데이터 동기화 코드 리뷰** 세션입니다. 이 문서는 구현·검증 작업의 결과 보고이며, 전체 항목 통과나 운영 배포 승인으로 해석하지 않습니다. 승인된 구현 및 합성 DB 검증 범위에는 A3의 사본 형식 분할과 A6의 reducer v2 전환 경로 추가가 포함됩니다.

## 데이터 안전과 검증 범위

- v1 canonical·receipt·conflict 해시와 과거 병합 결과를 고정값으로 확인했습니다. v2는 명시 전환 이후에만 적용됩니다.
- 실제 Node 두 사이트와 PostgreSQL에서 전환·서로 다른 사본 셀 편집·동일 셀 충돌 해결·연결 해제 후 재연결·연도 정리/복원을 확인했습니다. 원본 업무와 사본을 구분하며 C/P·문서·셀·미전송 입력을 보존합니다.
- 전환 중 새 저장은 유효한 `upgrade:` lease에 한해서 409로 거절합니다. 마지막 writer에서도 새 P와 snapshot guard를 재확인합니다. 일반 동기화 중 편집은 허용합니다.
- 기존 team v1/site v1 백업 원본의 읽기 호환성과 v2 상태의 backup v3 복구를 실제 PG에서 확인했습니다. 일반 실행·복구 대상의 최신 스키마 검사는 유지합니다.
- 실제 운영 DB 변환·삭제·배포, 운영 DB 사본의 리허설은 실행하지 않았습니다. B12의 산출물은 배포 전 체크리스트이며 실제 서버에서는 [패치 가이드](PATCH_GUIDE.md)를 따라 사본 검증을 수행해야 합니다.
- 외부 Supabase/Deno의 CPU·메모리 및 실제 클라우드 네트워크 성능은 이번 로컬 검증 범위 밖입니다. 기존 1만 업무·60주 대량 benchmark 전체 실행도 C11 측정과 구분합니다.

## 보고 후 확인한 운영 제약과 후속 논의

### 동기화 일시정지와 v2 전환의 차이

`paused`는 해당 팀의 내부망↔외부망 Git 송수신을 멈추는 상태입니다. 서버 프로세스와 조회는 유지되며 일반 로컬 저장도 계속 가능하고 미전송 변경으로 보관됩니다. v2 전환 실행 중에는 각 사이트의 유효한 `upgrade:` lease가 해당 팀의 동기화 업무 저장을 409로 거절합니다. 거절된 저장 트랜잭션은 롤백되어 기존 자료를 보존합니다.

**양쪽 전환 명령 사이의 전체 기간을 자동으로 읽기 전용으로 묶는 기능은 없습니다.** 운영자는 그 기간에도 사용자 편집과 자동 쓰기를 중지해야 합니다. 첫 사이트가 v2 전환을 게시한 뒤 아직 v1인 사이트에 새 미전송 변경이 생기면, 두 번째 전환은 기존 C/P를 보존한 채 거절됩니다. 이 시점의 v1 미전송 변경을 자동으로 v2로 변환·게시하는 경로는 현재 없으며 단순 재시도로 해결된다고 안내하지 않습니다. 기존 전환 테스트 통과는 이런 운영 협조 없이 무중단 전환할 수 있다는 근거가 아닙니다.

각 전환이 끝나도 양쪽은 동기화 일시정지를 유지합니다. 같은 v2 head·hash와 자료 보존을 확인한 뒤 관리자가 재개합니다. 이후 일상적인 저장·동기화에서 이 절차를 반복하지 않습니다. 관련 구현은 `server/sync/service.mjs`, `server/sync/capture.mjs`, `worker/data.mjs`이며 저장 차단·일반 paused 저장 허용은 `tests/sync-upgrade-write-guard.test.mjs`에서 확인했습니다.

이번 내부망 운영 서버는 동기화 기능을 처음 도입하고 외부 DB는 테스트 자료를 초기화할 계획입니다. 현재 신규 내부 연결과 빈 Git 저장소의 최초 게시도 v1이며, 처음부터 v2로 게시하는 기능은 구현하지 않았습니다. 이미 v2인 저장소에 새 외부 사이트가 합류하는 경우에는 v2를 가져올 수 있습니다. 외부 DB 초기화만으로 기존 Git 이력이 제거되지는 않습니다. 운영 적용 시에는 기존 Git 이력과 신규 연결 조건을 확인하고, 현재 구현을 사용한다면 사용자 접속 재개 전에 첫 연결·v2 전환·검증을 마쳐야 합니다.

### reportTask·reportCell은 기존 사본의 내부 명칭

기존 화면의 **사본 추가** 기능은 원래부터 코드와 API에서 `report`·`/reports`라는 이름을 사용했습니다. 새 보고서 화면을 추가한 것이 아닙니다. `report`는 사본 이름·연도·설정·보기, `reportTask`는 그 사본 속 행 정보·순서, `reportCell`은 특정 셀 값·서식·버전을 나타내는 동기화 기록 종류입니다. 사본 ID를 키에 포함해 원본과 구분하며 앱에는 다시 기존 사본 표로 조합합니다. 변경된 셀과 필요한 행 정보를 나눠 보내는 것이 A3 분할의 목적입니다.

### 첨부 이미지 5MiB 정책은 아직 코드에 미반영

현재 문서 첨부 이미지는 내부·외부 모두 파일당 **10MiB**, 프로필 이미지는 **5MiB**입니다. **4MiB는 동기화 이벤트 파일의 한도**이며 이미지 파일은 별도 객체로 전송됩니다. 사용자와 문서 첨부 이미지의 신규 업로드 한도를 5MiB로 낮추는 방안을 논의했지만, 이 보고서 대상 커밋에는 그 변경이 없습니다.

이 정책을 구현할 경우 신규 업로드 제한과 기존 객체의 읽기·동기화·복구 허용 한도를 분리해야 합니다. 공통 10MiB 상수만 5MiB로 낮추어 이미 저장된 이미지를 거절하지 않아야 합니다. 5MiB 정책 논의는 동기화 이벤트 상한을 4MiB에서 올리자는 의미가 아닙니다.

## 성능 측정 이력

측정 자료·표본 수·판정 기준을 유지했습니다. 첫 준비 실행은 미전송 명령을 한 주기만 처리한 측정기 문제로 전환이 거절되어 미완료로 기록했습니다. 이후 측정기는 미전송 0과 상대 head 수렴을 확인한 다음 전환합니다.

| 완료 측정 | 유휴 저장 p95 미연결→연결 | 사본 편집 최대 | 5만 acknowledged 상태 조회 p95 전→후 | 실제 브라우저 추가 조회 |
| --- | --- | --- | --- | --- |
| 최적화 전 | 27.45→36.54ms (+33.13%) | 114.29ms | 4.00→32.97ms | 30개 모두 0 |
| 조회·캡처 최적화 1차 | 29.94→46.88ms (+56.60%) | 102.14ms | 1.85→1.87ms | 30개 모두 0 |
| 최종: 직렬화·사본 해독 최적화 2차 | 25.78→34.20ms (+32.67%) | 97.46ms | 2.19→1.61ms | 30개 모두 0 |

첫 두 완료 측정은 유휴 저장 증가 ≤10%, 사본 편집 모든 요청 <100ms 목표를 충족하지 못했습니다. 세 번째 유효 측정은 사본 편집 최대 97.460ms로 해당 목표를 충족했고, 유휴 저장 증가 32.670%는 여전히 목표 미달입니다. 원시 결과는 `sync-review-performance-before-optimization.json`, `sync-review-performance-after-optimization-1.json`, `sync-review-performance-after-optimization-2.json`에 각각 보존했습니다. 첫 최적화 후 두 번째 연결 구간에 76ms 지연이 나타났으며 별도 DB 커밋·GC 관찰 실행에서는 재현되지 않았습니다. 진단 실행은 합격 수치로 사용하지 않습니다.

세 번째 유효 측정의 소스 해시는 `9a43e06eaef12734e78d89c8b85bf4421216eca07f67220adea2c9bd723602c2`입니다. A6의 256KiB Markdown 측정에서 양쪽 1,000자 치환은 병합됐고 Node CPU p95는 236.942ms, 양쪽 1,001자 치환은 원문을 보존한 충돌이 됐고 CPU p95는 313.739ms였습니다. 전체 시나리오·장비·표본·제약은 [프로토콜의 검증 결과](SYNC_PROTOCOL.md#추가-최적화-2차-후-동일-조건-측정)에 기록했습니다. 실제 Supabase/Deno 성능이나 운영 장비의 지연을 보장하는 결과가 아닙니다.

측정 뒤 실행 코드의 유일한 변경은 `server/db.mjs`에서 v31의 기동 거절 오류에 기존 마이그레이션 안내를 적용한 것입니다. 최종 소스 해시는 `41eac8e12900714261ac01c0ff2539ca16ef2e06a879ba9378877fdd931785cb`이며, 이 한 줄을 되돌려 계산한 해시가 위 측정 소스와 일치함을 확인했습니다. 정상 v32 저장 경로와 측정기는 바뀌지 않았습니다.

별도의 진단에서 미전송 작업 1,170개가 쌓이는 동안 receipt 증분 조회는 호출당 최대 1행, 전체 receipt 합계와 사용자 목록은 각각 최초 1회였고 pending 전체 재조회는 없었습니다. 이 진단은 합격 수치에 포함하지 않았습니다. 추가 병목이 확인되지 않은 상태에서 원자 커밋·내구성·검증 경계를 완화하지 않았으며, 유휴 저장 목표는 미해결로 남깁니다.
