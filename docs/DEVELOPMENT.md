# 그래보드 개발 안내

[처음으로](../README.md) · [구성도](ARCHITECTURE.md) · [사용 안내](USER_GUIDE.md) · [운영 안내](OPERATIONS.md) · [데이터 형식](DATA_FORMAT.md) · [프로젝트 작업 규칙](../AGENTS.md)

그래보드는 실제 운영 중입니다. 개발·테스트 환경은 운영 DB와 문서 이미지 경로를 분리하고, 기능 변경 시 기존 운영 데이터와 저장 형식의 호환성을 확인합니다. 이 문서는 현재 저장소의 구현을 설명하며 실제 서버에 배포된 커밋·Node.js·DB 버전은 배포 전에 별도로 확인합니다.

## 작업 원칙

- 코드 탐색은 `codebase-memory-mcp`를 우선 사용하며, 미인덱싱 저장소는 `index_repository`부터 실행합니다. `search_graph` → `trace_path` → `get_code_snippet` 순서로 심벌·실제 호출 관계·구현을 확인하고, 복잡한 관계는 `query_graph`, 전체 구조는 `get_architecture`로 살펴봅니다.
- 문자열·오류 메시지·설정값·비코드 파일은 `search_code` 또는 `rg`로 찾습니다. 그래프 도구를 사용할 수 없거나 결과가 부족할 때도 `rg`와 파일 읽기로 보완합니다.
- 기능 변경 전에 유사한 기존 기능의 호출 경로와 공통 컴포넌트·스타일·저장 로직·이벤트 처리를 확인합니다. 기존 명명·구조를 따르고 구현을 재사용하거나 확장·공통화합니다.
- 같은 사용자 동작은 버튼·폼·포커스·문구·알림·삭제·실행취소·저장 흐름까지 일관되게 제공합니다. 요청이나 실제 요구사항에 근거하지 않은 안내 메시지·아이콘·확인 단계를 추가하지 않습니다.
- 완료 전에 기준으로 삼은 기존 기능과 비교하여 불필요하게 달라진 부분이 없는지 확인합니다.

## 구조

외부 런타임은 `edge/main.mjs`(Supabase/Deno) → `edge/handler.mjs` → 기존 `worker/entry.mjs`의 API·repository를 재사용합니다. `worker/gateway.mjs`는 Cloudflare에서 HTTP 전달·정적 파일·R2/Images binding을 담당합니다. `scripts/build-edge.mjs`가 공통 모듈과 고정 버전 npm import를 묶습니다. `tests/edge-gateway.test.mjs`는 실제 workerd 전달/자원 경계를, `tests/team-site.test.mjs`는 Pages → gateway → Edge handler → PostgreSQL 및 내부 SQLite/Git 흐름을 확인합니다. Deno 호환성은 생성 함수의 실행과 실제 Supabase 배포로 별도 확인합니다.

## 개발 실행

Node.js **22.13.0 이상**이 필요합니다(`package.json`의 `engines.node`). Node.js 16에서는 현재 실행 옵션과 내장 SQLite를 사용할 수 없습니다. 다른 서비스의 Node.js와 충돌하는 경우 프로젝트 실행 셸·서비스에 별도의 지원 버전 경로를 지정합니다.

```sh
npm ci --include=dev
npm run dev
```

Vite는 `5173`, API는 `4310` 포트를 사용합니다. 개발 프록시는 `/api`를 로컬 API로 전달합니다. 기본 포트를 변경할 때는 `vite.config.ts`도 함께 확인합니다. `.env`의 적용 방식은 [운영 안내](OPERATIONS.md#환경-설정)를 따릅니다.

개발용 `.env`를 만들 때는 `.env.example`을 참고하고 `DB_PATH`와 `DOCUMENT_IMAGES_DIR`가 개발 전용 경로인지 확인합니다. 이미 있는 `.env`는 덮어쓰지 않습니다. 예시 계정과 업무는 비어 있는 개발 DB의 최초 설정에서 선택하여 생성할 수 있습니다. 실제 운영 파일을 테스트 픽스처로 사용하지 않습니다.

| 명령            | 실행 내용                                                                     |
| --------------- | ----------------------------------------------------------------------------- |
| `npm run dev`   | API의 파일 변경 감시와 Vite 개발 서버를 함께 실행                             |
| `npm run build` | TypeScript 검사와 프런트엔드 배포 빌드. 결과는 `dist/`                        |
| `npm run start` | Node API 서버 실행. API와 준비된 `dist/`를 함께 제공하며 빌드는 수행하지 않음 |

운영은 빌드한 프런트엔드와 서버 소스·런타임 의존성을 함께 배포합니다. `dist/`만으로는 인증·업무 저장·문서·캘린더 API가 동작하지 않습니다. `start`가 `NODE_ENV=production`을 자동 설정하지 않으므로 운영 `.env` 또는 서비스 환경에서 지정합니다. 기존 운영 환경의 업데이트는 [운영 안내](OPERATIONS.md)의 절차를 따릅니다.

로컬 브라우저 테스트는 `npm run build` 후 `node scripts/e2e-server.mjs`로 실행합니다. 기본 주소는 `http://127.0.0.1:4311`이며, 기본 테스트 계정은 **`test@somansa.com` / `1234`**입니다. 이 계정은 테스트 전용 임시 DB에 생성되며 서버 종료 시 테스트 데이터가 삭제됩니다. 다른 포트는 `E2E_PORT`로 지정합니다.

## 운영 데이터에 영향을 주는 변경

DB 스키마·영속 데이터 형식·기존 데이터 일괄 변환·백업 호환성을 변경할 때는 [데이터베이스 변경 지침](DATABASE_CHANGES.md)을 먼저 읽고, 명시적 사용자 승인과 해당 문서의 구현·검증·배포 절차를 따릅니다. 현재 저장 구조와 지원 버전은 [데이터 형식](DATA_FORMAT.md#버전과-운영-호환성)에서 확인합니다.

## 주요 처리 흐름

### 조회와 개인 보기

로그인 세션은 기존 `sessions.expires_at`와 HTTP-only·SameSite=Strict 쿠키를 이용해 30일 유지합니다. 유효한 인증 요청에서 하루에 한 번만 갱신하여 매 요청의 DB 쓰기와 Set-Cookie를 피합니다. 로그아웃·비밀번호 변경은 자체 삭제·재발급 경로를 사용하며 만료·비활성 계정은 갱신하지 않습니다. DB 버전·형식은 변경하지 않습니다.

로그인 후 `/api/bootstrap`에서 소속 팀·사용자를 읽고 사용자·팀·기준 연도별 보기를 복원한 다음, `startMonth`부터 12개월에 해당하는 업무를 조회합니다. `getTasks`는 한 연도 또는 인접한 두 연도를 받아 SQL의 EXISTS 조건으로 중복 없이 업무를 읽습니다. 화면의 기준 연도는 업무 추가·삽입의 등록 연도입니다. 업무 응답은 ETag로 조건부 조회합니다. 팀·연도가 바뀌면 이전 요청 결과가 새 화면을 덮어쓰지 않도록 조회 대상을 검사합니다. 셀 값 저장은 SSE로 즉시 전달합니다. 행 추가·삭제·순서·공통 서식·설정과 사본 시트 변경은 리소스 SSE 알림으로 재조회합니다. 원본의 보완 조회는 내부망 7초·외부망 30초로 구분하며, 편집·저장 중에는 전체 목록 교체를 보류합니다. SSE 셀 갱신은 편집 중에도 처리합니다. 같은 범위·변경 버전의 동시 목록 갱신은 하나로 합치고, 429는 Retry-After와 증가하는 재시도 간격을 지킵니다. 업무·화면 정보 재조회가 성공하면 해당 조회 오류만 해제하며 저장·보기 저장·다른 작업의 오류는 보존합니다. 명시적인 내부 사이트 설정은 Access 인증 모드보다 우선합니다.

변경되지 않은 ETag 요청은 업무를 조회·직렬화하기 전에 304로 응답합니다. 조회 캐시의 전체 예산은 64MiB입니다. 원문과 gzip의 합이 예산보다 크면 gzip만 보관하고, 압축을 받지 않는 클라이언트의 응답 시에만 원문을 복원합니다. 압축본도 예산을 넘으면 캐시하지 않습니다. 이전 팀의 보기 저장이 뒤늦게 실패해도 현재 팀 화면에 오류를 표시하지 않습니다.

팀·연도 전환과 월 이동·월·주차 기간 선택은 왼쪽 업무 열에서 시작합니다. 달력은 항상 12개월이며 화살표는 한 달씩 이동합니다. `movePeriodView`는 월 선택을 실제 연월로, 주차 선택을 날짜로 유지하고 구간 경계에서만 선택 길이를 보존해 이동합니다. 연도 화살표의 전체 연도 초기화와 구분하며 원본·사본에 같은 규칙을 적용합니다. `taskQuery`는 같은 두 연도에 걸친 월들을 같은 요청 경로로 정규화하므로 월 이동마다 데이터를 재조회하지 않습니다. 보기의 저장 키와 업무 조회 범위를 분리하고, 늦은 조회 응답과 SSE가 다른 범위를 덮어쓰지 않도록 검사합니다. 기간 표는 포인터 캡처로 월/주 단위의 연속 범위를 선택하고 드래그를 마칠 때 보기를 저장합니다. 기존 보기 설정 모달은 제거했으며 열 고정은 머리글 메뉴, 팀 기본 셀 높이는 기본 서식 관리에 있습니다. 연도·기간 바, 서식 툴바와 팝업 제목 옆 `?` 도움말은 즉시 툴팁을 공유합니다. 팝업 소개 문구는 `Modal`의 `help`로 전달하며, 마우스 호버나 키보드 포커스로 확인합니다. 기본 서식과 표는 `Toolbar`를 공유하고, 서식 선택·테두리 팝업은 모달 안에서 열리면 해당 dialog를 portal 대상으로 사용합니다. 발표 모드는 현재 보기와 위치를 유지하며 종료하면 화면 위치를 복원합니다.

필터 목록과 현재 조건·선택은 팀을 열 때 `/api/filters?teamId=…`에서 읽고, 연도 전환 때 다시 읽거나 초기화하지 않습니다. 표 배치의 `views`와 별도로 연도 컬럼이 없는 `saved_filters`, `filter_states`에 저장합니다. `/api/filters/current`는 본인의 현재 상태만 저장하며, 공용·개인 정의 변경은 `/api/filters/:id`에서 권한을 검사합니다. 팀원이 공용 조건을 바꾸면 개인의 현재 조건으로 분리합니다. 스냅샷과 UI에서만 배치·조건을 하나의 View로 합칩니다.

필터 신규 저장·같은 이름 저장이 완료되면 갱신한 목록에서 이름과 공개 범위가 일치하는 필터를 찾아 바로 선택·적용합니다. 목록에서 선택할 때도 `applySavedFilter`로 같은 조건·선택 저장 경로를 사용합니다. 목록에서 필터를 선택할 때는 `Grid`의 기존 `jump`를 통해 렌더링 후 세로 스크롤을 0으로 이동하고 가로 위치는 유지합니다. 원본·사본과 같은 필터 재선택에 공통 적용하며, 저장 완료 경로는 `scrollToTop: false`로 현재 위치를 유지합니다. 사본에서 원본으로 돌아올 때의 위치 복원도 유지합니다. 이름 변경만 할 때는 현재 선택을 바꾸지 않습니다. 선택 상태는 필터 보기 표시줄과 목록 항목의 `aria-pressed`에 반영하며 목록 오른쪽 체크 아이콘은 표시하지 않습니다.

### 셀 저장과 동시 수정

작업 완료 안내는 `src/Toast.tsx`의 `Toast`·`useToast`를 사용합니다. 설정·비밀번호·이력 정리·사본 이름 모달 안에서 렌더링하여 열린 dialog 위에 표시하며, 같은 문구를 다시 알려도 4초 표시 시간을 갱신합니다. 사본 표의 자동 저장 상태는 보조기기에 알리고, 저장 오류는 표 위에서 확인·재시도할 수 있습니다. 오류·입력 검증과 현재 진행 상태는 해당 화면에서 유지합니다.

`src/api.ts`는 `shared/api-error-message.js`로 플랫폼 오류의 작업명·원인별 조치·HTTP 상태·제공된 요청 ID를 표시합니다. Supabase의 `sb-error-code`/JSON `code`, `Retry-After`를 읽으며 provider의 임의 `message`·HTML·SQL 원문은 표시하지 않습니다. 기존 앱 검증·권한·충돌 메시지와 `ApiError.details`는 보존합니다. 네트워크 실패와 잘못된 성공 응답 형식도 분류하며 호출자가 취소한 요청은 그대로 전달합니다. `tests/api-error-message.test.mjs`와 `tests/browser/api-errors.spec.ts`는 429·실행 한도·인증·시간 초과·비정상 본문을 검사합니다.

기본 셀 툴바와 발표 도구는 `ZoomControls`의 50~200% 입력·증감·복원을 공유합니다. 확대는 `.grid-area`에만 적용하며 `Grid`의 행·열 크기 드래그는 포인터 이동량을 배율로 나눠 원래 치수에 반영합니다. 확대율은 화면 상태이며 업무 데이터와 View에 저장하지 않습니다. 발표 모드는 기본 배율을 초기값으로 받아 별도로 조절하고 종료 시 기본 배율을 복원합니다.

기간 밖 주차와 접힌 월을 포함한 현재 12개월 전체 열 순서로 숨김 구간을 계산합니다. 날짜 구간을 펼칠 때는 현재 보이는 주차와 펼칠 주차만 남기고 나머지를 `hiddenWeeks`로 표현하여 다른 구간의 숨김을 유지합니다. 달력의 선택 표시도 실제 표시 주차를 사용합니다.

서식 선택 범위와 테두리의 인접 셀은 필터를 통과한 전체 행(숨긴 행 포함)과 숨김 전 전체 열 순서로 계산합니다. 값 편집·복사·붙여넣기·행 이동은 보이는 셀 기준을 유지합니다.

`Toolbar`의 서식 복사는 `App`에 선택 범위의 표시 서식을 보관하고, `Grid`의 선택 드래그 종료 또는 Enter에서 적용합니다. 값은 보내지 않고 기존 `mutate`·`submitChanges` 경로로 셀 버전과 공통 서식 revision을 검사합니다. 한 셀의 서식을 행·열·전체에 적용할 때는 기존 공통 서식 scope를 사용하며 사본도 기존 저장·실행취소 경로를 공유합니다. 복사한 셀의 표시 서식을 재현하기 위해 공통 scope에도 기본 글꼴·크기 값을 명시하고, 없는 서식 속성은 null로 전달하여 대상에 남은 강조·배경색 등을 제거합니다. 대상 업무의 기본 서식으로 되돌리는 reset과 구분합니다. 단일 적용은 완료 후 해제하고 두 번 클릭한 연속 적용은 Esc·버튼 클릭·시트 전환으로 해제합니다. 서식 복사의 전역 Esc는 열린 dialog에 양보합니다. 그 외에는 이벤트 전파를 유지해 저장된 필터 메뉴도 닫히게 하며, Grid는 이미 처리된 Escape(`defaultPrevented`)나 서식 복사 중인 Escape에서 선택을 해제하지 않아 이벤트 도중 렌더링 시점에 영향을 받지 않습니다. 저장 중 추가 적용은 `submitChanges`와 같은 `rejectPendingChanges` 안내를 사용하고 복사 상태를 유지합니다. DB·저장 형식은 변경하지 않습니다.

주차 기본 경계선은 `settings.weekBorders`에 저장하며 `shared/borders.js`의 `weekBoundaryStyles`와 `withWeekBoundaries`로 실제 표시·반출 열의 첫 날짜와 마지막 날짜에 적용합니다. 같은 경계를 공유하는 두 셀을 함께 계산하며, 셀이나 행·열에 직접 지정한 선이 경계선보다 우선합니다. `null`·`none`이나 업무 기본 서식에서 상속된 선은 주차 경계선을 가리지 않습니다. 원본 셀 서식은 수정하지 않으며 그리드의 머리글·셀·텍스트 넘침 경계와 XLSX에서 같은 계산을 사용합니다. 셀 클립보드는 저장된 서식만 복사합니다.

이번 주 기본 좌우 테두리는 선택 설정 `settings.currentWeekBorders`를 같은 `weekBoundaryStyles` 계산에 전달합니다. 실제 표시·반출 열 중 한국 시간의 월요일 키에만 적용하며, 설정한 방향은 양 끝 경계선보다 우선합니다. 직접 지정한 셀·행·열·이웃 셀의 선은 기존 `withWeekBoundaries` 경로로 우선합니다. `Grid`와 `PeriodPicker`는 `useTodayKey`로 한국 시간 자정과 탭 복귀 시 날짜를 갱신하므로, 자동 조회가 없는 사본에서도 이번 주 표시가 이동합니다. 기존 `teams.settings` JSON에 선택 필드만 추가하며 SQLite v30·JSON v6, 셀·이력·사본의 기존 읽기 호환성을 유지하고 데이터 변환은 하지 않습니다.

`shared/compact.js`의 서식 사전을 HTTP 요청·응답, SSE, JSON 반출, 이력·스냅샷에 공통 적용합니다. DB는 `styles` 테이블을 `cells.style_id`·`tasks.default_style`·`tasks.row_style`·`format_rules.style_id`에서 참조합니다. 새 셀의 빈 내용과 불필요한 서식은 생략하되, 삭제·실행취소 후에도 기존 셀 버전은 유지합니다. `tests/compact-storage.test.mjs`는 실제 생성 API, 3,180셀 범위 저장, 공통 사전 크기, 서식 정리 후 이력 복원·재시도, 변경 없는 요청과 충돌, 잘못된 압축 참조를 검증합니다.

2026-10-12, 기준 커밋 `5a79eaf`와 v14 코드를 같은 합성 업무 100행으로 비교했습니다. 임시 메모리 SQLite DB·로컬 HTTP 서버를 각각 만들고 2,000셀 공통 서식 변경을 번갈아 실행했습니다(준비 4회, 측정 24회, Node.js v22.23.1). 요청 인코딩부터 응답 해석까지의 중앙값은 31.24→29.16ms, P95는 34.75→32.62ms였습니다. 마지막 작업 기준 요청 JSON은 830,105→214,310바이트, 응답 JSON은 1,676,634→443,003바이트, 이력·재시도 저장 본문은 1,676,685→443,076바이트로 줄었습니다. gzip(level 1) 응답은 23,505→17,572바이트입니다. 공백 주차에 null 테두리가 채워진 별도 합성 행은 54→4셀로 저장되고, 응답 JSON은 6,937→591바이트였습니다. 같은 환경의 비교값이며 운영 네트워크·디스크 지연의 보장은 아닙니다. 상세 결과는 `docs/validation/compact-storage-performance-20261012.json`에 있습니다.

공통 서식의 범위 판정은 요청별로 행·열·제외 열을 `Set`으로 한 번 인덱싱하고 재사용합니다. 각 셀마다 선택 행 배열 전체를 다시 검색하지 않습니다. 2026-10-13 로컬 Node.js 22.23.1·메모리 SQLite·HTTP API에서 10,000행, 기존 190,000셀에 배경색 공통 규칙을 적용한 3회 측정의 중앙값은 10,227.75→335.82ms로 줄었습니다. 요청 인코딩부터 응답 해석까지 측정했으며, 요청·응답 크기와 셀 레코드 수는 동일합니다. 운영 환경의 지연 보장은 아닙니다.

압축 응답을 풀 때는 참조가 바뀌는 경로만 복제하며 원본 전송 데이터는 변경하지 않습니다. 같은 Node.js 22.23.1·Chromium 환경에서 기준 커밋 `5a79eaf`와 당시 변경 코드를 순서대로 측정한 1만 행 화면 표시 10회의 중앙값은 209→251ms, P95는 713→841ms였습니다. 동시 30명 조회 P95는 1,001→1,050ms, 저장은 46→31ms, 검색은 170→167ms였습니다. 초기 표시에는 소폭 증가가 남아 있으며, 상세 로컬 결과는 `docs/validation/precommit-performance-20261013.json`에 있습니다.

셀 편집을 확정하면 `/api/cells/batch`로 `operationId`·최초 `createdAt`, 셀별 `expectedVersion`, 값 또는 서식을 보냅니다. 서버는 인증·팀 접근·업무 편집 권한·속성 종류를 확인하고 전체 변경을 한 트랜잭션으로 저장합니다.

한 셀이라도 버전이 다르면 409로 전체 작업을 취소합니다. 같은 사용자의 동일 작업 ID 재시도는 이전 성공 결과를 재사용합니다. 저장 실패 시 입력과 요청을 유지하고, 재적용 시 최신 버전을 확인합니다. 실행취소도 같은 버전 검사와 저장 경로를 사용합니다. 업무 추가 취소는 삭제 응답의 `updatedAt`을 보관하고 재실행할 때 서버에 보내며, 그 사이 다른 복구·수정·삭제가 있으면 실제 복구와 감사 기록 전에 409로 거절합니다.

전후 셀 데이터는 `audit`에 한 번만 저장하고 `operations`에는 이력 ID·팀 ID·응답 시각·업무 수정시각만 남깁니다. 여러 팀이 섞인 요청은 팀별 원래 위치 번호를 함께 기록합니다. 정상 저장에서는 현재 셀과 같은 변경을 건너뛰며 과거 이력을 읽거나 비교하지 않습니다. 재시도에만 `audit.id` 인덱스로 읽어 최초 응답을 재구성합니다. 참조가 사라졌으면 410을 반환하고 재적용하지 않습니다. `tests/cell-operations.test.mjs`는 저장량, 정상 저장의 이력 조회 부재, 재시도의 인덱스 사용, 재시작·후속 편집·복원·권한 변경·팀 삭제·트랜잭션 롤백을 검증합니다.

시스템 감사 로그는 `server/system-audit.mjs`와 `src/SystemAuditLog.tsx`에서 조회합니다. 공통 이력만 관리자에게 공개하고 한국 시간 날짜·수행자·종류로 필터링합니다. `(created_at,id)` 커서로 50건씩 조회하며 목록은 전후 JSON을 읽지 않습니다. 브라우저는 상세를 펼칠 때만 가져오고 필터가 바뀌거나 화면을 닫으면 이전 요청을 취소합니다. `tests/system-audit.test.mjs`는 실제 로그인·로그아웃 기록, 세션 확인·재발급 시 중복 방지, 권한·날짜 경계·같은 시각의 페이지 경계·정리 중 커서 유지·큰 상세·인덱스 사용을, `tests/browser/system-audit.spec.ts`는 로그인 화면부터 오늘 로그 조회, 검색·초기화·페이지 이동·상세 지연 조회·오류 재시도·늦은 응답 무시를 검증합니다.

시스템 이력 정리는 `server/history-cleanup.mjs`와 `src/HistoryCleanup.tsx`가 담당합니다. 팀별 본문 용량을 집계하고 관리자 전용 미리보기 토큰에 고정된 팀·한국 시간 기준 날짜로 작은 묶음을 처리하며, 일반 저장 경로에는 요청 시각의 상수 시간 검사만 추가합니다. `tests/history-cleanup.test.mjs`는 권한·토큰 만료·한국 시간 날짜 경계·팀별 UTF-8 용량·다른 팀 및 다중 팀 참조 보호·묶음 한도·롤백·만료 요청 재실행 방지를 실제 API로 검사합니다. `tests/browser/history-cleanup.spec.ts`는 별도 임시 서버에서 팀·날짜 변경 시 미리보기 폐기·늦은 응답 무시·확인창 취소·실행·중단·재개·팀장 메뉴 제한과 재시도 생성시각 보존을 확인합니다.

2026-10-12 로컬 Node.js 22.23.1에서 변경 직전 코드와 참조 저장 코드를 별도 임시 SQLite DB·API 서버로 실행해 비교했습니다. 합성 업무·텍스트·서식을 동일하게 구성하고 두 서버에 번갈아 HTTP 요청을 보냈습니다. 각 서버 6회 준비 실행 후 한 셀은 120회, 2,000셀은 30회 서식 저장을 측정했으며, 요청 시작부터 응답 JSON 읽기까지의 시간입니다. 한 셀의 중앙값은 2.13→2.10ms, P95는 2.48→2.55ms로 비슷했고, 2,000셀 중앙값은 45.84→39.04ms, P95는 49.45→42.58ms였습니다. 2,000셀 작업의 이력·재시도 JSON 합계는 작업당 평균 4.18→2.09MB로 약 50% 감소했습니다. 저장량 평균에는 준비 실행을 포함한 36개 작업을 사용했습니다. 운영 환경의 지연 보장이 아니며, 기존 DB를 변환한 결과도 아닙니다.

커밋 전 전체 리뷰에서는 `1543a6e`와 최종 코드를 같은 임시 데이터로 교차 측정했습니다. 한 셀 240회·2,000셀 100회(각 6회 준비 실행 제외)의 HTTP 요청·응답 시간이며, 2,000셀 작업의 이력·재시도 본문 저장량은 약 50% 줄었습니다.

| ----- | ------------------------- | ----------------- |
| 1     | 2.14 → 2.14ms             | 2.58 → 2.95ms     |

리뷰 중 열 너비 드래그마다 셀 표시 서식이 다시 만들어지는 것을 수정했습니다. 표시 서식은 너비와 독립적인 열 키와 업무·경계선이 바뀔 때만 계산합니다. 2,000행·Chromium CPU 4배 감속 조건에서 드래그 단계 중앙값은 수정 전 42ms에서 34ms로 줄어 기준 커밋의 34ms와 같았습니다. 셀 선택 중앙값도 기준 커밋과 최종 코드 모두 33ms였습니다. 별도 1만 행·45.5MB 스냅샷 샘플의 gzip 압축은 level 9의 534~546ms·1.60MB에서 level 1의 64~67ms·2.42MB로 바뀌었습니다. 이 수치는 로컬 합성 데이터 측정이며 압축 시간은 스냅샷 API 전체 응답 시간이 아닙니다.

`GET /api/tasks`의 `X-Cell-Event-ID` 헤더는 스냅샷 시점의 SSE 커서입니다. 304 응답에도 포함합니다. 프런트엔드는 스냅샷을 표시한 뒤 `/api/cells/events?teamId=…&year=…&after=…`에 연결하므로 조회와 연결 사이의 변경도 재전송받습니다. 서버는 DB 커밋 후 값 또는 개별 서식이 바뀐 셀 레코드를 전송합니다. 레코드의 값·서식·버전은 일관된 저장 결과를 사용하며, 공통 서식 변경은 팀 리소스 알림으로 최신 목록을 읽어 반영합니다. 재시도된 작업·실패한 트랜잭션·개인 View 저장은 셀 이벤트를 발생시키지 않습니다.

SSE는 로그인 세션과 팀 접근을 구독 시점, 이벤트 전송 전, 15초 heartbeat마다 검사합니다. 여러 연도에 속한 업무의 셀 변경은 해당 연도 구독자에게 전달합니다. `startMonth`로 두 연도를 구독할 때도 SSE 연결은 하나이며, 작업별 변경 셀을 중복 제거하여 하나의 이벤트로 전송·재전송합니다. 따라서 하나의 커서가 두 연도의 변경 전체를 나타냅니다. `Last-Event-ID`로 재접속하며, 서버 메모리의 최근 512개 작업·8MiB 범위에서 재전송합니다. 서버 재시작·버퍼 만료 또는 256KiB 초과 이벤트는 `reset`을 보내 최신 DB 스냅샷과 새 커서로 복구합니다. DB 스키마 변경이나 별도 메시지 서버는 필요하지 않으며 단일 앱 프로세스를 전제로 합니다.

수신한 변경은 40ms 동안 모아서 셀별 최신 버전만 반영하고 바뀌지 않은 행 객체는 재사용합니다. 느린 연결의 서버 송신 버퍼와 클라이언트 대기 셀 수에도 한도를 둡니다. 숨긴 셀도 내부 데이터는 갱신하지만 개인 View·선택·스크롤·실행취소 기록은 바꾸지 않습니다. 편집 시작 시점의 값과 버전을 보관하여 입력 중 원격 변경으로 저장 기준이 바뀌지 않도록 하며, 해당 행의 필터·정렬 재평가는 편집 종료까지 미룹니다. 본인이 입력 중 적용한 서식 저장만 편집 기준 버전을 올립니다. 늦은 HTTP 응답과 재접속 스냅샷도 최신 셀을 되돌리지 않습니다.

전체 행·열 선택은 선택한 업무 ID·열 키와 서식만 서버로 보내며 셀마다 요청을 만들지 않습니다. 서버는 공통 규칙과 영향을 받는 기존 셀 예외만 변경합니다. `shared/formatting.js`가 표시·행 복사·XLSX 반출에서 같은 상속 계산을 사용하고, `src/format-selection.js`가 숨김을 포함한 선택 영역의 테두리를 같은 패턴끼리 묶습니다. 셀 예외와 값은 개별 버전으로, 공통 규칙은 팀별 revision으로 충돌을 검사합니다. `format-audit` 재시도·이력 정리·업무별 이력 조회도 일반 셀 변경과 같은 보관 계약을 따릅니다. 공통 규칙 전송은 문서별 `$formats` 사전으로 중복을 제거합니다.

저장 규칙의 기준 문서는 [데이터 형식과 API](DATA_FORMAT.md#저장-규칙-요약)입니다. 내부 모델은 긴 서식 이름을 사용하되, 변경 이력의 JSON 표시는 `pack`으로 저장 형식을 그대로 재구성합니다. 셀 서식 요약 JSON도 `compactStyle`로 축약합니다. 업무 생성·이동·삭제 이력에는 `taskAuditSnapshot`으로 관계없는 행 규칙과 업무 ID를 제외합니다. 실시간 업무 응답의 팀별 공통 상태는 유지합니다.

`tests/common-formatting.test.mjs`는 공통 행·열 저장, 연도 경계, 1,000행 빈 셀 미생성, 속성별 우선순위, 셀 예외 재적용, 복사, 충돌·권한·이력 복원과 업무 이력의 불필요한 규칙 제외를 실제 API로 검증합니다. `tests/browser/common-formatting.spec.ts`는 화면의 행 선택→월 이동→새해→새로고침, 열 서식→셀 예외→재적용→실행취소·재실행, 큰 글자의 행 높이·테두리, 축약된 이력 JSON 표시를 확인합니다.

2026-10-13, 당시 코드의 셀별 저장과 공통 규칙 저장을 같은 합성 업무 100행·56열에서 비교했습니다. 별도 메모리 SQLite·로컬 HTTP API를 사용해 4회 준비 후 24회씩 번갈아 측정했습니다(Node.js v22.23.1, 요청 생성·인코딩부터 응답 해석까지). 행 전체 서식 요청은 597,953→10,804바이트, 응답은 1,237,800→11,005바이트, gzip(level 1) 응답은 49,959→2,990바이트였습니다. 원래 제목 셀만 100개인 데이터에서 셀별 저장은 5,600셀을 만들었고, 공통 규칙 저장은 100셀을 유지하고 규칙 하나를 추가했습니다. 중앙값은 73.05→3.92ms, P95는 84.86→4.24ms였습니다. 이는 같은 코드 안의 두 저장 경로 비교이며 운영 디스크·네트워크 지연 보장이 아닙니다. 로컬 상세 결과는 `docs/validation/common-formatting-performance-20261013.json`에 있습니다.

`/api/teams/:id/events`와 `/api/reports/:id/events`는 성공한 변경 뒤 재조회 알림을 보냅니다. 개인 보기 저장은 알리지 않으며 셀 값은 기존 델타 스트림을 유지합니다. `useResourceSync`는 같은 리소스의 연결을 탭 안에서 공유하고 짧은 연속 알림을 묶습니다. 페이지별 `X-Client-ID`로 이미 응답을 반영한 자기 변경 알림의 중복 조회를 줄이며 같은 계정의 다른 탭은 별도로 갱신합니다. 편집·저장 중에는 갱신을 보류하고 화면·팀을 떠날 때 연결과 요청을 정리합니다. 사본의 독립 셀 수정은 `rebaseReportCells`로 최신 시트에 재적용하되 동일 셀·행 삭제·구조 작업 충돌은 기존 오류 흐름으로 남깁니다. 원격 변경 뒤 실행취소 기준에는 상대방의 최신 값이 포함됩니다. 문서 유무·개수는 사본 시트 revision과 독립적이므로 같은 revision 응답에서도 기존 문서 메타데이터 갱신 경로를 사용합니다. 조회 중 로컬 문서나 이름이 바뀌면 오래된 응답을 적용하지 않고 다시 읽습니다.

### 업무 문서와 에디터 선택

문서 브라우저의 검색은 선택한 팀·연도·원본/사본 범위에서 작업 이름만 부분 일치로 비교하며, 앞뒤 공백과 영문 대소문자를 무시합니다. 문서 제목과 본문은 검색하지 않고, 일치한 작업의 모든 문서를 순서대로 표시합니다. 작업 이름을 클릭하면 첫 문서를 엽니다. 본문은 결과 페이지의 짧은 미리보기를 만들 때만 읽습니다.

`DocumentEditor`는 모든 Markdown 저장 경로에서 본문 SSE를 구독합니다. 업무·사본 업무·원본 메모·사본 메모·캘린더 문서의 저장 시 최신 스냅샷을 전달하며 재연결에서는 마지막 커서 이후 변경된 경우에만 본문을 보내고 `shared/document-merge.js`로 독립 변경을 병합합니다. `sync: {session,sequence}`는 서버 프로세스 내 전송 순서이며 숫자 또는 UUID인 영속 revision과 분리합니다. HTTP 응답이 SSE보다 먼저 도착해도 오래된 스냅샷을 다시 적용하지 않습니다. 접근 권한은 전송마다 다시 확인합니다. 업무 상세의 여러 문서 탭은 선택한 문서만 본문 스트림을 유지하고, 다시 선택할 때 최신 스냅샷을 받습니다. 꼬리 메모는 여러 본문을 나란히 표시하므로 펼친 패널에서 로딩한 모든 메모의 구독을 유지합니다. 다른 메모를 선택해도 이미 표시된 본문은 자동 갱신하며, 패널을 접으면 구독을 해제합니다. 문서 목록의 추가·이름·순서는 별도 목록 알림으로 갱신합니다.

`GridCell`의 작업명 오른쪽 문서 버튼은 기존 `rowMenu` 상세 열기 경로를 공유합니다. 본문이 없는 업무에서는 행 hover·작업명 선택·키보드 초점에서 흐리게 표시하고, 본문이 있으면 문서 개수 표시와 함께 항상 표시합니다. 편집 중에는 버튼을 숨기고 발표 모드에서는 빈 업무의 버튼을 만들지 않습니다. 발표 중 문서가 있는 업무의 버튼은 기존 `RowPanel`을 읽기 전용으로 열며 업무 동작 버튼을 숨깁니다. 버튼의 포인터·키보드 이벤트는 셀 편집·범위 선택으로 전파하지 않습니다.

`TaskDocumentPanel`과 `RichMarkdownEditor`를 동적 import로 분리합니다. 목록에는 `hasDocument`만 보내고 상세에서 문서 제목 목록, 선택한 탭의 본문을 순서대로 조회합니다. 내용도 로컬 초안도 없으면 캐릭터 안내와 작성 버튼을 표시하고 본문·리치 편집기 조회를 미룹니다. 작성 버튼은 저장 부작용 없이 편집기를 열고, 기존 본문·초안은 바로 복원합니다. 방문한 문서만 편집기를 만들고 숨겨진 탭의 상태는 유지합니다. 원문 입력창은 팝업의 문서 영역에 flex로 맞춰지고 내부에서 스크롤하며, 리치 본문은 기존처럼 상세 영역을 스크롤합니다. 한글 조합 중에는 저장하지 않으며 전환·닫기 전에 입력을 flush합니다. 초안 저장 키는 사용자·팀·원본/사본·업무·문서 ID로 나눕니다.

상세는 `DocumentLoading`으로 중앙의 같은 캐릭터와 높이를 유지한 뒤 탭·도구·본문을 함께 표시합니다. `LoadingState`를 앱 초기화·업무표 조회·XLSX 처리·감사 로그·용량 조회에서도 공유합니다. `GraeLoading`은 기존 캐릭터의 네 칸을 순서대로 밝히고 reduced-motion에서는 정지합니다.

Milkdown 진입 전 AST 왕복 검사를 하고 안전한 `<br>`만 줄바꿈으로 표시합니다. 지원하지 않는 HTML·외부 이미지 등은 원문을 보존합니다. 이미지 붙여넣기·드롭은 문서별 권한 API를 거치며 크기 조절 값은 로컬 이미지 URL에 보존합니다. 문서 제목은 탭 안에서 글자 길이에 맞춰 늘어나는 입력 상자로 수정하며, UI 및 원본·사본 생성/이름 변경 API에서 최대 50자를 허용합니다. 탭에는 10자 이상인 이름을 앞 9자와 …로 줄여 표시하되 접근성 이름·툴팁·저장값은 전체 제목을 유지합니다. 조합 입력을 보호하고 blur·Enter·탭 전환·닫기에서 동일한 저장 Promise를 기다립니다. 문서별 편집기의 원문/리치 토글은 선택된 탭의 오른쪽으로 portal 렌더링하여 본문 상태를 유지합니다. 리치 편집의 저장 상태는 툴바 오른쪽 실행취소·재실행 버튼 앞에 렌더링하고, 원문·읽기 전용·편집기 오류 상태에서는 제목 줄에 표시합니다. 제목 줄과 그 바로 아래 리치 툴바는 스크롤 상단에 고정합니다. 제목 탭은 가로 스크롤하고 수평 wheel 이벤트 및 overscroll 경계를 처리해 브라우저 탐색을 방지합니다. 전체 페이지에서도 업무 속성을 유지합니다.

`src/DocumentToggle.ts`는 `<details>`·`<summary>` HTML 블록을 remark 변환 단계에서 `details` 노드로 묶고 `toggle`·`toggle_summary`·`toggle_content` ProseMirror 노드, 직렬화 핸들러, Enter·Backspace 처리, 요약 줄의 접기 버튼 node view를 제공합니다. `open` 속성과 `<summary>` 안의 `<h1>`~`<h6>`만 허용하며 그 외 속성·태그나 닫히지 않은 블록은 html 노드로 남겨 `checkMarkdown`이 원문 모드로 유도합니다. 같은 줄에 이어진 본문이나 `</details>` 뒤 텍스트는 Markdown으로 다시 파싱해 묶습니다. 요약은 `text*`만 담아 이미지·HTML이 들어가지 않으므로 서버의 이미지 참조 검사는 기존 파서로 본문 이미지를 찾습니다. 접힘 상태는 `open` 속성으로 문서에 저장하고 체크박스처럼 실행취소 이력에 포함하며, 읽기 전용에서는 DOM에서만 바꿉니다. `checkMarkdown`은 remark 변환 후 트리를 검사합니다. `src/DocumentSlashMenu.tsx`는 문단에서 `/`와 이어진 글자를 찾아 툴바와 같은 명령 목록을 거르고, 표 셀에서는 열지 않습니다. 메뉴 위치·선택 상태와 Esc 해제는 `RichMarkdownEditor`의 플러그인 view와 `handleKeyDown`에서 갱신합니다. 공식 `trailing` 플러그인은 표·코드·목록·토글·이미지로 끝나는 문서 뒤에 빈 문단을 유지하며 doc 직렬화가 마지막 빈 문단을 제외하므로 저장 결과는 같습니다. 원격 병합의 비교 문서에도 같은 빈 문단을 붙여 그 줄에 있던 커서를 보존합니다. 업로드로 삽입한 이미지는 `appendTransaction`에서 다음 문단(없으면 새로 생성)으로 커서를 옮기고, 본문 아래 여백 클릭은 문서 끝으로 이동합니다. `tests/browser/document-editor-blocks.spec.ts`가 세 동작을 검증합니다.

연간 업무의 `canEdit(user, task)`는 팀별 `canContribute`를 사용합니다. 팀장·팀원은 작성자·담당자·지원자와 관계없이 같은 팀의 표·속성·문서를 편집하고 업무를 삭제·실행취소할 수 있습니다. 담당자·지원자 지정과 묶음 행 삽입·붙여넣기도 같은 기준을 사용합니다. 꼬리 메모는 기존 `canContribute` 검사로 공동 편집하며, 열람자와 외부 팀 사용자의 쓰기는 거절합니다. 캘린더 개인 일정의 소유자 검사와 팀 관리 권한은 별도로 유지합니다. 권한 설정 필드·SQLite 스키마·기존 데이터 변환은 추가하지 않습니다.

원본과 사본 문서 모두 자동 저장합니다. 각 사본은 자체 문서 배열을 갖고 불변 본문만 공유하며, 저장은 해당 문서 참조만 교체합니다. 분기 UI·원문/분기 연결 API는 제거했습니다. 사본 표의 `useReportDraft`는 저장 중 새 입력을 대기열에 추가하고 완료 후 이어 저장합니다. 실행취소는 셀/행 상태를 복원하지만 현재 행의 문서 참조는 유지합니다. 삭제 직전 문서를 읽어 행 복원에 포함합니다. 사용자 자료는 검증 fixture로 사용하지 않습니다.

사본 본문 자동 저장은 `report_documents`의 해당 참조만 갱신하고 이전 본문 버전만 정리합니다. 문서 조회용 행 ID·제목 인덱스는 압축 BLOB 해시로 무효화하며, 셀·본문을 보관하지 않는 16MiB 예산의 캐시를 사용합니다. 표를 해제한 뒤에는 `readReport`로 최신 문서 참조를 합쳐야 합니다. 여러 행 삭제·실행취소는 `POST /api/reports/:id/documents/batch`로 최대 100개 행씩 읽고 실행취소 이력을 한 번에 갱신합니다. 응답 본문 합계는 8MiB에서 다음 행으로 나누되 한 행의 문서는 분할하지 않으며, 클라이언트는 반환된 행 수부터 이어 읽습니다. 화면에서 문서가 없어 보이는 행도 함께 조회해 다른 사용자의 최근 저장을 보존합니다.

사본 메모는 `server/memo-storage.mjs`의 참조 복사와 `DocumentBusinessService`의 공통 편집 경로를 사용합니다. 사본 표를 읽거나 저장할 때 메모 본문을 읽거나 표 BLOB에 포함하지 않습니다. 테스트는 복사 전후 `document_versions` 수, 공유 참조 ID, 메모 편집 전후 표 BLOB·revision 동일성, 재복사·재시도·권한·충돌·정리·이미지·JSON 반출·백업과 화면의 닫힌 상태 복사·저장 직후 재복사·원본 분리를 검증합니다.

업무 상세와 꼬리 메모는 `DocumentPanel`의 같은 탭·제목 입력·메뉴 구현을 사용합니다. 각 탭은 편집 여부와 관계없이 40px 높이를 유지하며, 제목 입력은 측정용 텍스트가 결정한 grid 영역 위에 배치해 팝업의 공통 입력칸 너비가 탭 폭을 늘리지 않게 합니다. 화살표 hover는 사본 탭과 같이 색상을 바꾸지 않으며 선택 상태만 표시합니다. 각 문서 탭 오른쪽의 아래 화살표에서 공통 이름 변경·삭제 메뉴를 엽니다. 다른 문서의 메뉴를 열 때도 기존 `select()`로 현재 입력을 저장한 뒤 대상을 전환합니다. 메뉴는 `SheetTabs`와 같이 가로 스크롤 영역 밖의 제목 줄에 배치하고 화살표 위치를 따라가며, 화면 밖으로 스크롤되면 닫습니다. 기존 바깥 클릭·Escape·Tab 닫기와 열람자 권한을 유지합니다. 문서 폭은 `DocumentPage`가 포인터 캡처로 조절하며 키보드 조절·취소를 지원합니다. 폭은 사용자·팀·원본 연도/사본·문서별 localStorage에 보관하고 본문·순서는 기존 API를 이용합니다. `AnnualMemoPanel`은 제목 버튼·중앙 가로 스크롤 영역·별도 본문으로 아코디언을 구성하고, 사용자·팀·원본 연도/사본별 `weekly-plan:memo-open:…` 키에 펼침 상태를 기억합니다. 닫기는 기존 문서 `flush()`가 성공한 뒤에만 상태를 저장하며, 접힌 상태에서는 `DocumentPanel`을 마운트하지 않아 메모를 조회하지 않습니다. 저장소 접근이 차단되어도 현재 화면에서는 열고 닫을 수 있습니다. 복원된 열린 상태에서는 표를 아래로 이동하지 않으며, 직접 아코디언을 열었을 때만 `scrollOnOpen`으로 문서를 보여 줍니다. 탭 선택은 탭 레일의 가로 위치만 조절합니다. 아코디언은 서식 툴바와 같은 높이 변수와 팀 테마를 사용하고 글자는 11px입니다. 발표 모드에서도 같은 패널을 읽기 전용으로 유지하며, 발표 도구의 입력 가로채기에서 메모·업무 문서 버튼·열린 dialog를 제외해 아코디언·문서 탭·팝업을 조작할 수 있습니다. 꼬리 메모에 마우스를 올리거나 dialog가 열리면 발표 커서 덮어쓰기를 멈추고 레이저·지우개 표시를 숨겨 기본 커서를 복원합니다. 전역 Escape 처리도 열린 dialog에 양보하므로 중첩 이미지 팝업을 닫을 때 발표가 종료되지 않습니다. `SheetHorizontalScroll`은 업무 표의 가로 스크롤을 메모 위에 표시하며, 기존 `.sheet-scroll`의 좌표와 동기화해 행 가상화·고정 열·위치 복원을 유지합니다. 표의 가로 wheel·터치 이동을 처리하고 메모 내부 제스처는 각 문서와 메모 영역에 맡깁니다.

### 접속 토큰과 클라이언트 시각

`AccountMenu` → `AccessTokens` → `/api/access-tokens`는 본인 토큰의 생성·목록·재조회·삭제를 처리합니다. 내부 `server/access-tokens.mjs`는 SQLite 트랜잭션을, 외부 `worker/access-tokens.mjs`는 기존 `controlTransaction`을 사용하며 입력 검증·난수·해시·AES-GCM은 `storage/access-token-service.mjs`를 공유합니다. 신규 토큰에는 만료일이 없으며 원문은 암호화해 저장하고 눈 아이콘을 눌렀을 때 본인에게만 복호화해 반환합니다. 내부 키는 `access-token-key.mjs`에서 DB 밖의 파일 또는 환경 변수로 관리합니다. 브라우저 영속 저장소와 감사 로그에는 토큰을 넣지 않으며, 조회용 Bearer 인증은 아직 연결하지 않습니다. 미배포 신규 기능의 스키마 변경을 v33/site v3/control v2 마이그레이션 하나에 포함합니다. 배포·키 관리·백업 취급은 [운영 안내](OPERATIONS.md#접속-토큰-도입-업데이트)를 따릅니다.

`api.ts`는 내부·외부 JSON 응답의 `X-Server-Time`을 받아 monotonic clock에 고정합니다. 표 저장·명시적 덮어쓰기·상세 속성 저장은 `serverNow()`로 새 작업의 시각을 만들고, 재시도는 기존 ID와 시각을 유지합니다. 서버의 7일 재시도 유효기간과 미래 시각 검증은 유지합니다. `tests/browser/workspace-improvements.spec.ts`는 빠른/느린 PC 및 로그인 후 시각 변경, 숨긴 일정 목록, 검색 위치 보존, 마지막 문서 삭제, 꼬리 메모 편집·전체 화면·스크롤, 토큰 메뉴를 검사합니다. `tests/access-tokens.test.mjs`는 두 실제 DB의 소유권·해시·동시 발급 상한·migration 롤백·복구 폐기를 확인합니다.

### 속성과 상태 통계

작업·팀원·상태는 필수 속성입니다. 팀원과 지원자는 업무 담당 정보를 나타내며 단일·복수 선택 구성을 유지합니다. 연간 업무의 편집 권한은 담당자·지원자 값에 의존하지 않습니다. 설정의 `revision`은 관리자 간 충돌을 검사합니다. 속성 종류 변경은 기존 셀을 변환하고, 변환 불가능한 값이 있으면 전체 변경을 취소합니다.

상태 통계는 실제 상태 옵션을 기준으로 현재 달력의 최대 두 연도에 속하는 전체 업무를 중복 없이 집계합니다. 필터·숨김은 통계 분모를 바꾸지 않습니다. 보관된 속성과 값은 기존 셀·스냅샷을 해석할 수 있도록 보존합니다.

### 이관과 삭제

XLSX 분석·생성은 내부 SQLite와 외부 PostgreSQL에서 `shared/workbook.mjs`를 직접 사용하며, 빌드 중 서버 소스를 잘라 별도 파서를 생성하지 않습니다. XLSX는 미리보기 후 담당자·예외 확인을 거쳐 적용합니다. 파일·팀·행 범위 및 열 연결 설정·시트·모드·연도 조합으로 중복 적용을 방지합니다. 담당자가 비어 있으면 미지정으로 유지합니다. 여러 표가 섞인 원본에는 API의 `sheetOptions`로 업무 표의 범위를 지정할 수 있습니다. 사본은 생성 당시 값·사용자·설정·보기를 보존하고 이후 독립적으로 편집합니다.

사본 편집은 `src/useReportDraft.ts`의 자동 저장 큐·실행취소 기록을 사용합니다. `shared/report-editing.js`가 브라우저와 서버에서 같은 편집 작업을 적용하고, `server/report-editing.mjs`는 팀 기여 권한·사본의 속성·BLOB revision을 검증한 뒤 해당 사본만 저장합니다. 현재 업무의 mutation·SSE·실행취소·필터 저장 경로와 연결하지 않습니다. `tests/reports.test.mjs`는 원본 속성 변경·원본 업무 삭제·권한·원자성·동시 수정·재시작·응답 유실 재시도를, `tests/browser/report-editing.spec.ts`는 편집·추가·삭제·서식·실행취소·자동 저장·실패 재시도·기존 필터 복귀를 검증합니다.

업무 삭제는 복구 가능한 삭제 상태로 보존하며, 별도 휴지통 UI 없이 시트별 변경 이력에서 복구합니다. 원본 다중 삭제·복구는 전체 권한과 버전을 검사하고 하나의 트랜잭션으로 처리합니다. 사본 삭제 이력은 삭제 직전 행·문서 본문·참조된 사용자 이름을 보관하며, 복구는 해당 사본에만 적용합니다. 팀 삭제는 시스템 관리자가 확인한 경우 모든 연도의 업무와 연관 데이터를 트랜잭션으로 영구 삭제합니다. 다른 팀·공용 계정은 보존합니다.

## 확장과 변경

- 짧은 저장·드래그로 입력을 잠글 때는 `src/busyProps.ts`로 실제 `disabled`와 임시 잠금 표시를 함께 전달합니다. 권한·필수값 부족으로 비활성화한 컨트롤의 흐린 표시는 유지하고, 임시 잠금 때문에 화면 전체를 흐리게 만들지 않습니다. 저장 상태는 변경 중인 항목에 표시합니다. 캘린더 저장은 해당 팀원의 데이터만 교체하고, 변경 없는 주간 배치는 다시 정렬하지 않습니다.
- 포인터 드래그의 이동·종료·취소는 `src/trackPointerDrag.ts`를 공유합니다. 캘린더 이동·기간 조정, 기간 선택, 행 이동, 속성 값 순서 변경에 적용되어 있습니다. 새 드래그도 이 모듈을 사용하고 각 화면은 시작 임계값·대상 계산·스크롤·저장만 담당합니다. 캡처 해제는 취소가 아니며, 버튼이 풀린 이동 이벤트가 먼저 오면 마지막으로 누른 위치를 한 번만 확정합니다. 실제 `pointercancel`·창 포커스 이탈·Escape와 화면 해제는 취소하고, 일반 `pointerup`에서는 최종 좌표를 반영합니다. 브레이브 트랙패드의 캡처 해제 → 버튼 해제 이동 → 늦은 `pointerup` 순서는 `tests/browser/monthly-calendar.spec.ts`에서 재검증합니다.
- 일반 폼의 `input`·`select`·`textarea` 테두리와 포커스는 `src/styles.css`의 공통 규칙을 사용합니다. 화면별 CSS는 필요한 크기·배치만 조정하고, 입력칸 바깥으로 떨어지는 `outline`이나 별도 테두리·모서리 규칙을 중복 지정하지 않습니다. 공통 버튼도 같은 스타일 파일에서 포커스 선을 기존 테두리 안쪽에 겹쳐 그려 이중 테두리가 생기지 않게 합니다. 셀 편집기와 테두리 없는 도구 모음은 기존 전용 표시를 유지합니다.
- 일반 폼 선택은 `Select.tsx`, 같은 값을 재선택하여 적용해야 하는 서식 선택은 `FormatSelect.tsx`를 사용합니다.
- 입력 팝업의 초기 포커스는 `Modal.initialFocus`로 지정해 `showModal()` 뒤에 적용합니다. 생성은 폼 제출로 버튼과 Enter를 연결하고, 한글 조합 확정 Enter와 저장 중 중복 제출을 구분합니다.
- 일정 제목의 자동 저장은 입력 초안과 서버 제목을 분리합니다. 저장값의 앞뒤 공백은 정리하되 응답으로 편집 중인 초안을 덮어쓰지 않아 공백·커서·한글 조합을 보존합니다. 저장 여부와 초안 보관은 공백 정리 후 비교하여 공백만 바뀐 경우 중복 요청이나 불필요한 미저장 표시가 생기지 않도록 합니다.
- 캘린더 태그의 고정 팔레트는 `shared/calendar-tags.js`, 관리·선택 UI는 `src/CalendarTags.tsx`를 공유합니다. 이름·색상은 팀·소유자별 목록에 한 번 저장하고 일정에는 순서가 있는 ID만 연결합니다. 개인 일정·태그는 사용자 ID로, 팀 공용 일정·태그는 `userId: null`로 구분합니다. `Calendar`의 팀 월간·개인 월간·팀 주간은 같은 카드·편집·저장 경로를 사용하고 조회·태그·배치 캐시는 소유자별로 분리합니다. 태그 목록 변경은 다른 소유자의 태그 연결과 체크 상태를 정리하지 않습니다. 공용 일정과 공용 태그는 열람자를 포함한 모든 팀원이 관리할 수 있습니다. 개인 일정·태그는 기여 권한이 있는 본인과 해당 팀장·관리자만 편집합니다. 관리 버튼·팝업 제목은 소유자에 따라 개인 태그 관리·팀 태그 관리로 일치시킵니다. 목록 변경은 표시 캐시를 갱신하며 캘린더 전체를 재조회하지 않습니다. 제목·기간·문서·태그의 독립 저장 응답은 다른 필드를 덮어쓰지 않도록 병합합니다. `tests/calendar.test.mjs`와 `tests/browser/calendar-tags.spec.ts`에서 권한·충돌·삭제·복구·배경색과 동시 저장을 검증합니다.
- 캘린더 삭제·실행취소도 업무와 같은 복구 가능한 삭제를 사용합니다. `Toast.tsx`의 `UndoToast`를 공유하고, 상세에서 편집 중인 제목·기간·본문 저장을 마친 뒤 확인 팝업 없이 삭제합니다. 실행취소는 본문과 태그 연결을 유지한 동일 일정 ID를 복구하며 삭제/복구 요청 ID로 응답 유실 재시도를 보호합니다. 전체 목록을 재조회하지 않고 영향받은 소유자의 일정과 위치 정보만 병합합니다. 실행취소 알림은 8초 표시하되 저장·다른 팝업 사용 중에는 만료를 멈춥니다.
- 주간 할 일 기준은 연간 업무의 `PropertyFilter`를 그대로 사용합니다. 작업(`title`)·팀원(`owner`)을 제외한 활성 속성의 값 검색·복수 선택·미지정·일치/제외·필터 해제를 공유하고, 텍스트·날짜·숫자 값은 기존 업무 API와 `taskQuery`로 한 번 조회해 재사용합니다. `matchesPropertyFilter`를 화면 필터와 서버 가져오기에서 함께 사용하므로 숫자 0·빈 셀·복수 팀원도 같은 규칙으로 판정합니다. 기준 가져오기는 대상 사용자가 `owner`인 업무에만 적용하며 지원자·검토자로만 참여한 업무는 제외합니다. 작업·팀원 속성은 화면에서 선택을 비활성화하고 서버에서도 저장·가져오기를 거절합니다.
- 주간 할 일의 직접 선택과 이번 주 기준 가져오기는 `server/calendar.mjs`의 같은 연결 저장 함수를 사용합니다. `CalendarTaskPicker`는 공통 Modal·Button·검색 폼을 사용하고 원본 업무 ID만 선택합니다. 검색은 제목·연도 요약만 50개씩 조회하며 이전 검색을 취소하고 결과 키를 검사합니다. 응답 유실 후 재시도도 같은 주에 중복 연결을 만들지 않습니다. `Calendar`는 응답의 `weekly`를 대상 사용자·주에만 병합하고 원본 제목 수정도 기존 업무 상세 저장 경로를 재사용합니다. 과거·미래의 직접 선택, 서울 일요일 기준 가져오기 제한, 권한·중복·제목 연동은 API와 브라우저 테스트에서 검증합니다.
- 캘린더 문서는 기존 Markdown/revision 저장 형식을 유지한 채 `/calendar/entries/:id/document/events` SSE로 최신 저장본을 전달합니다. 구독·전송·주기 점검마다 세션과 팀 접근 권한을 재검사하고 재연결은 마지막 커서 이후 변경된 경우에만 최신 스냅샷을 받습니다. 같은 저장의 전송 본문은 한 번만 직렬화해 연결들에 공유하며, 각 연결의 현재 권한·revision은 별도로 검사합니다. `DocumentEditor`의 동기화는 모든 Markdown 문서에 기본 적용하며, `shared/document-merge.js`로 독립적인 문자 구간을 병합하고 같은 부분의 상충하는 교체는 기존 충돌 UI에서 입력을 보존합니다. 저장 중 추가 입력·한글 조합·이미지 업로드는 보류한 원격 문서와 합칩니다. 리치 편집기는 변경된 구간만 적용하고 원격 변경을 로컬 실행취소 이력에 추가하지 않습니다.
- 일정 생성은 저장 후 목록으로 돌아갑니다. 카드 우클릭은 공통 `GridHeaderMenu`를 쓰고, 복제는 새 UUID와 `/calendar/entries/:id/copy`로 기간·선택 태그·체크만 저장하고 제목에 번호를 붙입니다. 서버 트랜잭션에서 같은 소유자의 전체 날짜 이름을 확인하며 일반 생성과 같은 저장 함수를 사용합니다. 응답 유실 재시도에는 같은 UUID의 결과를 돌려줍니다. 본문은 복사하지 않습니다. 카드와 상세의 삭제는 `calendar-entry-actions.ts`를 공유하며 같은 실행취소로 복원합니다. 상세 제목은 공통 Modal의 `titleContent`에 배치하고 삭제는 하단에 둡니다. 제목이 비어 있으면 측정용 텍스트와 입력 placeholder에 같은 문구를 사용해 다시 클릭할 폭을 유지합니다. 모달 바깥에서 끝난 텍스트 선택은 닫기로 처리하지 않습니다. 태그 선택 목록은 클릭 처리 뒤 닫아 생성 버튼의 위치가 pointerdown과 pointerup 사이에 바뀌지 않게 합니다.
- 일정별 선택 태그 드래그·Alt+좌우 정렬은 기존 dnd-kit 구현 패턴과 태그 저장 API를 사용합니다. 순서는 기존 `calendar_entry_tags.position`에 저장하며 태그 정의 목록의 정렬·DB 버전은 변경하지 않습니다. 태그 체크·제거와 드래그 이벤트는 분리합니다.
- 체크 태그의 체크 상태는 일정별 연결에 저장합니다. 카드·상세는 `CalendarCheckTag`와 `calendar-tag-checks.ts`의 저장·병합 함수를 공유합니다. 체크박스는 카드 버튼 바깥에 배치하고 포인터·키보드 이벤트를 분리하여 드래그·상세 열기를 방지합니다. 체크 저장은 해당 필드만 갱신하며, 다른 저장 응답의 오래된 체크 상태로 덮어쓰지 않습니다.

여러 탭의 실시간 구독은 `StreamBroker`를 SharedWorker에서 실행합니다. 채널 집합·필요 커서가 같으면 살아 있는 POST 연결을 유지하고, 추가·제거 시 재연결하더라도 기존 문서·리소스의 커서를 보내 변경 없는 초기 프레임을 생략합니다. 내부 Node의 `createDocumentEvents`는 무구독 중 변경도 추적하며 본문 없이 revision·전송 순서만 최대 10,000개 키까지 보존합니다. 메타데이터 퇴출이나 서버 세대 변경은 최신 스냅샷으로 복구합니다. 각 리스너는 자기 커서 이하의 재전송을 받지 않아 새 스냅샷을 과거 셀로 되돌리지 않습니다. 종료 사유 없는 `closed`와 `rejected` 5xx는 커서를 유지한 일시 종료로 처리하고, 백오프 동안 같은 연결의 정상 채널과 같은 청크의 후속 프레임은 계속 처리합니다. 사유 없는 부분 종료 대기 중 구독 추가·제거는 연결 재시도 시각에 반영합니다. `rejected` 5xx는 해당 채널에만 1.5~30초 백오프를 두며 기한 전 POST에서 제외합니다. 정상 채널·새 구독은 10ms 묶음 처리 후 연결하고, 별도 채널 타이머가 기한에 재연결을 예약합니다. 채널이 15초 이상 유지되면 해당 채널의 지연을 초기화합니다. EOF·네트워크·heartbeat 부재와 단독 `closed`는 기존 연결 단위 백오프를 쓰며 채널 지연과 독립적입니다. 마지막 구독 제거는 즉시 정리하고, 과거 커서로 새 리스너가 합류하면 재전송을 건너뛰지 않도록 먼저 연결을 끊습니다. `access-revoked`는 `{status}`를 전달하며 401은 세션 손실, 403·404는 권한 상실·삭제입니다. 상태 코드가 없는 기존 프레임은 403으로 해석합니다. 401 이외의 `access-revoked` 또는 비재시도 `rejected`가 선행된 종료만 해당 구독의 영구 종료입니다. 모든 리스너가 떠나면 그 키를 제거해 다음 구독은 새 채널을 만듭니다. HTTP 400의 `rejectedIds`만 종료하고 정상 채널은 실패 백오프를 늘리지 않고 다시 연결합니다. 요청 수준 HTTP 401은 전체 연결을, 연결 중 `access-revoked {status:401}`은 해당 채널을 세션 종료로 분류합니다. 문서·리소스 화면은 세션 종료에서 스트림을 닫지 않으며 문서 편집을 권한·삭제 오류로 막지 않습니다. `components.tsx`의 초기 로그인과 재인증 성공은 `resumeSession()`을 호출합니다. 워커의 `resume` 또는 페이지 내 fallback 브로커의 `resume()`이 스트림 키 변화 없이 모든 탭의 세션 종료 채널을 새 ID·보존 커서로 재승인합니다. 구독 없는 로그인 화면도 워커에 신호를 보내고 확인 응답 후 임시 포트를 닫습니다. 세션 종료 채널이 없으면 재연결하지 않습니다. 셀 복구 등 새 스트림 추가·재합류에 의한 기존 재승인도 유지합니다. 반복 전송 실패는 1.5~30초 백오프하고, 셀 스냅샷 복구와 셀의 `rejected` 5xx도 SSE `ready`를 받기 전까지 1~30초 백오프를 유지합니다. 문서·리소스 구독의 비재시도 거부는 기존 접근 거부 처리로 정리하고, 5xx 복구는 브로커가 맡습니다. 워커 대기열 4MiB 초과·리스 만료는 페이지에 즉시 재구독을 요청합니다. 미지원 환경도 같은 브로커를 페이지 안에서 사용합니다. 탭은 `EventStream` 인터페이스를 유지하므로 셀·문서·목록의 기존 동기화 호출부를 재사용합니다. 배포 시 서버와 빌드 결과를 함께 갱신하고 기존 탭을 새로고침합니다. 서로 다른 빌드의 워커 URL은 별개이므로 이전 탭은 새 워커에 자동 합류하지 않습니다.

외부 문서의 GET·PUT·충돌 응답·SSE에는 같은 PG 문서 revision 기준의 `sync`를 사용합니다. SSE 전송 커서 `pg:<site_events cursor>`와 문서 `sync.sequence`는 서로 다른 순서이므로 비교하거나 덮어쓰지 않습니다. `worker/events.mjs`는 `payload.sync`를 보존합니다. 열린 연간 메모·업무 문서에서 변경을 누락하지 않도록 실제 Edge handler → PG 조회·저장·SSE 경로와 리치/Markdown 편집 화면을 함께 확인합니다. ## 검증

```sh
npm test
npm run build
npx playwright install chromium firefox webkit
npm run test:e2e
```

`npm test`는 임시 DB에서 API·권한·동시 수정·이관·백업/복구·이슈 링크를 검증합니다. `DEBUG_HTTP=1`로 실행하면 서버가 거절한 요청(4xx)의 경로와 사유를 콘솔에 남겨 테스트 실패 원인을 바로 볼 수 있습니다. `npm run test:e2e`는 별도 임시 서버와 DB를 만들고 Chromium·Firefox·WebKit에서 실제 UI를 조작합니다. `4311` 포트를 사용하며 실행 중에는 앱·테스트 소스를 바꾸지 않습니다. Linux 환경에서 브라우저 시스템 의존성이 없다면 `npx playwright install --with-deps chromium firefox webkit`를 사용합니다.

실패한 브라우저 검사는 `test-results/`에 스크린샷·트레이스를 남기고 HTML 보고서는 `playwright-report/`에 생성됩니다. 이 파일들은 Git에서 제외합니다. 테스트 데이터는 코드에서 생성한 가상 업무·계정이며 운영 DB를 사용하지 않습니다.

필요한 경우 다음 보조 명령을 실행합니다.

```sh
npm run performance
npm run performance:stress
npm run licenses
```

성능 명령은 임시 DB에 큰 데이터 집합을 생성하여 조회·저장·렌더링을 측정하고 `docs/validation/`에 로컬 결과를 저장합니다. `npm run performance:ui`는 빌드 후 Chromium에서 화면 처리 시간을 측정해 콘솔에 출력합니다. 문서의 날짜가 붙은 수치는 해당 시점의 로컬 측정 기록이며 현재 릴리스의 검증 결과나 운영 환경의 용량·지연시간 보장이 아닙니다. `docs/validation/`은 Git 제외 경로이므로 새로 clone한 저장소에는 과거 결과 파일이 없을 수 있습니다. 라이선스 명령은 잠금 파일과 설치 패키지에서 [고지 목록](THIRD_PARTY_NOTICES.json)과 [원문](THIRD_PARTY_NOTICES.txt)을 갱신합니다.

2026-10-21 캘린더 개선은 Apple M4 Pro·Node.js 22.23.1·Chromium 156의 같은 로컬 환경에서 기준 커밋 `f7130a5`와 비교했습니다. 합성 일정 1,000개의 화면 표시 중앙값은 179→181ms, 월간 조회 P95는 17.8→17.7ms였습니다. 256KiB 문서를 저장해 30개 HTTP SSE 연결 모두에 전달하는 P95는 전송 직렬화 공유 전 82.1ms에서 적용 후 42.5ms로 감소했습니다. 1만 행·30명 동시 조회 P95는 기준 968~1,000ms, 변경 후 1,045~1,063ms였으며, 저장 P95는 38~41→31~33ms였습니다(각 2회 실행). 실제 사내망이나 30개 브라우저 동시 실행을 측정한 결과는 아닙니다. 로컬 상세 결과는 `docs/validation/calendar-performance-20261021.json`에 있습니다.

2026-10-22 최종 로컬 검증에서는 1만 행·30개 HTTP 세션 동시 조회 P95 1,059ms, 저장 P95 33ms, 편집 화면 843ms, 검색 177ms를 측정했습니다. 같은 장비에서 합성 일정 1,000개의 화면 표시 중앙값은 187ms(기준 179ms), 64KiB 리치 문서 열기는 325ms(기준 368ms)였습니다. 256KiB 문서를 30개 SSE 연결 모두에 전달하는 P95는 48.2ms, 1,000개 일정·20개 태그를 가진 원본의 번호 붙인 복제 P95는 4.3ms였습니다. 독립 수정 병합과 커서 위치 계산의 256KiB P95는 34ms였습니다. API·도메인 검사 231건, Chromium·Firefox·WebKit의 문서/시트 동기화·사본 편집·복제 재시도 및 로딩 관련 최종 회귀 검사가 통과했습니다. 상세 수치는 로컬 `docs/validation/all-document-sync-performance-20261022.json`에 있으며, 합성 데이터·로컬망 측정이므로 운영 동시 사용자 지연을 보장하지 않습니다.

같은 날 로그인 유지·꼬리 메모 후속 개선 후 API·도메인 검사 232건과 세 브라우저의 관련 회귀 검사 54건이 통과했습니다. 브라우저 프로세스 종료 후 같은 프로필의 자동 로그인, 직접 로그아웃·비밀번호 변경, 메모의 독립 폭·취소·로컬 복원·항목별 메뉴, 원본/사본 메모와 문서 동기화, 표 스크롤·배율·고정 열·키보드 편집을 포함합니다. 폭 조절은 본문 API 쓰기를 만들지 않는 것도 확인했습니다. 마지막 1만 행·30개 HTTP 세션 측정은 조회 P95 1,032ms, 저장 P95 42ms, 편집 화면 803ms, 검색 163ms였습니다. 위와 동일한 로컬 합성 데이터 측정 조건이며 운영망의 보장 수치는 아닙니다.

`performance:stress`는 1천·1만·2만 업무를 별도 서버 프로세스에서 검증합니다. 53주 일정 열의 점유율은 각각 30%·30%·100%이며, 마지막 시나리오는 128만 셀입니다. 100개 가상 계정 중 30개 세션의 동시 조회·저장, 변경 없는 조회, 2천 셀 서식 변경, 동일 셀 충돌, Chromium의 검색·묶음·스크롤·편집 후 재조회를 확인합니다. 클라이언트의 동시 응답은 스트리밍으로 소비하여 테스트 도구가 대용량 JSON을 중복 보관하지 않게 합니다. 실제 사용자 데이터는 사용하지 않습니다.

특정 규모만 실행하려면 `npm run performance:stress -- 10000:30`처럼 `업무수:일정점유율`을 전달합니다. 결과는 `docs/validation/load-test-results.json`, 화면은 같은 폴더에 저장합니다. Node.js 22.13.0 이상과 설치된 Chromium이 필요하며, 2만 업무 시나리오는 수 GB의 메모리를 사용하므로 운영 서버와 분리해 실행합니다. 30개 HTTP 세션과 한 브라우저의 검증이며, 30개 브라우저 동시 사용이나 사내 네트워크의 지연시간을 측정하는 검사는 아닙니다.

검증 한계: 클립보드 자동 검사는 합성 이벤트와 브라우저 API 대역을 포함하므로 외부 Excel·OS 클립보드의 모든 조합을 보장하지 않습니다. 운영 서버의 HTTPS·프록시·재시작 설정, 백업 복구 시간과 실제 사용 데이터 규모에서의 동작은 배포 환경에서 별도로 점검합니다. 내부 인증은 로컬 계정·세션 방식이며 외부는 전용 Cloudflare Access JWT와 앱 사용자·팀 권한을 검증합니다. 실제 Cloudflare Access/Images/Supabase 계정 배포와 모바일 전용 UX는 로컬 검증과 구분합니다. 릴리스마다 실행한 검사와 결과를 기록하고 과거 통과 건수를 현재 결과로 재사용하지 않습니다.

## 저장소 범위

소스, 잠금 파일, 테스트 코드, 실행 안내와 데이터 명세를 관리합니다. DB·백업·반출 파일·실제 환경 설정·로그·스크린샷·원본 시트가 참조된 초기 RFP는 Git에 포함하지 않습니다. `.env.example`에는 비밀값 없이 설정 항목만 제공합니다.

## 외부 동기화 개발·검증

[설치 안내](CLOUD_SETUP.md)와 [프로토콜](SYNC_PROTOCOL.md)을 기준으로 `server/sync/`, `server/storage/`, `worker/`, `edge/`의 호출 경로를 함께 확인합니다. 내부 `transaction`은 동기 콜백만 허용하고, PG는 하나의 client에서 모든 await·COMMIT·rollback을 끝냅니다. Node의 timer는 readonly SQLite worker에서 Git·병합·해시·재투영을 수행하고 메인 쓰기 경계에서 현재 head·로컬 변경·L·작업 guard를 다시 검사합니다. 사이트 이벤트는 commit 뒤 기존 SSE 경로로 전달합니다.

```sh
npm test
npm run build
npm run build:edge
npm run build:pages
npm run test:e2e -- tests/browser/data-sync.spec.ts
npm run performance:sync
```

PG 테스트는 임시 서버를 직접 실행합니다. 일반 `npm test`에서는 사용할 PG 서버 바이너리가 없으면 관련 검사를 `skip`하고 성공 종료할 수 있으므로, 종료 코드만으로 PG 검증을 주장하지 않습니다. 릴리스 검증은 `TEST_PG_BIN=/absolute/PostgreSQL/bin npm run test:postgres`를 사용합니다. macOS 개발 PC는 `brew install postgresql@17`로 서버 바이너리를 준비합니다. `libpq`가 이미 설치되어 `brew link`가 헤더 충돌로 실패하면 `initdb`가 찾는 공유 파일이 연결되지 않으므로, `/opt/homebrew/share/postgresql@17`과 `/opt/homebrew/lib/postgresql@17`을 Cellar의 `share/postgresql`·`lib/postgresql`로 링크한 뒤 `TEST_PG_BIN=/opt/homebrew/Cellar/postgresql@17/<버전>/bin`을 지정합니다. `libpq`의 `initdb`는 `postgres` 실행 파일이 없어 사용할 수 없습니다. 이 명령은 `postgres`, `initdb`, `pg_ctl`을 먼저 실행 확인하고 하나라도 없거나 실행할 수 없으면 테스트를 시작하기 전에 실패합니다. 준비가 확인되면 같은 경로를 모든 테스트에 전달해 전체 단위·통합 검사를 실행하며, 최종 pass/fail/skip 수도 기록합니다. 공통 외부 API 테스트는 임시 control/team PG와 실제 JWT 검증, 대역 R2/Images/GitHub HTTP를 사용합니다. Git CLI 경합·복구 테스트는 임시 bare 저장소를 사용합니다. 실제 cloud 변환 품질·도메인/Access policy·rate limit·운영 DB는 별도 검증 대상입니다.

**저장 형식은 내부·외부와 동기화 경로에서 같게 유지합니다.** 동기화 로직을 제외한 저장 방식·코드 흐름이 사이트마다 달라지면 한쪽에서만 실패하는 경우가 생깁니다. 사본 `data`는 사내 BLOB·HTTP 응답·동기화 명령·외부 `site_entities`에서 모두 `$styles`/`$formats` 공유 사전 형태입니다([사본 저장 형태](DATA_FORMAT.md#보기사본계정)). 직렬화는 `shared/report-sync-data.js`의 `packReportData`(키 정렬 후 pack)로, 해제는 `unpackReportData`로만 합니다. 사본 payload를 비교하는 새 코드는 `equal` 대신 `payloadEqual`을 사용해 기존 평문 payload와 공유 사전 payload를 내용으로 비교합니다. 사내 진입점은 `server/sync/entities.mjs`의 `readEntity`(직렬화)·`materializeEntity`(해제), 외부 진입점은 `worker/data.mjs`의 `DataSession`(읽을 때 해제, 저장·명령 생성 때 직렬화)입니다. 검증(`validateEntityPayload`)·v2 분할(`splitReportRecord`)·조합(`applicationEntities`)·reducer 비교도 두 형태를 받아들입니다. 성능 픽스처에 팀 공통 서식이 없으면 이런 중복이 측정에 드러나지 않으므로, 사본·동기화 크기를 검증할 때는 `tests/sync-report-format.test.mjs`처럼 운영 규모의 행·열 규칙을 넣습니다.

공유 상태 전체에는 기본 상한이 없고 `SYNC_MAX_STATE_BYTES`·`SYNC_MAX_ENTITIES`를 지정한 경우에만 검사합니다(`shared/sync-capacity.mjs`의 `capacityLimits`). snapshot은 64MiB, 이벤트 파일은 32MiB(사본 복사처럼 나눌 수 없는 명령 하나가 들어가도록 정한 값), receipt는 별도 16MiB로 검사합니다. `tests/sync-state-capacity.test.mjs`는 28.76MiB·33,021개 합성 자료의 SQLite 최초 게시, 외부 `serviceFor`의 PG 가져오기, 기존 4MiB 환경값에서의 원자적 거절, HTTP 후속 저장·역방향 수신을 검증합니다. 상태·파일 예산을 결합해 이벤트 제한까지 풀리는 회귀, 미전송 변경의 임의 삭제, DB 계수와 메모리 계수의 불일치를 확인합니다. Node 테스트의 성공은 Supabase/Deno 자원 한도 내 실행 보장이 아닙니다. 형식과 스키마를 유지한 한도 상향에는 DB 버전 증가를 하지 않으며 양쪽 런타임 배포와 기존 낮은 환경값 확인이 필요합니다.

2026-10-29 한도 상향·동기화 오류 표시 검증은 Node.js 22.23.1과 실제 임시 PostgreSQL 18.6에서 567건을 통과했고 실패·skip은 없었습니다. Chromium·Firefox·WebKit의 동기화 화면 검사 39건에서 버튼 아래 붉은 오류, 작은 화면 내 표시, 재진입 시 오류 보존, 성공 재시도 후 해제, 실행 성공 후 상태 조회 실패의 구분을 확인했습니다. Firefox는 이 개발 PC의 시스템 프록시가 loopback을 우회한 실패를 확인한 뒤 테스트 실행에만 `network.proxy.type=0`을 적용했습니다. 앱의 네트워크 설정은 변경하지 않았습니다. `tests/sync-error-message.test.mjs`는 내부·외부 HTTP 경계의 알려진 원인 안내와 알 수 없는 오류의 상세 정보 비공개를 검사합니다. 프런트엔드·Edge·Pages 빌드도 통과했으며 실제 사내망·Supabase 배포에서의 전송 완료는 별도 점검 대상입니다.

`performance:stress -- 10000:30`은 이전 릴리스 비교용 기존 시나리오이고 `performance:sync`는 같은 팀/자료에서 미연결·연결·외부 장애·초기 게시·백업 중 저장 및 commit→30개 SSE 도착을 비교합니다. 결과는 Git 제외 `docs/validation/`에 저장합니다. 측정 당시의 실제 결과와 목표 미달은 릴리스 보고서에 기록하며 통과 수치를 고정 보장으로 설명하지 않습니다.

안정 상태 paired 비교는 `schedule:false`로 주기 발신을 끄고 저장·캡처 비용을 측정합니다. 실제 게시·수신과 겹치는 비용은 별도 작업 행으로 보고합니다. 초기 Git 장애 검사는 bare 저장소 경로를 바꾼 즉시 실패이며 지연·무응답 원격 검증을 대신하지 않습니다. 별도 자식 프로세스의 PG/S3 장애 probe는 내부 서버에 연결되지 않으므로 그동안의 저장 표본을 외부 장애 격리 성능으로 주장하지 않습니다. 두 팀의 동시 동기화와 동기화 작업 중 대량 붙여넣기도 별도 근거가 필요합니다.

## 업무 저장소 계약

Node와 Edge의 일반 업무 API는 `server/storage/`의 도메인 서비스에 repository를 주입합니다. SQLite 구현은 기존 관계형 테이블, prepared statement, task cache와 동기 `transaction()`을 유지합니다. PostgreSQL 구현은 `site_entities`/`site_operations`/`site_audit`/`site_events`를 같은 PG 트랜잭션에서 변경하며 C+P 기준으로 outbox를 작성합니다. API와 공통 명령은 SQL dialect나 `s.tx.query`에 의존하지 않습니다. `DatabaseAdapter`는 이 업무 계약 아래의 sync 상태·트랜잭션 포트입니다.

| 계약                                                     | 실제 명령 범위                                                                                                  |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| TaskBusinessService                                      | 조회/ETag, 셀 배치·서식·재시도, 생성/복제/수정/삭제/복원/순서, 개인 보기                                        |
| DocumentBusinessService                                  | 원본/사본 문서, 연간/사본 메모, 일정 Markdown, 제목/순서/본문 CAS, 이미지 접근 권한과 선택된 저장소의 읽기/쓰기 |
| ReportBusinessService                                    | 사본 생성·복사·이름·행/셀/서식 편집·삭제·revision                                                               |
| CalendarBusinessService                                  | 일정·태그·배치·주간 업무·자동 가져오기·개인 규칙                                                                |
| SettingsBusinessService / FilterBusinessService          | 팀 설정·이름/테마, 셀 종류 변환, 보기/필터 정규화, 공유/개인 필터·선택 상태                                     |

| DocumentBrowserBusinessService / TransferBusinessService | 문서 탐색, CSV/XLSX/JSON 내보내기, 실제 업로드 미리보기·적용·재시도                                             |

`createApp()`은 내부 SQLite 저장소만 구성합니다. Node에서 PG repository를 선택하는 테스트 전용 모드와 factory 주입은 제거했습니다. 외부 API는 `worker/`의 route 함수와 `worker/storage/` PostgreSQL 구현을 사용하며, 인증·멤버십도 외부 PG control/site 저장소에서 확인합니다. 공통 도메인 서비스는 양쪽 명령 검증을 공유하지만 Node 라우트의 SQLite 트랜잭션은 동기를 유지합니다. 문서 이미지 준비와 XLSX 생성·읽기는 필요한 비동기 처리를 명시적으로 기다립니다.

외부 Edge는 `RequestContext.data`와 `capacityLimits(env)`를 통해 쓰기 전 DB 용량 검사와 commit 전 상태 검사를 수행합니다. 내부 SQLite 업무 경로의 행 수 시험이나 PG 어댑터 직접 호출 시험은 외부 API의 지원 규모를 보장하지 않습니다. [용량 범위](CLOUD_SETUP.md#15-실행-한도와-검증-범위)를 함께 확인합니다.

이미지 변환은 내부 Node의 sharp·`FileImageStore`, 외부 Edge의 Cloudflare Images·`R2ImageStore`를 사용합니다. PG 이미지 업로드는 작업 lease를 기록해 정리·연결 교체와 겹치지 않게 합니다. Git 실행기 설정과 인증은 논리 팀 자료 이관과 별도로 관리합니다.

내부 `setup-config.mjs`는 기존 dotenv 형식의 지정 변수만 원자 교체하고 파일 revision·기존 연결·중복 저장소·환경 우선순위·키 누락을 검사합니다. 프로필은 시작 시 검사와 같은 `server/sync/profiles.mjs` 규칙으로 파일·실행 목록을 검증한 뒤 `sync.apply`로 실행 중 목록에 바로 적용하며, 설치 식별자가 없는 최초 설치만 재시작으로 적용합니다. 환경 변수 우선순위는 프로세스 시작 시 읽은 값과 비교하므로 같은 서버의 이전 저장이 재정의로 오인되지 않습니다. 토큰 UI 저장은 작업이 없는 팀의 실행기 캐시만 무효화합니다. 설정 조회의 `tokenEnvironment`는 프로필의 환경 변수 토큰 유무를, `tokenPreview`는 `server/sync/credentials.mjs`의 `tokenPreview`로 계산한 토큰 앞부분(GitHub 공통 접두어 뒤 10자, 길이의 절반 이하)만 알립니다. 저장 형식 변경 없이 조회 때 기존 암호문을 풀어 계산하며, 현재 키로 풀 수 없으면 빈 값입니다. `DELETE /api/admin/teams/:id/sync-credential`은 토큰 저장과 같은 권한·작업 중 검사 뒤 암호문 행만 지우고 실행기 캐시를 비웁니다. 마법사는 저장된 토큰이 있으면 입력란 대신 앞부분과 삭제 버튼을 표시합니다. 내부 연결 검사는 GitHub 저장소에 쓸 토큰이 하나도 없으면 GitHub 호출 전에 409로 토큰 미등록을 안내합니다. 새 스키마·백업 형식은 없습니다. `tests/sync-setup.test.mjs`는 실제 임시 SQLite/API/환경 파일과 암호문·기존 연결 보존을 검사하고, `--env-file` 재시작과 같은 환경 변수 적재 후 연속 저장·연결 전 수정·즉시 적용된 프로필의 토큰 저장과 연결, 시작 시 거절될 프로필 목록과 쓸 수 없는 파일의 409 응답을 포함합니다. `tests/browser/sync-setup.spec.ts`는 실제 내부 설정 저장과 즉시 적용, 최초 설치의 재시작 안내와 재시작 후 적용, 안내를 연 동안 상태 polling이 중복되지 않는지, 외부 팀장 진입점 비표시, 입력 검증·팀 전환·작은 화면을 확인하며 외부 응답/영수증 경계는 route fixture로 검사합니다. 실제 외부 통합은 기존 `team-site`·`worker-sync-integration` 검사와 구분합니다.

Pages 접속은 `functions/[[path]].js` → `GRAEBOARD_BACKEND` → gateway Worker → Supabase Edge의 경로입니다. `worker/forwarder.mjs`는 이전 Worker 이름으로 들어오는 Service binding을 같은 gateway에 전달합니다. Hyperdrive binding과 이전 Cron, 전체 Worker 호환성 빌드 설정은 제거합니다. `public/_routes.json`으로 모든 경로를 Functions에 전달합니다. `tests/pages-gateway.test.mjs`는 누락된 binding의 JSON 503, 헤더·업로드·쿠키·스트리밍 보존을 검사하고, `tests/edge-gateway.test.mjs`는 실제 gateway의 workerd 실행으로 전달·정적 파일·인증 경계를 검증합니다. 팀 사이트 통합 검사는 이 Pages 진입점을 거쳐 SQLite/Git/PostgreSQL 간 구성원·승인·탈퇴 흐름을 확인합니다.

신규 외부 설치는 `PG_SITE` + `SITE_TEAM_ID`와 프로필 하나로 구성합니다. 사내 모든 팀은 SQLite v32에 남고 연결된 팀의 구성원만 `server/sync/directory.mjs`를 통해 별도 Git 브랜치에 게시합니다. `worker/directory.mjs`가 단방향 반영하고 `worker/site-auth.mjs`가 최초 팀장 연결·계정 선택·팀장 승인·접속 세션을 처리합니다. 기존 분리형 `PG_CONTROL` 경로는 호환용으로 유지합니다.

팀장 키: `TeamSetupKey` → 내부 `/teams/:id/setup-key` → `external_setup_keys` → 기존 동기화 실행 뒤 Git 키 브랜치 → `worker/setup-keys.mjs` → site v2 → `/auth/setup` 순서입니다. 원문은 React 메모리/발급 응답에만 두고 저장하거나 로그로 남기지 않습니다. `tests/team-site.test.mjs`는 내부 실제 API 발급, Git 전송, 다른 팀/일반 구성원 거부, 만료·재발급, 동시 소비, 연결 해제 뒤 재사용 거부, 반영/사용 영수증과 백업을 확인합니다. `tests/sync-migrations.test.mjs`는 v29/v30/v31 보존·원자적 v32 업그레이드를 검사합니다. 실제 운영 DB에는 테스트를 실행하지 않습니다.

외부 팀의 `Team.status`가 `unconnected`, `importing`, `maintenance`이면 업무 조회 대신 준비 상태 안내를 표시하고, 같은 팀이 active로 바뀌면 필터·보기·업무 조회를 다시 시작합니다. 내부 팀은 이 외부 상태로 화면을 차단하지 않습니다. 최초 조회 실패는 무기한 로딩으로 남기지 않습니다. `tests/browser/external-loading.spec.ts`와 기존 auth/data-sync 브라우저 검사를 함께 실행합니다.

배포 역할은 `shared/site-mode.js`에서 `GRAEBOARD_SITE`와 서버 호스트를 대조합니다. Node는 DB를 열기 전에 internal을, 외부 API는 요청·Cron 전에 external을 검사합니다. 화면은 bootstrap/setup의 명시적 `site`를 우선하며 기존 배포와 호환할 때만 `authMode`를 사용합니다. 초기 게시 API는 외부에서 403으로 거절하며 가져오기로 대체 실행하지 않습니다. `tests/site-mode.test.mjs`, `tests/team-site.test.mjs`, `tests/browser/data-sync.spec.ts`는 설정 오류·요청 값 변조·외부 게시 차단과 환경별 버튼을 확인합니다.

`TeamSyncIndicator`는 bootstrap/setup에서 계산한 공통 `site` 객체를 Context로 받아 상단 표시를 구분합니다. 내부는 정상·미전송·상대 확인 대기를 숨기되 오류·충돌·복구·중단·조회 실패를 표시하며, 최초 조회 실패도 숨기지 않습니다. 외부는 클라우드 저장·Git 반영·내부망 반영을 세 태그로 분리하고 대기/진행 중은 회색, 완료는 푸른색으로 표시합니다. 저장 중·실패에는 후속 단계도 완료로 표시하지 않습니다. 상태 조회는 기본 15초이며 내부 미연결 팀은 60초 간격으로 줄입니다. 포커스 갱신은 유지하고, 저장 후 상태 조회는 외부에서만 마지막 알림 이후 2초 뒤에 실행합니다. 내부 저장 및 인증·관리 API의 성공은 이 추가 조회를 만들지 않습니다. 팀 전환 시 이전 조회 실패 상태를 초기화합니다. `tests/browser/team-sync-indicator.spec.ts`는 같은 URL에서 서버 환경 값에 따른 표시, 오류 복구, 최초 조회 실패, 적용 확인 조건, 색상과 좁은 화면 배치를 검증합니다.

내부 재연결은 `TeamSyncSettings` → `POST /api/teams/:id/sync/reconnect` → `createNodeSync.reconnect` → readonly background snapshot의 경로입니다. 같은 설치의 disconnected 상태만 허용하고 팀장 권한을 계산 전후에 확인합니다. C+P와 실제 업무 자료의 차이를 기존 operation 형식으로 P에 추가한 뒤 같은 트랜잭션에서 active(초기 게시 전은 paused)로 전환합니다. 기존 C·P ID·writer epoch·L은 유지합니다. capture가 꺼진 동안의 문서 변경도 감지하도록 메인 연결의 total_changes와 data_version, 기존 snapshot guard를 커밋 직전에 검사하며 동시 저장 시 재계산합니다. 새 DB 스키마나 백업 형식은 도입하지 않습니다. `sync-integration`·`sync-lifecycle-review`·`browser/data-sync` 검사는 실제 API/Git에서 재연결·본문 보존·충돌·동시 저장·권한 철회·롤백을 확인합니다.

### 리뷰 반영 검증 기준

내부 오류 응답의 원문은 그대로 표시하며 외부 연결 오류의 진단 문구와 구분합니다. 내부 업무 polling은 7초, 외부는 30초이고 실패 재시도는 공통 정책과 Retry-After를 따릅니다. 내부 미연결 팀의 동기화 상태 조회는 60초 간격이며 업무 저장마다 조회하지 않습니다. 외부 저장 알림은 마지막 알림 이후 2초 뒤 한 번의 조회로 합칩니다. 공유 refresh는 마지막 소비자가 취소한 경우에만 네트워크를 취소합니다.

v1/v2의 기준 이력 재생, 일시정지한 양쪽의 명시 전환 수신, reportTask/reportCell 독립성, receipt 별도 용량, SQLite v32·PostgreSQL team v2 migration 및 정리 경계는 합성 DB에서 검증합니다. PostgreSQL strict는 `TEST_PG_BIN=/테스트/PG/bin npm run test:postgres`로 실행합니다. 실제 운영 v29 백업 사본의 `restore --dry-run`과 실제 사본 migration·행/이미지 보존은 [패치 체크리스트](PATCH_GUIDE.md)에 별도로 기록합니다. 개발 합성 DB 통과를 운영 사본 확인으로 대신하지 않습니다.
