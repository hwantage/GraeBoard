# 그래보드 개발 안내

[처음으로](../README.md) · [사용 안내](USER_GUIDE.md) · [운영 안내](OPERATIONS.md) · [데이터 형식](DATA_FORMAT.md) · [프로젝트 작업 규칙](../AGENTS.md)

그래보드는 실제 운영 중입니다. 개발·테스트 환경은 운영 DB와 문서 이미지 경로를 분리하고, 기능 변경 시 기존 운영 데이터와 저장 형식의 호환성을 확인합니다. 이 문서는 현재 저장소의 구현을 설명하며 실제 서버에 배포된 커밋·Node.js·DB 버전은 배포 전에 별도로 확인합니다.

## 작업 원칙

- 코드 탐색은 `codebase-memory-mcp`를 우선 사용하며, 미인덱싱 저장소는 `index_repository`부터 실행합니다. `search_graph` → `trace_path` → `get_code_snippet` 순서로 심벌·실제 호출 관계·구현을 확인하고, 복잡한 관계는 `query_graph`, 전체 구조는 `get_architecture`로 살펴봅니다.
- 문자열·오류 메시지·설정값·비코드 파일은 `search_code` 또는 `rg`로 찾습니다. 그래프 도구를 사용할 수 없거나 결과가 부족할 때도 `rg`와 파일 읽기로 보완합니다.
- 기능 변경 전에 유사한 기존 기능의 호출 경로와 공통 컴포넌트·스타일·저장 로직·이벤트 처리를 확인합니다. 기존 명명·구조를 따르고 구현을 재사용하거나 확장·공통화합니다.
- 같은 사용자 동작은 버튼·폼·포커스·문구·알림·삭제·실행취소·저장 흐름까지 일관되게 제공합니다. 요청이나 실제 요구사항에 근거하지 않은 안내 메시지·아이콘·확인 단계를 추가하지 않습니다.
- 완료 전에 기준으로 삼은 기존 기능과 비교하여 불필요하게 달라진 부분이 없는지 확인합니다.

## 개발 실행

Node.js **22.13.0 이상**이 필요합니다(`package.json`의 `engines.node`). Node.js 16에서는 현재 실행 옵션과 내장 SQLite를 사용할 수 없습니다. 다른 서비스의 Node.js와 충돌하는 경우 프로젝트 실행 셸·서비스에 별도의 지원 버전 경로를 지정합니다.

```sh
npm ci --include=dev
npm run dev
```

Vite는 `5173`, API는 `4310` 포트를 사용합니다. 개발 프록시는 `/api`를 로컬 API로 전달합니다. 기본 포트를 변경할 때는 `vite.config.ts`도 함께 확인합니다. `.env`의 적용 방식은 [운영 안내](OPERATIONS.md#환경-설정)를 따릅니다.

개발용 `.env`를 만들 때는 `.env.example`을 참고하고 `DB_PATH`와 `DOCUMENT_IMAGES_DIR`가 개발 전용 경로인지 확인합니다. 이미 있는 `.env`는 덮어쓰지 않습니다. 예시 계정과 업무는 비어 있는 개발 DB의 최초 설정에서 선택하여 생성할 수 있습니다. 실제 운영 파일을 테스트 픽스처로 사용하지 않습니다.

| 명령            | 실행 내용                                                                     |
| --------------- | ----------------------------------------------------------------------------- |
| `npm run dev`   | API의 파일 변경 감시와 Vite 개발 서버를 함께 실행                             |
| `npm run build` | TypeScript 검사와 프런트엔드 배포 빌드. 결과는 `dist/`                        |
| `npm run start` | Node API 서버 실행. API와 준비된 `dist/`를 함께 제공하며 빌드는 수행하지 않음 |

운영은 빌드한 프런트엔드와 서버 소스·런타임 의존성을 함께 배포합니다. `dist/`만으로는 인증·업무 저장·문서·캘린더 API가 동작하지 않습니다. `start`가 `NODE_ENV=production`을 자동 설정하지 않으므로 운영 `.env` 또는 서비스 환경에서 지정합니다. 기존 운영 환경의 업데이트는 [운영 안내](OPERATIONS.md)의 절차를 따릅니다.

로컬 브라우저 테스트는 `npm run build` 후 `node scripts/e2e-server.mjs`로 실행합니다. 기본 주소는 `http://127.0.0.1:4311`이며, 기본 테스트 계정은 **`test@somansa.com` / `1234`**입니다. 이 계정은 테스트 전용 임시 DB에 생성되며 서버 종료 시 테스트 데이터가 삭제됩니다. 다른 포트는 `E2E_PORT`로 지정합니다.

## 운영 데이터에 영향을 주는 변경

DB 스키마·영속 데이터 형식·기존 데이터 일괄 변환·백업 호환성을 변경할 때는 [데이터베이스 변경 지침](DATABASE_CHANGES.md)을 먼저 읽고, 명시적 사용자 승인과 해당 문서의 구현·검증·배포 절차를 따릅니다. 현재 저장 구조와 지원 버전은 [데이터 형식](DATA_FORMAT.md#버전과-운영-호환성)에서 확인합니다.

## 주요 처리 흐름

### 조회와 개인 보기

로그인 세션은 기존 `sessions.expires_at`와 HTTP-only·SameSite=Strict 쿠키를 이용해 30일 유지합니다. 유효한 인증 요청에서 하루에 한 번만 갱신하여 매 요청의 DB 쓰기와 Set-Cookie를 피합니다. 로그아웃·비밀번호 변경은 자체 삭제·재발급 경로를 사용하며 만료·비활성 계정은 갱신하지 않습니다. DB 버전·형식은 변경하지 않습니다.

로그인 후 `/api/bootstrap`에서 소속 팀·사용자를 읽고 사용자·팀·기준 연도별 보기를 복원한 다음, `startMonth`부터 12개월에 해당하는 업무를 조회합니다. `getTasks`는 한 연도 또는 인접한 두 연도를 받아 SQL의 EXISTS 조건으로 중복 없이 업무를 읽습니다. 화면의 기준 연도는 업무 추가·삽입의 등록 연도입니다. 업무 응답은 ETag로 조건부 조회합니다. 팀·연도가 바뀌면 이전 요청 결과가 새 화면을 덮어쓰지 않도록 조회 대상을 검사합니다. 셀 값 저장은 SSE로 즉시 전달합니다. 행 추가·삭제·순서·공통 서식·설정과 사본 시트 변경은 리소스 SSE 알림으로 재조회합니다. 기존 7초 조회는 원본의 보완 경로로 유지하며, 편집·저장 중에는 전체 목록 교체를 보류합니다. SSE 셀 갱신은 편집 중에도 처리합니다.

변경되지 않은 ETag 요청은 업무를 조회·직렬화하기 전에 304로 응답합니다. 조회 캐시의 전체 예산은 64MiB입니다. 원문과 gzip의 합이 예산보다 크면 gzip만 보관하고, 압축을 받지 않는 클라이언트의 응답 시에만 원문을 복원합니다. 압축본도 예산을 넘으면 캐시하지 않습니다. 이전 팀의 보기 저장이 뒤늦게 실패해도 현재 팀 화면에 오류를 표시하지 않습니다.

팀·연도 전환과 월 이동·월·주차 기간 선택은 왼쪽 업무 열에서 시작합니다. 달력은 항상 12개월이며 화살표는 한 달씩 이동합니다. `movePeriodView`는 월 선택을 실제 연월로, 주차 선택을 날짜로 유지하고 구간 경계에서만 선택 길이를 보존해 이동합니다. 연도 화살표의 전체 연도 초기화와 구분하며 원본·사본에 같은 규칙을 적용합니다. `taskQuery`는 같은 두 연도에 걸친 월들을 같은 요청 경로로 정규화하므로 월 이동마다 데이터를 재조회하지 않습니다. 보기의 저장 키와 업무 조회 범위를 분리하고, 늦은 조회 응답과 SSE가 다른 범위를 덮어쓰지 않도록 검사합니다. 기간 표는 포인터 캡처로 월/주 단위의 연속 범위를 선택하고 드래그를 마칠 때 보기를 저장합니다. 기존 보기 설정 모달은 제거했으며 열 고정은 머리글 메뉴, 팀 기본 셀 높이는 기본 서식 관리에 있습니다. 연도·기간 바, 서식 툴바와 팝업 제목 옆 `?` 도움말은 즉시 툴팁을 공유합니다. 팝업 소개 문구는 `Modal`의 `help`로 전달하며, 마우스 호버나 키보드 포커스로 확인합니다. 기본 서식과 표는 `Toolbar`를 공유하고, 서식 선택·테두리 팝업은 모달 안에서 열리면 해당 dialog를 portal 대상으로 사용합니다. 발표 모드는 현재 보기와 위치를 유지하며 종료하면 화면 위치를 복원합니다.

필터 목록과 현재 조건·선택은 팀을 열 때 `/api/filters?teamId=…`에서 읽고, 연도 전환 때 다시 읽거나 초기화하지 않습니다. 표 배치의 `views`와 별도로 연도 컬럼이 없는 `saved_filters`, `filter_states`에 저장합니다. `/api/filters/current`는 본인의 현재 상태만 저장하며, 공용·개인 정의 변경은 `/api/filters/:id`에서 권한을 검사합니다. 팀원이 공용 조건을 바꾸면 개인의 현재 조건으로 분리합니다. 스냅샷과 UI에서만 배치·조건을 하나의 View로 합칩니다.

필터 신규 저장·같은 이름 저장이 완료되면 갱신한 목록에서 이름과 공개 범위가 일치하는 필터를 찾아 바로 선택·적용합니다. 목록에서 선택할 때도 `applySavedFilter`로 같은 조건·선택 저장 경로를 사용합니다. 목록에서 필터를 선택할 때는 `Grid`의 기존 `jump`를 통해 렌더링 후 세로 스크롤을 0으로 이동하고 가로 위치는 유지합니다. 원본·사본과 같은 필터 재선택에 공통 적용하며, 저장 완료 경로는 `scrollToTop: false`로 현재 위치를 유지합니다. 사본에서 원본으로 돌아올 때의 위치 복원도 유지합니다. 이름 변경만 할 때는 현재 선택을 바꾸지 않습니다. 선택 상태는 필터 보기 표시줄과 목록 항목의 `aria-pressed`에 반영하며 목록 오른쪽 체크 아이콘은 표시하지 않습니다.

### 셀 저장과 동시 수정

작업 완료 안내는 `src/Toast.tsx`의 `Toast`·`useToast`를 사용합니다. 설정·비밀번호·이력 정리·사본 이름 모달 안에서 렌더링하여 열린 dialog 위에 표시하며, 같은 문구를 다시 알려도 4초 표시 시간을 갱신합니다. 사본 표의 자동 저장 상태는 보조기기에 알리고, 저장 오류는 표 위에서 확인·재시도할 수 있습니다. 오류·입력 검증과 현재 진행 상태는 해당 화면에서 유지합니다.

기본 셀 툴바와 발표 도구는 `ZoomControls`의 50~200% 입력·증감·복원을 공유합니다. 확대는 `.grid-area`에만 적용하며 `Grid`의 행·열 크기 드래그는 포인터 이동량을 배율로 나눠 원래 치수에 반영합니다. 확대율은 화면 상태이며 업무 데이터와 View에 저장하지 않습니다. 발표 모드는 기본 배율을 초기값으로 받아 별도로 조절하고 종료 시 기본 배율을 복원합니다.

기간 밖 주차와 접힌 월을 포함한 현재 12개월 전체 열 순서로 숨김 구간을 계산합니다. 날짜 구간을 펼칠 때는 현재 보이는 주차와 펼칠 주차만 남기고 나머지를 `hiddenWeeks`로 표현하여 다른 구간의 숨김을 유지합니다. 달력의 선택 표시도 실제 표시 주차를 사용합니다.

서식 선택 범위와 테두리의 인접 셀은 필터를 통과한 전체 행(숨긴 행 포함)과 숨김 전 전체 열 순서로 계산합니다. 값 편집·복사·붙여넣기·행 이동은 보이는 셀 기준을 유지합니다.

`Toolbar`의 서식 복사는 `App`에 선택 범위의 표시 서식을 보관하고, `Grid`의 선택 드래그 종료 또는 Enter에서 적용합니다. 값은 보내지 않고 기존 `mutate`·`submitChanges` 경로로 셀 버전과 공통 서식 revision을 검사합니다. 한 셀의 서식을 행·열·전체에 적용할 때는 기존 공통 서식 scope를 사용하며 사본도 기존 저장·실행취소 경로를 공유합니다. 복사한 셀의 표시 서식을 재현하기 위해 공통 scope에도 기본 글꼴·크기 값을 명시하고, 없는 서식 속성은 null로 전달하여 대상에 남은 강조·배경색 등을 제거합니다. 대상 업무의 기본 서식으로 되돌리는 reset과 구분합니다. 단일 적용은 완료 후 해제하고 두 번 클릭한 연속 적용은 Esc·버튼 클릭·시트 전환으로 해제합니다. 서식 복사의 전역 Esc는 열린 dialog에 양보합니다. 그 외에는 이벤트 전파를 유지해 저장된 필터 메뉴도 닫히게 하며, Grid는 이미 처리된 Escape(`defaultPrevented`)나 서식 복사 중인 Escape에서 선택을 해제하지 않아 이벤트 도중 렌더링 시점에 영향을 받지 않습니다. 저장 중 추가 적용은 `submitChanges`와 같은 `rejectPendingChanges` 안내를 사용하고 복사 상태를 유지합니다. DB·저장 형식은 변경하지 않습니다.

주차 기본 경계선은 `settings.weekBorders`에 저장하며 `shared/borders.js`의 `weekBoundaryStyles`와 `withWeekBoundaries`로 실제 표시·반출 열의 첫 날짜와 마지막 날짜에 적용합니다. 같은 경계를 공유하는 두 셀을 함께 계산하며, 셀이나 행·열에 직접 지정한 선이 경계선보다 우선합니다. `null`·`none`이나 업무 기본 서식에서 상속된 선은 주차 경계선을 가리지 않습니다. 원본 셀 서식은 수정하지 않으며 그리드의 머리글·셀·텍스트 넘침 경계와 XLSX에서 같은 계산을 사용합니다. 셀 클립보드는 저장된 서식만 복사합니다.

이번 주 기본 좌우 테두리는 선택 설정 `settings.currentWeekBorders`를 같은 `weekBoundaryStyles` 계산에 전달합니다. 실제 표시·반출 열 중 한국 시간의 월요일 키에만 적용하며, 설정한 방향은 양 끝 경계선보다 우선합니다. 직접 지정한 셀·행·열·이웃 셀의 선은 기존 `withWeekBoundaries` 경로로 우선합니다. `Grid`와 `PeriodPicker`는 `useTodayKey`로 한국 시간 자정과 탭 복귀 시 날짜를 갱신하므로, 자동 조회가 없는 사본에서도 이번 주 표시가 이동합니다. 기존 `teams.settings` JSON에 선택 필드만 추가하며 SQLite v30·JSON v6, 셀·이력·사본의 기존 읽기 호환성을 유지하고 데이터 변환은 하지 않습니다.

`shared/compact.js`의 서식 사전을 HTTP 요청·응답, SSE, JSON 반출, 이력·스냅샷에 공통 적용합니다. DB는 `styles` 테이블을 `cells.style_id`·`tasks.default_style`·`tasks.row_style`·`format_rules.style_id`에서 참조합니다. 새 셀의 빈 내용과 불필요한 서식은 생략하되, 삭제·실행취소 후에도 기존 셀 버전은 유지합니다. `tests/compact-storage.test.mjs`는 실제 생성 API, 3,180셀 범위 저장, 공통 사전 크기, 서식 정리 후 이력 복원·재시도, 변경 없는 요청과 충돌, 잘못된 압축 참조를 검증합니다.

2026-10-12, 기준 커밋 `5a79eaf`와 v14 코드를 같은 합성 업무 100행으로 비교했습니다. 임시 메모리 SQLite DB·로컬 HTTP 서버를 각각 만들고 2,000셀 공통 서식 변경을 번갈아 실행했습니다(준비 4회, 측정 24회, Node.js v22.23.1). 요청 인코딩부터 응답 해석까지의 중앙값은 31.24→29.16ms, P95는 34.75→32.62ms였습니다. 마지막 작업 기준 요청 JSON은 830,105→214,310바이트, 응답 JSON은 1,676,634→443,003바이트, 이력·재시도 저장 본문은 1,676,685→443,076바이트로 줄었습니다. gzip(level 1) 응답은 23,505→17,572바이트입니다. 공백 주차에 null 테두리가 채워진 별도 합성 행은 54→4셀로 저장되고, 응답 JSON은 6,937→591바이트였습니다. 같은 환경의 비교값이며 운영 네트워크·디스크 지연의 보장은 아닙니다. 상세 결과는 `docs/validation/compact-storage-performance-20261012.json`에 있습니다.

공통 서식의 범위 판정은 요청별로 행·열·제외 열을 `Set`으로 한 번 인덱싱하고 재사용합니다. 각 셀마다 선택 행 배열 전체를 다시 검색하지 않습니다. 2026-10-13 로컬 Node.js 22.23.1·메모리 SQLite·HTTP API에서 10,000행, 기존 190,000셀에 배경색 공통 규칙을 적용한 3회 측정의 중앙값은 10,227.75→335.82ms로 줄었습니다. 요청 인코딩부터 응답 해석까지 측정했으며, 요청·응답 크기와 셀 레코드 수는 동일합니다. 운영 환경의 지연 보장은 아닙니다.

압축 응답을 풀 때는 참조가 바뀌는 경로만 복제하며 원본 전송 데이터는 변경하지 않습니다. 같은 Node.js 22.23.1·Chromium 환경에서 기준 커밋 `5a79eaf`와 당시 변경 코드를 순서대로 측정한 1만 행 화면 표시 10회의 중앙값은 209→251ms, P95는 713→841ms였습니다. 동시 30명 조회 P95는 1,001→1,050ms, 저장은 46→31ms, 검색은 170→167ms였습니다. 초기 표시에는 소폭 증가가 남아 있으며, 상세 로컬 결과는 `docs/validation/precommit-performance-20261013.json`에 있습니다.

셀 편집을 확정하면 `/api/cells/batch`로 `operationId`·최초 `createdAt`, 셀별 `expectedVersion`, 값 또는 서식을 보냅니다. 서버는 인증·팀 접근·업무 편집 권한·속성 종류를 확인하고 전체 변경을 한 트랜잭션으로 저장합니다.

한 셀이라도 버전이 다르면 409로 전체 작업을 취소합니다. 같은 사용자의 동일 작업 ID 재시도는 이전 성공 결과를 재사용합니다. 저장 실패 시 입력과 요청을 유지하고, 재적용 시 최신 버전을 확인합니다. 실행취소도 같은 버전 검사와 저장 경로를 사용합니다. 업무 추가 취소는 삭제 응답의 `updatedAt`을 보관하고 재실행할 때 서버에 보내며, 그 사이 다른 복구·수정·삭제가 있으면 실제 복구와 감사 기록 전에 409로 거절합니다.

전후 셀 데이터는 `audit`에 한 번만 저장하고 `operations`에는 이력 ID·팀 ID·응답 시각·업무 수정시각만 남깁니다. 여러 팀이 섞인 요청은 팀별 원래 위치 번호를 함께 기록합니다. 정상 저장에서는 현재 셀과 같은 변경을 건너뛰며 과거 이력을 읽거나 비교하지 않습니다. 재시도에만 `audit.id` 인덱스로 읽어 최초 응답을 재구성합니다. 참조가 사라졌으면 410을 반환하고 재적용하지 않습니다. `tests/cell-operations.test.mjs`는 저장량, 정상 저장의 이력 조회 부재, 재시도의 인덱스 사용, 재시작·후속 편집·복원·권한 변경·팀 삭제·트랜잭션 롤백을 검증합니다.

시스템 감사 로그는 `server/system-audit.mjs`와 `src/SystemAuditLog.tsx`에서 조회합니다. 공통 이력만 관리자에게 공개하고 한국 시간 날짜·수행자·종류로 필터링합니다. `(created_at,id)` 커서로 50건씩 조회하며 목록은 전후 JSON을 읽지 않습니다. 브라우저는 상세를 펼칠 때만 가져오고 필터가 바뀌거나 화면을 닫으면 이전 요청을 취소합니다. `tests/system-audit.test.mjs`는 실제 로그인·로그아웃 기록, 세션 확인·재발급 시 중복 방지, 권한·날짜 경계·같은 시각의 페이지 경계·정리 중 커서 유지·큰 상세·인덱스 사용을, `tests/browser/system-audit.spec.ts`는 로그인 화면부터 오늘 로그 조회, 검색·초기화·페이지 이동·상세 지연 조회·오류 재시도·늦은 응답 무시를 검증합니다.

2026-10-12 로컬 Node.js 22.23.1에서 변경 직전 코드와 참조 저장 코드를 별도 임시 SQLite DB·API 서버로 실행해 비교했습니다. 합성 업무·텍스트·서식을 동일하게 구성하고 두 서버에 번갈아 HTTP 요청을 보냈습니다. 각 서버 6회 준비 실행 후 한 셀은 120회, 2,000셀은 30회 서식 저장을 측정했으며, 요청 시작부터 응답 JSON 읽기까지의 시간입니다. 한 셀의 중앙값은 2.13→2.10ms, P95는 2.48→2.55ms로 비슷했고, 2,000셀 중앙값은 45.84→39.04ms, P95는 49.45→42.58ms였습니다. 2,000셀 작업의 이력·재시도 JSON 합계는 작업당 평균 4.18→2.09MB로 약 50% 감소했습니다. 저장량 평균에는 준비 실행을 포함한 36개 작업을 사용했습니다. 운영 환경의 지연 보장이 아니며, 기존 DB를 변환한 결과도 아닙니다.

커밋 전 전체 리뷰에서는 `1543a6e`와 최종 코드를 같은 임시 데이터로 교차 측정했습니다. 한 셀 240회·2,000셀 100회(각 6회 준비 실행 제외)의 HTTP 요청·응답 시간이며, 2,000셀 작업의 이력·재시도 본문 저장량은 약 50% 줄었습니다.

리뷰 중 열 너비 드래그마다 셀 표시 서식이 다시 만들어지는 것을 수정했습니다. 표시 서식은 너비와 독립적인 열 키와 업무·경계선이 바뀔 때만 계산합니다. 2,000행·Chromium CPU 4배 감속 조건에서 드래그 단계 중앙값은 수정 전 42ms에서 34ms로 줄어 기준 커밋의 34ms와 같았습니다. 셀 선택 중앙값도 기준 커밋과 최종 코드 모두 33ms였습니다. 별도 1만 행·45.5MB 스냅샷 샘플의 gzip 압축은 level 9의 534~546ms·1.60MB에서 level 1의 64~67ms·2.42MB로 바뀌었습니다. 이 수치는 로컬 합성 데이터 측정이며 압축 시간은 스냅샷 API 전체 응답 시간이 아닙니다.

`GET /api/tasks`의 `X-Cell-Event-ID` 헤더는 스냅샷 시점의 SSE 커서입니다. 304 응답에도 포함합니다. 프런트엔드는 스냅샷을 표시한 뒤 `/api/cells/events?teamId=…&year=…&after=…`에 연결하므로 조회와 연결 사이의 변경도 재전송받습니다. 서버는 DB 커밋 후 값 또는 개별 서식이 바뀐 셀 레코드를 전송합니다. 레코드의 값·서식·버전은 일관된 저장 결과를 사용하며, 공통 서식 변경은 팀 리소스 알림으로 최신 목록을 읽어 반영합니다. 재시도된 작업·실패한 트랜잭션·개인 View 저장은 셀 이벤트를 발생시키지 않습니다.

SSE는 로그인 세션과 팀 접근을 구독 시점, 이벤트 전송 전, 15초 heartbeat마다 검사합니다. 여러 연도에 속한 업무의 셀 변경은 해당 연도 구독자에게 전달합니다. `startMonth`로 두 연도를 구독할 때도 SSE 연결은 하나이며, 작업별 변경 셀을 중복 제거하여 하나의 이벤트로 전송·재전송합니다. 따라서 하나의 커서가 두 연도의 변경 전체를 나타냅니다. `Last-Event-ID`로 재접속하며, 서버 메모리의 최근 512개 작업·8MiB 범위에서 재전송합니다. 서버 재시작·버퍼 만료 또는 256KiB 초과 이벤트는 `reset`을 보내 최신 DB 스냅샷과 새 커서로 복구합니다. DB 스키마 변경이나 별도 메시지 서버는 필요하지 않으며 단일 앱 프로세스를 전제로 합니다.

수신한 변경은 40ms 동안 모아서 셀별 최신 버전만 반영하고 바뀌지 않은 행 객체는 재사용합니다. 느린 연결의 서버 송신 버퍼와 클라이언트 대기 셀 수에도 한도를 둡니다. 숨긴 셀도 내부 데이터는 갱신하지만 개인 View·선택·스크롤·실행취소 기록은 바꾸지 않습니다. 편집 시작 시점의 값과 버전을 보관하여 입력 중 원격 변경으로 저장 기준이 바뀌지 않도록 하며, 해당 행의 필터·정렬 재평가는 편집 종료까지 미룹니다. 본인이 입력 중 적용한 서식 저장만 편집 기준 버전을 올립니다. 늦은 HTTP 응답과 재접속 스냅샷도 최신 셀을 되돌리지 않습니다.

전체 행·열 선택은 선택한 업무 ID·열 키와 서식만 서버로 보내며 셀마다 요청을 만들지 않습니다. 서버는 공통 규칙과 영향을 받는 기존 셀 예외만 변경합니다. `shared/formatting.js`가 표시·행 복사·XLSX 반출에서 같은 상속 계산을 사용하고, `src/format-selection.js`가 숨김을 포함한 선택 영역의 테두리를 같은 패턴끼리 묶습니다. 셀 예외와 값은 개별 버전으로, 공통 규칙은 팀별 revision으로 충돌을 검사합니다. `format-audit` 재시도·이력 정리·업무별 이력 조회도 일반 셀 변경과 같은 보관 계약을 따릅니다. 공통 규칙 전송은 문서별 `$formats` 사전으로 중복을 제거합니다.

저장 규칙의 기준 문서는 [데이터 형식과 API](DATA_FORMAT.md#저장-규칙-요약)입니다. 내부 모델은 긴 서식 이름을 사용하되, 변경 이력의 JSON 표시는 `pack`으로 저장 형식을 그대로 재구성합니다. 셀 서식 요약 JSON도 `compactStyle`로 축약합니다. 업무 생성·이동·삭제 이력에는 `taskAuditSnapshot`으로 관계없는 행 규칙과 업무 ID를 제외합니다. 실시간 업무 응답의 팀별 공통 상태는 유지합니다.

`tests/common-formatting.test.mjs`는 공통 행·열 저장, 연도 경계, 1,000행 빈 셀 미생성, 속성별 우선순위, 셀 예외 재적용, 복사, 충돌·권한·이력 복원과 업무 이력의 불필요한 규칙 제외를 실제 API로 검증합니다. `tests/browser/common-formatting.spec.ts`는 화면의 행 선택→월 이동→새해→새로고침, 열 서식→셀 예외→재적용→실행취소·재실행, 큰 글자의 행 높이·테두리, 축약된 이력 JSON 표시를 확인합니다.

2026-10-13, 당시 코드의 셀별 저장과 공통 규칙 저장을 같은 합성 업무 100행·56열에서 비교했습니다. 별도 메모리 SQLite·로컬 HTTP API를 사용해 4회 준비 후 24회씩 번갈아 측정했습니다(Node.js v22.23.1, 요청 생성·인코딩부터 응답 해석까지). 행 전체 서식 요청은 597,953→10,804바이트, 응답은 1,237,800→11,005바이트, gzip(level 1) 응답은 49,959→2,990바이트였습니다. 원래 제목 셀만 100개인 데이터에서 셀별 저장은 5,600셀을 만들었고, 공통 규칙 저장은 100셀을 유지하고 규칙 하나를 추가했습니다. 중앙값은 73.05→3.92ms, P95는 84.86→4.24ms였습니다. 이는 같은 코드 안의 두 저장 경로 비교이며 운영 디스크·네트워크 지연 보장이 아닙니다. 로컬 상세 결과는 `docs/validation/common-formatting-performance-20261013.json`에 있습니다.

`/api/teams/:id/events`와 `/api/reports/:id/events`는 성공한 변경 뒤 재조회 알림을 보냅니다. 개인 보기 저장은 알리지 않으며 셀 값은 기존 델타 스트림을 유지합니다. `useResourceSync`는 같은 리소스의 연결을 탭 안에서 공유하고 짧은 연속 알림을 묶습니다. 페이지별 `X-Client-ID`로 이미 응답을 반영한 자기 변경 알림의 중복 조회를 줄이며 같은 계정의 다른 탭은 별도로 갱신합니다. 편집·저장 중에는 갱신을 보류하고 화면·팀을 떠날 때 연결과 요청을 정리합니다. 사본의 독립 셀 수정은 `rebaseReportCells`로 최신 시트에 재적용하되 동일 셀·행 삭제·구조 작업 충돌은 기존 오류 흐름으로 남깁니다. 원격 변경 뒤 실행취소 기준에는 상대방의 최신 값이 포함됩니다. 문서 유무·개수는 사본 시트 revision과 독립적이므로 같은 revision 응답에서도 기존 문서 메타데이터 갱신 경로를 사용합니다. 조회 중 로컬 문서나 이름이 바뀌면 오래된 응답을 적용하지 않고 다시 읽습니다.

### 업무 문서와 에디터 선택

문서 브라우저의 검색은 선택한 팀·연도·원본/사본 범위에서 작업 이름만 부분 일치로 비교하며, 앞뒤 공백과 영문 대소문자를 무시합니다. 문서 제목과 본문은 검색하지 않고, 일치한 작업의 모든 문서를 순서대로 표시합니다. 작업 이름을 클릭하면 첫 문서를 엽니다. 본문은 결과 페이지의 짧은 미리보기를 만들 때만 읽습니다.

2026-10-14 공식 문서·저장소·npm 메타데이터를 비교해 MIT 라이선스의 **Milkdown 7.22.3**을 선택했습니다. [공식 소개](https://milkdown.dev/docs/guide/why-milkdown), [설치와 Kit 사용법](https://milkdown.dev/docs/guide/getting-started), [소스·라이선스](https://github.com/Milkdown/milkdown), [유지보수 이력](https://github.com/Milkdown/milkdown/releases)을 확인했습니다. ProseMirror의 편집·IME·history와 Remark의 Markdown 파이프라인을 사용하며, 공식 CommonMark·GFM 확장 및 명령 API를 연결합니다. React peer dependency를 요구하지 않는 Kit 인스턴스를 React 19 effect에서 생성·정리하고 TypeScript/Vite 빌드로 확인합니다. 자체 contenteditable 엔진은 만들지 않습니다.

세 후보 모두 오픈소스의 필요한 편집 기능은 제공하지만, 한국어 OS IME 품질이나 접근성 전체를 패키지 설명만으로 보장하지 않았습니다. 선택한 에디터에 한글 조합·붙여넣기·실행취소·버튼/체크박스/모드의 키보드 경로를 실제 브라우저로 검증합니다. 후보 전체의 완성 번들 크기를 같은 UI로 벤치마크한 것은 아닙니다. 채택한 구성의 번들은 빌드 청크와 초기 네트워크 요청으로 측정합니다. 패키지 설치 크기는 실제 브라우저 전송량과 구분합니다.

`DocumentEditor`는 모든 Markdown 저장 경로에서 본문 SSE를 구독합니다. 업무·사본 업무·원본 메모·사본 메모·캘린더 문서의 저장 시 최신 스냅샷을 전달하며 재연결에서는 마지막 커서 이후 변경된 경우에만 본문을 보내고 `shared/document-merge.js`로 독립 변경을 병합합니다. `sync: {session,sequence}`는 서버 프로세스 내 전송 순서이며 숫자 또는 UUID인 영속 revision과 분리합니다. HTTP 응답이 SSE보다 먼저 도착해도 오래된 스냅샷을 다시 적용하지 않습니다. 접근 권한은 전송마다 다시 확인합니다. 여러 문서 탭은 선택한 문서만 본문 스트림을 유지하고, 다시 선택할 때 최신 스냅샷을 받습니다. 문서 목록의 추가·이름·순서는 별도 목록 알림으로 갱신합니다.

`GridCell`의 작업명 오른쪽 문서 버튼은 기존 `rowMenu` 상세 열기 경로를 공유합니다. 본문이 없는 업무에서는 행 hover·작업명 선택·키보드 초점에서 흐리게 표시하고, 본문이 있으면 문서 개수 표시와 함께 항상 표시합니다. 편집 중에는 버튼을 숨기고 발표 모드에서는 빈 업무의 버튼을 만들지 않습니다. 발표 중 문서가 있는 업무의 버튼은 기존 `RowPanel`을 읽기 전용으로 열며 업무 동작 버튼을 숨깁니다. 버튼의 포인터·키보드 이벤트는 셀 편집·범위 선택으로 전파하지 않습니다.

`TaskDocumentPanel`과 `RichMarkdownEditor`를 동적 import로 분리합니다. 목록에는 `hasDocument`만 보내고 상세에서 문서 제목 목록, 선택한 탭의 본문을 순서대로 조회합니다. 내용도 로컬 초안도 없으면 캐릭터 안내와 작성 버튼을 표시하고 본문·리치 편집기 조회를 미룹니다. 작성 버튼은 저장 부작용 없이 편집기를 열고, 기존 본문·초안은 바로 복원합니다. 방문한 문서만 편집기를 만들고 숨겨진 탭의 상태는 유지합니다. 원문 입력창은 팝업의 문서 영역에 flex로 맞춰지고 내부에서 스크롤하며, 리치 본문은 기존처럼 상세 영역을 스크롤합니다. 한글 조합 중에는 저장하지 않으며 전환·닫기 전에 입력을 flush합니다. 초안 저장 키는 사용자·팀·원본/사본·업무·문서 ID로 나눕니다.

상세는 `DocumentLoading`으로 중앙의 같은 캐릭터와 높이를 유지한 뒤 탭·도구·본문을 함께 표시합니다. `LoadingState`를 앱 초기화·업무표 조회·XLSX 처리·감사 로그·용량 조회에서도 공유합니다. `GraeLoading`은 기존 캐릭터의 네 칸을 순서대로 밝히고 reduced-motion에서는 정지합니다.

Milkdown 진입 전 AST 왕복 검사를 하고 안전한 `<br>`만 줄바꿈으로 표시합니다. 지원하지 않는 HTML·외부 이미지 등은 원문을 보존합니다. 이미지 붙여넣기·드롭은 문서별 권한 API를 거치며 크기 조절 값은 로컬 이미지 URL에 보존합니다. 문서 제목은 탭 안에서 글자 길이에 맞춰 늘어나는 입력 상자로 수정하며, UI 및 원본·사본 생성/이름 변경 API에서 최대 50자를 허용합니다. 탭에는 10자 이상인 이름을 앞 9자와 …로 줄여 표시하되 접근성 이름·툴팁·저장값은 전체 제목을 유지합니다. 조합 입력을 보호하고 blur·Enter·탭 전환·닫기에서 동일한 저장 Promise를 기다립니다. 문서별 편집기의 원문/리치 토글은 선택된 탭의 오른쪽으로 portal 렌더링하여 본문 상태를 유지합니다. 리치 편집의 저장 상태는 툴바 오른쪽 실행취소·재실행 버튼 앞에 렌더링하고, 원문·읽기 전용·편집기 오류 상태에서는 제목 줄에 표시합니다. 제목 줄과 그 바로 아래 리치 툴바는 스크롤 상단에 고정합니다. 제목 탭은 가로 스크롤하고 수평 wheel 이벤트 및 overscroll 경계를 처리해 브라우저 탐색을 방지합니다. 전체 페이지에서도 업무 속성을 유지합니다.

연간 업무의 `canEdit(user, task)`는 팀별 `canContribute`를 사용합니다. 팀장·팀원은 작성자·담당자·지원자와 관계없이 같은 팀의 표·속성·문서를 편집하고 업무를 삭제·실행취소할 수 있습니다. 담당자·지원자 지정과 묶음 행 삽입·붙여넣기도 같은 기준을 사용합니다. 꼬리 메모는 기존 `canContribute` 검사로 공동 편집하며, 열람자와 외부 팀 사용자의 쓰기는 거절합니다. 캘린더 개인 일정의 소유자 검사와 팀 관리 권한은 별도로 유지합니다. 권한 설정 필드·SQLite 스키마·기존 데이터 변환은 추가하지 않습니다.

원본과 사본 문서 모두 자동 저장합니다. 각 사본은 자체 문서 배열을 갖고 불변 본문만 공유하며, 저장은 해당 문서 참조만 교체합니다. 분기 UI·원문/분기 연결 API는 제거했습니다. 사본 표의 `useReportDraft`는 저장 중 새 입력을 대기열에 추가하고 완료 후 이어 저장합니다. 실행취소는 셀/행 상태를 복원하지만 현재 행의 문서 참조는 유지합니다. 삭제 직전 문서를 읽어 행 복원에 포함합니다. 사용자 자료는 검증 fixture로 사용하지 않습니다.

사본 본문 자동 저장은 `report_documents`의 해당 참조만 갱신하고 이전 본문 버전만 정리합니다. 문서 조회용 행 ID·제목 인덱스는 압축 BLOB 해시로 무효화하며, 셀·본문을 보관하지 않는 16MiB 예산의 캐시를 사용합니다. 표를 해제한 뒤에는 `readReport`로 최신 문서 참조를 합쳐야 합니다. 여러 행 삭제·실행취소는 `POST /api/reports/:id/documents/batch`로 최대 100개 행씩 읽고 실행취소 이력을 한 번에 갱신합니다. 응답 본문 합계는 8MiB에서 다음 행으로 나누되 한 행의 문서는 분할하지 않으며, 클라이언트는 반환된 행 수부터 이어 읽습니다. 화면에서 문서가 없어 보이는 행도 함께 조회해 다른 사용자의 최근 저장을 보존합니다.

사본 메모는 `server/memo-storage.mjs`의 참조 복사와 `DocumentBusinessService`의 공통 편집 경로를 사용합니다. 사본 표를 읽거나 저장할 때 메모 본문을 읽거나 표 BLOB에 포함하지 않습니다. 테스트는 복사 전후 `document_versions` 수, 공유 참조 ID, 메모 편집 전후 표 BLOB·revision 동일성, 재복사·재시도·권한·충돌·정리·이미지·JSON 반출·백업과 화면의 닫힌 상태 복사·저장 직후 재복사·원본 분리를 검증합니다.

업무 상세와 꼬리 메모는 `DocumentPanel`의 같은 탭·제목 입력·메뉴 구현을 사용합니다. 각 탭은 편집 여부와 관계없이 40px 높이를 유지하며, 제목 입력은 측정용 텍스트가 결정한 grid 영역 위에 배치해 팝업의 공통 입력칸 너비가 탭 폭을 늘리지 않게 합니다. 화살표 hover는 사본 탭과 같이 색상을 바꾸지 않으며 선택 상태만 표시합니다. 각 문서 탭 오른쪽의 아래 화살표에서 공통 이름 변경·삭제 메뉴를 엽니다. 다른 문서의 메뉴를 열 때도 기존 `select()`로 현재 입력을 저장한 뒤 대상을 전환합니다. 메뉴는 `SheetTabs`와 같이 가로 스크롤 영역 밖의 제목 줄에 배치하고 화살표 위치를 따라가며, 화면 밖으로 스크롤되면 닫습니다. 기존 바깥 클릭·Escape·Tab 닫기와 열람자 권한을 유지합니다. 문서 폭은 `DocumentPage`가 포인터 캡처로 조절하며 키보드 조절·취소를 지원합니다. 폭은 사용자·팀·원본 연도/사본·문서별 localStorage에 보관하고 본문·순서는 기존 API를 이용합니다. `AnnualMemoPanel`은 전체 너비의 제목 버튼과 별도 본문으로 아코디언을 구성하고, 사용자·팀·원본 연도/사본별 `weekly-plan:memo-open:…` 키에 펼침 상태를 기억합니다. 닫기는 기존 문서 `flush()`가 성공한 뒤에만 상태를 저장하며, 접힌 상태에서는 `DocumentPanel`을 마운트하지 않아 메모를 조회하지 않습니다. 저장소 접근이 차단되어도 현재 화면에서는 열고 닫을 수 있습니다. 복원된 열린 상태에서는 표를 아래로 이동하지 않으며, 직접 아코디언을 열었을 때만 `scrollOnOpen`으로 문서를 보여 줍니다. 탭 선택은 탭 레일의 가로 위치만 조절합니다. 아코디언은 서식 툴바와 같은 높이 변수와 팀 테마를 사용하고 글자는 11px입니다. 발표 모드에서도 같은 패널을 읽기 전용으로 유지하며, 발표 도구의 입력 가로채기에서 메모·업무 문서 버튼·열린 dialog를 제외해 아코디언·문서 탭·팝업을 조작할 수 있습니다. 꼬리 메모에 마우스를 올리거나 dialog가 열리면 발표 커서 덮어쓰기를 멈추고 레이저·지우개 표시를 숨겨 기본 커서를 복원합니다. 전역 Escape 처리도 열린 dialog에 양보하므로 중첩 이미지 팝업을 닫을 때 발표가 종료되지 않습니다. `SheetHorizontalScroll`은 업무 표의 가로 스크롤을 메모 위에 표시하며, 기존 `.sheet-scroll`의 좌표와 동기화해 행 가상화·고정 열·위치 복원을 유지합니다. 표의 가로 wheel·터치 이동을 처리하고 메모 내부 제스처는 각 문서와 메모 영역에 맡깁니다.

### 속성과 상태 통계

작업·팀원·상태는 필수 속성입니다. 팀원과 지원자는 업무 담당 정보를 나타내며 단일·복수 선택 구성을 유지합니다. 연간 업무의 편집 권한은 담당자·지원자 값에 의존하지 않습니다. 설정의 `revision`은 관리자 간 충돌을 검사합니다. 속성 종류 변경은 기존 셀을 변환하고, 변환 불가능한 값이 있으면 전체 변경을 취소합니다.

상태 통계는 실제 상태 옵션을 기준으로 현재 달력의 최대 두 연도에 속하는 전체 업무를 중복 없이 집계합니다. 필터·숨김은 통계 분모를 바꾸지 않습니다. 보관된 속성과 값은 기존 셀·스냅샷을 해석할 수 있도록 보존합니다.

### 이관과 삭제

XLSX는 미리보기 후 담당자·예외 확인을 거쳐 적용합니다. 파일·팀·행 범위 및 열 연결 설정·시트·모드·연도 조합으로 중복 적용을 방지합니다. 담당자가 비어 있으면 미지정으로 유지합니다. 여러 표가 섞인 원본에는 API의 `sheetOptions`로 업무 표의 범위를 지정할 수 있습니다. 사본은 생성 당시 값·사용자·설정·보기를 보존하고 이후 독립적으로 편집합니다.

사본 편집은 `src/useReportDraft.ts`의 자동 저장 큐·실행취소 기록을 사용합니다. `shared/report-editing.js`가 브라우저와 서버에서 같은 편집 작업을 적용하고, `server/report-editing.mjs`는 팀 기여 권한·사본의 속성·BLOB revision을 검증한 뒤 해당 사본만 저장합니다. 현재 업무의 mutation·SSE·실행취소·필터 저장 경로와 연결하지 않습니다. `tests/reports.test.mjs`는 원본 속성 변경·원본 업무 삭제·권한·원자성·동시 수정·재시작·응답 유실 재시도를, `tests/browser/report-editing.spec.ts`는 편집·추가·삭제·서식·실행취소·자동 저장·실패 재시도·기존 필터 복귀를 검증합니다.

업무 삭제는 복구 가능한 삭제 상태로 보존하며, 별도 휴지통 UI 없이 시트별 변경 이력에서 복구합니다. 원본 다중 삭제·복구는 전체 권한과 버전을 검사하고 하나의 트랜잭션으로 처리합니다. 사본 삭제 이력은 삭제 직전 행·문서 본문·참조된 사용자 이름을 보관하며, 복구는 해당 사본에만 적용합니다. 팀 삭제는 시스템 관리자가 확인한 경우 모든 연도의 업무와 연관 데이터를 트랜잭션으로 영구 삭제합니다. 다른 팀·공용 계정은 보존합니다.

## 확장과 변경

여러 탭의 실시간 구독은 `StreamBroker`를 SharedWorker에서 실행합니다. 채널 집합·필요 커서가 같으면 살아 있는 POST 연결을 유지하고, 추가·제거 시 재연결하더라도 기존 문서·리소스의 커서를 보내 변경 없는 초기 프레임을 생략합니다. `createDocumentEvents`는 무구독 중 변경도 추적하며 본문 없이 revision·전송 순서만 최대 10,000개 키까지 보존합니다. 메타데이터 퇴출이나 서버 세대 변경은 최신 스냅샷으로 복구합니다. 각 리스너는 자기 커서 이하의 재전송을 받지 않아 새 스냅샷을 과거 셀로 되돌리지 않습니다. 종료 사유 없는 `closed`와 `rejected` 5xx는 커서를 유지한 일시 종료로 처리하고, 백오프 동안 같은 연결의 정상 채널과 같은 청크의 후속 프레임은 계속 처리합니다. 사유 없는 부분 종료 대기 중 구독 추가·제거는 연결 재시도 시각에 반영합니다. `rejected` 5xx는 해당 채널에만 1.5~30초 백오프를 두며 기한 전 POST에서 제외합니다. 정상 채널·새 구독은 10ms 묶음 처리 후 연결하고, 별도 채널 타이머가 기한에 재연결을 예약합니다. 채널이 15초 이상 유지되면 해당 채널의 지연을 초기화합니다. EOF·네트워크·heartbeat 부재와 단독 `closed`는 기존 연결 단위 백오프를 쓰며 채널 지연과 독립적입니다. 마지막 구독 제거는 즉시 정리하고, 과거 커서로 새 리스너가 합류하면 재전송을 건너뛰지 않도록 먼저 연결을 끊습니다. `access-revoked`는 `{status}`를 전달하며 401은 세션 손실, 403·404는 권한 상실·삭제입니다. 상태 코드가 없는 기존 프레임은 403으로 해석합니다. 401 이외의 `access-revoked` 또는 비재시도 `rejected`가 선행된 종료만 해당 구독의 영구 종료입니다. 모든 리스너가 떠나면 그 키를 제거해 다음 구독은 새 채널을 만듭니다. HTTP 400의 `rejectedIds`만 종료하고 정상 채널은 실패 백오프를 늘리지 않고 다시 연결합니다. 요청 수준 HTTP 401은 전체 연결을, 연결 중 `access-revoked {status:401}`은 해당 채널을 세션 종료로 분류합니다. 문서·리소스 화면은 세션 종료에서 스트림을 닫지 않으며 문서 편집을 권한·삭제 오류로 막지 않습니다. `components.tsx`의 초기 로그인과 재인증 성공은 `resumeSession()`을 호출합니다. 워커의 `resume` 또는 페이지 내 fallback 브로커의 `resume()`이 스트림 키 변화 없이 모든 탭의 세션 종료 채널을 새 ID·보존 커서로 재승인합니다. 구독 없는 로그인 화면도 워커에 신호를 보내고 확인 응답 후 임시 포트를 닫습니다. 세션 종료 채널이 없으면 재연결하지 않습니다. 셀 복구 등 새 스트림 추가·재합류에 의한 기존 재승인도 유지합니다. 반복 전송 실패는 1.5~30초 백오프하고, 셀 스냅샷 복구와 셀의 `rejected` 5xx도 SSE `ready`를 받기 전까지 1~30초 백오프를 유지합니다. 문서·리소스 구독의 비재시도 거부는 기존 접근 거부 처리로 정리하고, 5xx 복구는 브로커가 맡습니다. 워커 대기열 4MiB 초과·리스 만료는 페이지에 즉시 재구독을 요청합니다. 미지원 환경도 같은 브로커를 페이지 안에서 사용합니다. 탭은 `EventStream` 인터페이스를 유지하므로 셀·문서·목록의 기존 동기화 호출부를 재사용합니다. 배포 시 서버와 빌드 결과를 함께 갱신하고 기존 탭을 새로고침합니다. 서로 다른 빌드의 워커 URL은 별개이므로 이전 탭은 새 워커에 자동 합류하지 않습니다.

## 검증

```sh
npm test
npm run build
npx playwright install chromium firefox webkit
npm run test:e2e
```

`npm test`는 임시 DB에서 API·권한·동시 수정·이관·백업/복구·이슈 링크를 검증합니다. `DEBUG_HTTP=1`로 실행하면 서버가 거절한 요청(4xx)의 경로와 사유를 콘솔에 남겨 테스트 실패 원인을 바로 볼 수 있습니다. `npm run test:e2e`는 별도 임시 서버와 DB를 만들고 Chromium·Firefox·WebKit에서 실제 UI를 조작합니다. `4311` 포트를 사용하며 실행 중에는 앱·테스트 소스를 바꾸지 않습니다. Linux 환경에서 브라우저 시스템 의존성이 없다면 `npx playwright install --with-deps chromium firefox webkit`를 사용합니다.

실패한 브라우저 검사는 `test-results/`에 스크린샷·트레이스를 남기고 HTML 보고서는 `playwright-report/`에 생성됩니다. 이 파일들은 Git에서 제외합니다. 테스트 데이터는 코드에서 생성한 가상 업무·계정이며 운영 DB를 사용하지 않습니다.

필요한 경우 다음 보조 명령을 실행합니다.

```sh
npm run performance
npm run performance:stress
npm run licenses
```

성능 명령은 임시 DB에 큰 데이터 집합을 생성하여 조회·저장·렌더링을 측정하고 `docs/validation/`에 로컬 결과를 저장합니다. `npm run performance:ui`는 빌드 후 Chromium에서 화면 처리 시간을 측정해 콘솔에 출력합니다. 문서의 날짜가 붙은 수치는 해당 시점의 로컬 측정 기록이며 현재 릴리스의 검증 결과나 운영 환경의 용량·지연시간 보장이 아닙니다. `docs/validation/`은 Git 제외 경로이므로 새로 clone한 저장소에는 과거 결과 파일이 없을 수 있습니다. 라이선스 명령은 잠금 파일과 설치 패키지에서 [고지 목록](THIRD_PARTY_NOTICES.json)과 [원문](THIRD_PARTY_NOTICES.txt)을 갱신합니다.

## 외부 동기화 개발·검증

[설치 안내](CLOUD_SETUP.md)와 [프로토콜](SYNC_PROTOCOL.md)을 기준으로 `server/sync/`, `server/storage/`, `worker/`를 함께 변경합니다. 내부 `transaction`은 동기 콜백만 허용하고, PG는 하나의 client에서 모든 await·COMMIT·rollback을 끝냅니다. Node의 timer는 readonly SQLite worker에서 Git·병합·해시·재투영을 수행하고 메인 쓰기 경계에서 현재 head·로컬 변경·L·작업 guard를 다시 검사합니다. 사이트 이벤트는 commit 뒤 기존 SSE 경로로 전달합니다.

```sh
npm test
npm run build
npm run build:worker
npm run build:pages
npm run test:e2e -- tests/browser/data-sync.spec.ts
npm run performance:sync
```

PG 테스트는 임시 서버를 직접 실행합니다. 일반 `npm test`에서는 사용할 PG 서버 바이너리가 없으면 관련 검사를 `skip`하고 성공 종료할 수 있으므로, 종료 코드만으로 PG 검증을 주장하지 않습니다. 릴리스 검증은 `TEST_PG_BIN=/absolute/PostgreSQL/bin npm run test:postgres`를 사용합니다. 이 명령은 `postgres`, `initdb`, `pg_ctl`을 먼저 실행 확인하고 하나라도 없거나 실행할 수 없으면 테스트를 시작하기 전에 실패합니다. 준비가 확인되면 같은 경로를 모든 테스트에 전달해 전체 단위·통합 검사를 실행하며, 최종 pass/fail/skip 수도 기록합니다. Worker API 테스트는 임시 control/team PG와 실제 JWT 검증, 대역 R2/Images/GitHub HTTP를 사용합니다. Git CLI 경합·복구 테스트는 임시 bare 저장소를 사용합니다. 실제 cloud 변환 품질·도메인/Access policy·rate limit·운영 DB는 별도 검증 대상입니다.

`performance:stress -- 10000:30`은 이전 릴리스 비교용 기존 시나리오이고 `performance:sync`는 같은 팀/자료에서 미연결·연결·외부 장애·초기 게시·백업 중 저장 및 commit→30개 SSE 도착을 비교합니다. 결과는 Git 제외 `docs/validation/`에 저장합니다. 측정 당시의 실제 결과와 목표 미달은 릴리스 보고서에 기록하며 통과 수치를 고정 보장으로 설명하지 않습니다.

안정 상태 paired 비교는 `schedule:false`로 주기 발신을 끄고 저장·캡처 비용을 측정합니다. 실제 게시·수신과 겹치는 비용은 별도 작업 행으로 보고합니다. 초기 Git 장애 검사는 bare 저장소 경로를 바꾼 즉시 실패이며 지연·무응답 원격 검증을 대신하지 않습니다. 별도 자식 프로세스의 PG/S3 장애 probe는 내부 서버에 연결되지 않으므로 그동안의 저장 표본을 외부 장애 격리 성능으로 주장하지 않습니다. 두 팀의 동시 동기화와 동기화 작업 중 대량 붙여넣기도 별도 근거가 필요합니다.

## 업무 저장소 계약

Node와 Worker의 ordinary API는 `server/storage/`의 도메인 서비스에 repository를 주입합니다. SQLite 구현은 기존 관계형 테이블, prepared statement, task cache와 동기 `transaction()`을 유지합니다. PostgreSQL 구현은 `site_entities`/`site_operations`/`site_audit`/`site_events`를 같은 PG 트랜잭션에서 변경하며 C+P 기준으로 outbox를 작성합니다. API와 공통 명령은 SQL dialect나 `s.tx.query`에 의존하지 않습니다. `DatabaseAdapter`는 이 업무 계약 아래의 sync 상태·트랜잭션 포트입니다.

| 계약                                                     | 실제 명령 범위                                                                                                  |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| TaskBusinessService                                      | 조회/ETag, 셀 배치·서식·재시도, 생성/복제/수정/삭제/복원/순서, 개인 보기                                        |
| DocumentBusinessService                                  | 원본/사본 문서, 연간/사본 메모, 일정 Markdown, 제목/순서/본문 CAS, 이미지 접근 권한과 선택된 저장소의 읽기/쓰기 |
| ReportBusinessService                                    | 사본 생성·복사·이름·행/셀/서식 편집·삭제·revision                                                               |
| CalendarBusinessService                                  | 일정·태그·배치·주간 업무·자동 가져오기·개인 규칙                                                                |
| SettingsBusinessService / FilterBusinessService          | 팀 설정·이름/테마, 셀 종류 변환, 보기/필터 정규화, 공유/개인 필터·선택 상태                                     |
| ControlBusinessService                                   | bootstrap·참조 인물/연도, 프로필, 사용자·팀·멤버십 관리                                                         |
| HistoryBusinessService / AdminHistoryBusinessService     | 팀 이력·복원, 관리자 감사 검색·상세, 사이트 이력 정리                                                           |
| DocumentBrowserBusinessService / TransferBusinessService | 문서 탐색, CSV/XLSX/JSON 내보내기, 실제 업로드 미리보기·적용·재시도                                             |

`createApp()`의 기본값은 SQLite입니다. 서버 설정에서 팀 업무 저장소를 PG로 선택하는 예시는 다음과 같습니다. `env`에는 **서버 전용** 팀 PG binding과 팀 UUID에 대응하는 SYNC_PROFILES를 지정합니다. PG 업무 저장소 선택은 서버 전체에 적용되며 팀별 SQLite/PG 혼합 선택은 지원하지 않습니다. 사용할 모든 활성 팀에 해당 팀 UUID의 `SYNC_PROFILES` 항목과 PG binding을 준비해야 합니다. 프로필이 없는 팀은 `unconfigured`로 분류되고 해당 팀의 업무 요청은 HTTP 409로 거절됩니다. 내부 Node에서는 PG_CONTROL·R2·Git token을 이 업무 저장소 설정에 요구하지 않습니다. 사용자 입력으로 repository나 연결 문자열을 선택하지 않습니다.

```js
import { createApp } from "./server/app.mjs";
import { createPostgresBusinessStorage } from "./server/storage/business-storage.mjs";
const app = createApp({
  db: controlDatabase,
  documentImagesDir: imageDirectory,
  storage: createPostgresBusinessStorage({
    env: {
      PG_TEAM_A: { connectionString: process.env.PG_TEAM_A_URL },
      SYNC_PROFILES: [
        {
          profileId: "team-a",
          teamId: originalTeamUuid,
          databaseBinding: "PG_TEAM_A",
        },
      ],
    },
  }),
});
```

이 예시에서 Node 계정·비밀번호·쿠키 세션·멤버십·시스템 감사 이력은 하나의 SQLite control DB에 남습니다. PostgreSQL에 계정·팀 권한을 복제하지 않으며 SQLite 멤버십 철회는 PG 업무 SSE에도 반영됩니다. bootstrap은 이 control 정보와 선택한 팀 DB의 현재 설정·연도를 조합합니다. 팀 이력 정리는 PG에서 수행하고 관리 감사 기록은 SQLite에 남기며, Node의 정리 미리보기 토큰은 서버 메모리에 보관합니다.

Node PG와 외부 Worker는 같은 `RequestContext.data`와 `capacityLimits(env)`를 사용합니다. 두 호스트 모두 상태·pending **4 MiB**와 공유 엔티티 **12,000개**가 기본 상한이며 `SYNC_MAX_STATE_BYTES`·`SYNC_MAX_ENTITIES`는 더 낮출 수만 있습니다. 쓰기 전 DB 용량 검사와 commit 전 상태 검사에서 이 한도를 적용합니다. 기본 SQLite 업무 경로의 10,000행 성능 시험이나 PG 어댑터 직접 호출 시험은 이 PG 업무 API가 10,000행을 지원한다는 근거가 아닙니다. [용량 범위](CLOUD_SETUP.md#15-postgresql-업무-저장소의-한도와-worker-검증-범위)를 함께 확인합니다.

이미지 변환과 저장소도 DB 엔진과 독립적입니다. 내부 Node는 sharp와 `FileImageStore`, 외부 Worker는 Cloudflare Images와 `R2ImageStore`를 사용합니다. PG 이미지 업로드는 작업 lease를 기록해 정리·연결 교체와 겹치지 않게 합니다. 다른 호스트 저장소가 필요하면 factory의 `imageStoreFor(teamId)` 포트에 `read/has/install/remove/validate/getObject` 계약을 갖춘 구현을 주입할 수 있습니다. Git 실행기 설정은 논리 팀 자료 이관과 별도로 관리합니다. 운영 중 DB를 설정 한 줄로 옮기거나 인증 자료를 자동 복제하는 기능은 아닙니다.

`tests/*-storage-contract.test.mjs`, `task-command-contract.test.mjs`, `task-storage-events.test.mjs`, `ordinary-data-contract.test.mjs`는 같은 서비스에 두 실제 엔진을 넣어 permission/CAS/replay/L/late rollback을 비교합니다. Node PG-only HTTP 검사는 SQLite에 업무/사본을 남기지 않으며 셀·문서·사본·팀 SSE와 멤버십 철회를 검사합니다. PG_CONTROL·R2·Git binding 없이 기본 파일 이미지 업로드→본문 저장→이미지 조회→JSON 반출과 관리 이력 정리도 검증합니다. SQLite 검사에는 반환값이 Promise로 바뀌지 않았는지, 저장 후 별도 연결에서 P와 본문이 동시에 보이는지, 커밋 전 실패에 이벤트가 없는지도 포함됩니다. release 검사에서는 `TEST_PG_BIN`을 지정해 PG skip을 허용하지 않습니다.

## 팀별 외부 설치와 계정 연결

Pages 접속은 `functions/[[path]].js` → `GRAEBOARD_BACKEND` → 기존 Worker의 경로입니다. `public/_routes.json`으로 모든 경로를 Functions에 전달합니다. `tests/pages-gateway.test.mjs`는 누락된 binding의 JSON 503, 헤더·업로드·쿠키·스트리밍 보존을 검사하고, `tests/worker-runtime.test.mjs`는 실제 Pages 번들과 Worker 번들을 workerd Service binding으로 연결해 인증 전 정적 파일/API 차단과 origin 검사를 검증합니다. 팀 사이트 통합 검사는 이 Pages 진입점을 거쳐 SQLite/Git/PostgreSQL 간 구성원·승인·탈퇴 흐름을 확인합니다.

신규 외부 설치는 `PG_SITE` + `SITE_TEAM_ID`와 프로필 하나로 구성합니다. 사내 모든 팀은 SQLite v30에 남고 연결된 팀의 구성원만 `server/sync/directory.mjs`를 통해 별도 Git 브랜치에 게시합니다. `worker/directory.mjs`가 단방향 반영하고 `worker/site-auth.mjs`가 최초 팀장 연결·계정 선택·팀장 승인·접속 세션을 처리합니다. 기존 분리형 `PG_CONTROL` 경로는 호환용으로 유지합니다.

`tests/team-site.test.mjs`는 실제 SQLite·Git·PostgreSQL과 Worker fetch를 연결해 팀장 연결 설정, 다른 팀 제외, 승인 전 차단, Google 신원에 묶인 세션, 팀원 추가/역할 변경/탈퇴, site migration 롤백·재실행·기존 team 보존, 백업 v2의 승인 보존·세션 제외를 검사합니다. `tests/browser/data-sync.spec.ts`는 계정 선택·대기·승인 후 접속과 팀장 승인 화면을 확인합니다. release 검증은 `TEST_PG_BIN=/경로/postgresql/bin npm run test:postgres`, 프런트엔드/Worker 빌드, 세 브라우저의 해당 흐름을 사용합니다. 실제 Google/Cloudflare/Supabase 배포 검증은 별도입니다.
