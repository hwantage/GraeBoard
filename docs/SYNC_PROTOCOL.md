# 팀 Git 동기화 규약 v1·v2

[설치 안내](CLOUD_SETUP.md) · [데이터 형식](DATA_FORMAT.md) · [개발 안내](DEVELOPMENT.md)

동기화는 팀별 private GitHub 저장소의 `sync-v1` 브랜치에 확정된 변경을 같은 순서로 재생합니다. 내부 저장 응답과 같은 서버의 SSE는 로컬 DB 커밋을 기준으로 하며 Git 게시를 기다리지 않습니다.

## 상태와 원자성

| 상태 | 저장 내용                                          | 공유 여부               |
| ---- | -------------------------------------------------- | ----------------------- |
| C    | 적용한 Git head까지의 엔티티·삭제 표식·영수증·충돌 | 공유                    |
| P    | 로컬에 저장한 불변 변경 명령과 의존성              | 게시 전에는 로컬        |
| L    | 이 사이트에서 제외한 연도·문서                     | 사이트 로컬             |
| U    | `project(C,P)` — 제외 전 사용자 변경 반영본        | 계산 결과               |
| V    | U에 L을 적용한 앱 제공본                           | 사이트마다 다를 수 있음 |

업무 저장과 outbox는 같은 트랜잭션에 기록합니다. 수신 적용에서는 C·receipt·해당 op의 ACK·남은 P의 재투영·cursor를 함께 커밋합니다. GitHub 응답만 보고 outbox를 삭제하지 않습니다. 정리 때문에 V에서 사라진 항목을 공유 삭제로 해석하지 않으며, 일반 저장의 의도는 U를 기준으로 적용합니다.

내부 SQLite는 동기 트랜잭션을 사용합니다. PostgreSQL은 동일 client에서 `BEGIN`부터 모든 쿼리를 await한 뒤 commit/rollback합니다. DB 트랜잭션을 연 채 GitHub·R2 HTTP 응답을 기다리지 않습니다. 내부 호스트는 `server/`, 외부 저장소는 `worker/storage/`, 순수 상태 계약은 `shared/`와 `server/sync/`에 있습니다.

## 식별자와 명령

`repoId`와 `teamId`는 저장소 신원입니다. `bootstrapId`는 초기 엔티티 토큰을 고정하고, DB 밖 `installationId`는 설치를 구분합니다. `writerEpoch`는 새 발신 세대이며 복구된 이전 명령의 ID나 payload를 다시 작성하지 않습니다. `localSeq`는 로컬 outbox 순서이며 전역 식별자가 아닙니다.

v1 명령은 `protocol:1`, `reducer:1`, `repoId`, `teamId`, `opId`, `writerEpoch`, `actorRef`, `createdAt`, `dependsOn`, `changes`, `objects`를 포함합니다. 변경의 key는 문자열 배열입니다. `generation`, `baseVersion`, `action`, `base`, `desired`, `fields`로 어떤 세대·필드에 대한 변경인지 명시합니다. 생성·편집·삭제·복원을 구분합니다.

`opId` 하나는 영구히 하나의 payload를 가리킵니다. 같은 ID·같은 해시는 최초 receipt를 반환하며 같은 ID·다른 payload는 오류입니다. 제출 시각은 표시용이며 충돌 승패를 결정하지 않습니다. JSON은 객체 키를 정렬하고 배열 순서를 유지하며 유한·안전 범위 숫자와 UTF-8을 사용합니다. null·필드 없음·빈 문자열·빈 배열을 구분합니다.

receipt에는 `opId`, `payloadHash`, `result`, `conflictId`, `outputTokens`를 보존합니다. 같은 head의 C 해시에는 개인 보기·계정 권한·로컬 revision·P·L을 넣지 않습니다. 따라서 L이 다른 사이트의 V와 이미지 집합이 달라도 C는 같아야 합니다.

## 공유 범위

팀 이름·업무 설정, 사람의 UUID·표시 이름, 업무, 셀, 공통 서식, 문서, 원본·사본 메모, 사본 표, 개인·공용 일정, 태그, 주간 할 일·가져오기 기준, 공용 필터, 참조 문서 이미지를 공유합니다. 사본 표는 압축 BLOB 바이트 대신 정규화한 내용으로 다루되, 그 내용은 저장 BLOB·HTTP 응답과 같은 공유 사전 형태(`{ $styles, $formats, $data }`)입니다. 업무마다 반복되는 공통 서식 규칙과 셀 서식을 한 번만 싣고, 키를 정렬한 뒤 번호를 매겨 같은 내용은 어느 사이트에서 만들어도 같은 바이트가 됩니다. 사전이 필요 없는 작은 사본은 평문 그대로이며, 이 변경 전에 기록된 평문 사본 명령·기준본도 계속 읽습니다. reducer의 base·현재값 비교는 두 형태를 풀어 내용으로 수행하므로 기존 평문 기준본의 첫 편집·삭제가 충돌로 바뀌지 않습니다. 검증·v2 행 분할·사내 반영·외부 `DataSession` 읽기만 사전을 풀고, 앱 코드는 두 사이트 모두 풀린 객체를 다룹니다. 본문 참조는 최신 관계형 참조를 사용합니다.

업무 `sync-v1`에는 사용자 비밀번호·세션·로그인 이메일·활성 여부·시스템 역할·팀 권한, 개인 보기·개인 필터·현재 필터·캘린더 요일 설정, 자격증명, 기존 감사 로그·API 재시도 캐시를 포함하지 않습니다. 해당 팀의 이름·이메일·활성 상태·팀 역할은 아래 별도 구성원 브랜치로 내부에서 외부에 전달합니다. 업무의 표시용 사람 참조 자체는 로그인 권한을 주지 않습니다.

## Git 브랜치별 역할

모두 팀 전용 비공개 **데이터 저장소**의 브랜치이며 앱 소스·배포 브랜치와 분리합니다.

| 브랜치 | 전달 방향 | 내용 |
| --- | --- | --- |
| `sync-v1` | 내부 ↔ 외부 | 업무·문서·메모·이미지의 확정 이력 |
| `sync-directory/<내부 설치 UUID>` | 내부 → 외부 | 해당 팀 구성원의 UUID·이름·이메일·활성 상태·팀 역할 |
| `sync-setup/<내부 설치 UUID>` | 내부 → 외부 | 팀장 연결 키 해시·유효기간·폐기 상태 |
| `sync-setup-status/<외부 설치 UUID>` | 외부 → 내부 | 키의 반영·사용 확인, Google 신원 제외 |
| `sync-status/<설치 UUID>` | 각 사이트 → 상대 | 적용 head·모드·확인 시각 |

비밀번호·내부 세션·전체 시스템 관리자 권한은 전달하지 않습니다. Google 신원·외부 연결 승인·외부 접속 세션은 외부 DB에만 저장합니다. 키 원문을 Git에 넣지 않으며 [연결 키 저장 계약](DATA_FORMAT.md#팀별-외부-사이트-계정과-승인)을 따릅니다.

## 결정적 병합과 충돌

현재 공유값이 base와 같으면 desired를 적용합니다. desired가 base 또는 current와 같으면 이미 있는 내용을 유지합니다. 독립 필드는 병합하고, 같은 필드 그룹이 서로 다르게 바뀌면 먼저 확정된 공유값을 유지합니다. 일정 기간·배치, 순서 있는 태그 목록, 팀 속성 정의, v1 사본 표처럼 함께 유효해야 하는 묶음을 임의 leaf로 나누지 않습니다.

Markdown은 같은 삽입점의 다른 삽입과 겹치는 변경을 충돌로 보관합니다. 비겹침 변경만 병합하며 계산량 상한을 사용합니다. 실행 환경의 벽시계 속도에 따라 결과가 달라지는 timeout 판정을 사용하지 않습니다.

하나의 명령은 전부 적용되거나 전부 보류됩니다. 결과는 `applied`, `noop`, `conflict`, `dependency-blocked` 중 하나입니다. 충돌한 선행 명령을 바탕으로 작성한 후속 입력도 보존하며 공유 원본에 독립 적용하지 않습니다. 기존 conflict receipt를 중복 수신 때 noop으로 바꾸지 않습니다.

충돌 보관함의 해결은 최신 공유 head와 확인한 op frontier를 기준으로 새 명령을 만듭니다. 현재 내용 유지·제출 내용 적용·직접 편집을 선택할 수 있습니다. 해결하는 동안 더 생긴 후속 입력은 해결 대상으로 자동 포함하지 않습니다. 삭제된 엔티티의 늦은 편집은 자동 복원하지 않으며 명시 복원은 새 세대를 사용합니다.

## Git 전달과 적용 확인

내부는 앱 전용 저장소의 Git CLI를, 외부 Edge는 GitHub Git Data API를 사용합니다. 발신자는 관찰한 head 하나만 부모로 후보를 만들고 강제 갱신 없이 게시합니다. 경합하면 최신 head를 받아 동일한 불변 명령으로 다시 계산합니다. push 응답이 사라지면 원격 이력과 receipt를 대조합니다.

업무 이력과 별도로 `sync-status/<installationId>` 브랜치에 적용한 canonical head·사이트·writer 세대·모드·확인 시각을 게시합니다. 상태 브랜치는 reducer 입력이 아니며 상태 갱신을 보고 다시 상태를 게시하지 않습니다. 상태의 ancestry와 처리 결과가 맞을 때만 반대쪽 적용을 확인합니다. 과거 확인은 현재도 내부 서버가 실행 중임을 보장하지 않습니다.

내부 기본 수신 주기는 약 60초이고 외부는 gateway가 Edge를 호출하는 1분 Cron입니다. 내부 저장 후에는 약 1.5초 뒤 게시를 예약합니다. 외부는 첫 미전송 저장부터 2초를 모으고 자동 게시 시도 사이에 최소 5초 간격을 둡니다. 외부 진입·포커스 복귀·편집 시작의 최신화는 지연을 줄이는 보조 수단이며 optimistic revision 검사와 충돌 처리를 대체하지 않습니다. 외부 게시 주기가 이미 미전송 목록을 읽은 뒤 들어온 마지막 저장은 그 주기에 포함되지 않을 수 있습니다. 해당 P는 보존되고 후속 저장 요청 또는 다음 Cron에서 다시 게시를 시도합니다. 진행 중 게시가 끝났다는 이유만으로 추가 주기를 자동 예약하지 않습니다.

Git 수신으로 상대 DB가 바뀌면 그 사이트의 기존 SSE 경로가 열린 표·문서·메모에 전달합니다. 사이트 간 브라우저를 직접 연결하지 않습니다. 같은 사이트 SSE 지연과 Git 전달 지연은 별도로 측정합니다. 외부 화면 상단의 내부망 반영 완료는 내부 서버의 적용 상태이며 모든 브라우저의 렌더링 완료 응답이 아닙니다. 문서 본문의 버전과 SSE 재연결 커서는 [실시간 동기화 계약](DATA_FORMAT.md#실시간-동기화)을 따릅니다.

## 최초 게시·checkpoint·복구

최초 게시에서는 캡처를 먼저 켜고 일관된 snapshot과 outbox cutoff를 고정합니다. 초기 bundle에 포함된 변경은 중복 적용하지 않으며 이후 변경은 P에 남깁니다. 팀 신원·객체·이미지를 모두 검증한 뒤 새 외부 팀을 공개합니다. 이미 업무가 있는 외부 팀에 초기 snapshot을 덮지 않습니다.

checkpoint는 정확한 canonical head의 C와 receipts·충돌·객체를 보관합니다. 이후 커밋을 재생하며 실행 중인 사이트의 P나 L을 지우지 않습니다. checkpoint를 만들었다는 이유로 원격 이력·receipts를 자동 폐기하지 않습니다.

새 사이트 합류와 관리자가 이전 실행 종료를 확인한 명시 복구는 검증된 checkpoint에서 시작할 수 있습니다. 이 경로의 신뢰 기준은 설정된 비공개 저장소에 인증된 작성자입니다. 압축/해제 바이트 해시, snapshot 형식·개수·팀/저장소/엔티티 식별자, 기준 head와 원격 ancestry를 검사한 뒤 원자적으로 투영하지만 checkpoint 이전 reducer 이력 전체를 독립 재생해 재계산하지는 않습니다. 저장소 쓰기 권한을 가진 작성자의 악의적·잘못된 snapshot까지 재생으로 증명하는 경로는 아닙니다. 정상 실행 중인 사이트의 증분 수신은 각 커밋을 검증·재생하며 checkpoint로 건너뛰지 않습니다.

관리자는 활성 연결에서 `POST /api/teams/:id/sync/checkpoint`로 현재 공유본의 checkpoint를 만들 수 있습니다. 작업 소유권을 획득한 뒤 고정 head를 기준으로 작성하며 일시정지·복구·정리 중 게시하지 않습니다. snapshot은 `snapshots/*.json.gz`의 gzip JSON이며 압축 바이트 해시와 해제한 C의 결정적 해시를 각각 검증합니다. 기존 비압축 JSON도 읽을 수 있습니다.

현재 원격 head가 마지막 적용 head의 후손이 아니거나 형식·해시·팀 참조가 잘못되면 마지막 정상 cursor를 보존하고 복구 점검으로 전환합니다. restore·다른 설치의 DB 복사도 자동 발신을 막습니다. 원격 처리 여부·미전송 입력을 확인한 뒤 새 writer 세대로 재개합니다.

## 이미지와 사이트 정리

문서 이미지는 팀 UUID·SHA-256 경로의 WebP입니다. 내부 파일 폴더와 외부 R2에 제공하고 Git을 통해 교환합니다. 수신한 바이트는 해시를 검증하며 다시 인코딩하지 않습니다. 다른 팀 이미지와 계정 아바타는 전달하지 않습니다. 이미지 의존성은 문서 Markdown의 실제 이미지 문법(참조형 이미지 포함)에서 추출합니다. 셀 값·제목·태그·필터의 일반 문자열에 이미지처럼 보이는 주소가 있어도 공유할 수 있으며, 기존 미전송 명령의 ID·내용·의존성을 다시 쓰지 않습니다. 실제 문서 이미지의 다른 팀 주소는 저장 트랜잭션 전체를 거절합니다. 반면 같은 팀 이미지의 **파일이 없는 것**은 저장·사본 만들기·게시·수신 어느 것도 멈추지 않습니다(2026-11-02). 게시할 때 파일이 없으면(외부 R2·내부 폴더) 그 이미지 없이 커밋하고, 수신할 때 Git에 없거나 해시가 맞지 않으면 설치하지 않고 받습니다. 문서는 그 이미지를 **이미지 없음**으로 표시하며, 사용자가 지우고 다시 붙여넣으면 새 주소로 저장·동기화됩니다. 건너뛴 이미지는 `GraeBoard image skipped` 경고로 기록합니다. R2·네트워크 장애처럼 없는지 확인할 수 없는 오류는 지금처럼 실행을 멈추고 다음 주기에 다시 시도합니다.

Node의 일반 문서 저장은 앱 소유의 별도 parser Worker에서 현재 본문과 새 본문의 이미지 구문을 준비합니다. Git 작업과 큐를 공유하지 않으며, 작업 수·입력 크기·대기 시간을 제한합니다. 준비 후 세션·소속·권한과 현재 본문/revision을 다시 확인하고, 정확히 일치하는 두 본문의 추출 결과만 짧은 동기 쓰기 트랜잭션 동안 고정합니다. 팀 이미지 권한·파일 존재와 capture의 operation 검증은 그대로 실행합니다. Worker 오류·시간 초과·과부하에서는 해당 작업만 동기 parser로 보완합니다. 다른 대기 작업을 일괄 취소하지 않습니다. 준비 중 본문이 바뀌면 revision 검증으로 거절하며 본문·감사·P를 함께 보존합니다. 원격 operation·base·checkpoint의 검증은 이 로컬 준비 경계를 사용하지 않습니다.

공통 파서의 최근 추출 캐시는 프로세스별 최대 8개와 문자열·URL 계산량 2MiB로 제한됩니다(AST나 권한 성공을 저장하지 않음). 30초 만료는 다음 조회·삽입 때 정리하는 논리적 만료이며, 유휴 30초 뒤 문자열을 즉시 지우는 타이머는 아닙니다. 저장 명령의 고정 결과는 커밋 성공·실패 때 해제하며 최근 캐시의 만료·다른 문서에 의한 퇴출과 독립적입니다.

정리는 선택 사이트·팀의 유지보수 작업입니다. 미리보기 token의 범위·revision을 재검사하고 L과 작업 manifest를 보존한 뒤 파일을 묶음 처리합니다. 다른 문서·사본·P·충돌이 참조하는 이미지, 진행 중 업로드, 검증된 원격 보관본이 없는 파일은 보호합니다. 백업·복원·프로필 전환과 같은 팀의 작업 경계를 공유합니다.

정리·백업 복원은 L로 제외되지 않은 삭제 표식과 로컬 감사 이력이 참조하는 기존 이미지도 보호합니다. 삭제 표식만 남아 있어도 보호 기간이 자동 만료되지는 않습니다. 로컬 감사 이력은 Git으로 공유하지 않으며, 과거 이력의 유효한 같은 팀 주소는 보수적으로 보호하고 다른 팀 주소는 무시합니다. Git 수신의 설치 집합은 이 보호 집합과 다릅니다. 현재 표시할 살아 있는 문서와 P·미해결 충돌에 필요한 이미지만 설치하고, 삭제 표식·감사 이력만의 이미지나 L로 제외된 문서 이미지는 자동 재설치하지 않습니다. 단, 과거 커밋을 순서대로 적용할 때 당시 살아 있던 문서의 이미지는 그 단계에서 설치될 수 있습니다. L이 바뀐 문서 정리·복원은 task snapshot ETag를 전진시키고 열린 구독을 무효화합니다. 이미지 파일만 정리할 때는 셀 snapshot을 reset하지 않습니다.

SQLite 정리의 감사 이력 조회는 쓰기 트랜잭션 밖에서 100행씩 읽고 실행권을 양보합니다. 준비한 참조·revision을 계산한 뒤 짧은 쓰기 트랜잭션에서 같은 연결의 변경 횟수와 다른 연결의 data version을 재검사합니다. 이 fence는 팀 단위가 아닌 **같은 DB 파일 전체**의 쓰기를 감지하므로 다른 팀의 편집·세션 갱신에도 준비가 무효화될 수 있습니다. fence가 바뀐 경우에만 전체 참조와 revision을 새로 준비하며, 잠금 획득까지 합쳐 최초 시도 포함 최대 3회 시도합니다. 계속 바뀌면 서버의 다른 작업으로 준비를 마치지 못했다는 409를 반환하고 잠시 후 재시도하도록 안내합니다. 팀 자료·이미지 참조가 실제로 바뀌어 미리보기 revision이 달라진 경우에는 자동 재시도하지 않고 기존 409로 새 미리보기를 요구합니다. 미리보기 만료·권한·작업 소유권 거절도 재시도 대상으로 삼지 않습니다. 정리 guard를 활성화하기 전에는 파일을 삭제하지 않습니다.

새 사본은 생성한 사이트의 V에서 제공되는 자료를 복사해 새 ID로 공유합니다. 숨긴 연도·문서는 새 사본에서 제외하되 원본과 기존 사본의 숨긴 항목은 삭제하지 않습니다. 기존 자료를 교체하는 일반 편집·순서 변경과 새 사본 생성을 구분합니다.

명시 복원은 필요한 파일을 먼저 검증·설치하고 L을 해제합니다. 로컬 revision은 이전 high-water보다 커져야 하며 오래된 저장 요청을 다시 유효하게 만들지 않습니다. 공유 기준본의 본문은 DB에 남으므로 정리를 전체 DB 용량 회수로 설명하지 않습니다. Git 이력 삭제·force push·자동 GC는 이 기능에 포함하지 않습니다.

## 검증 기준

실제 API 캡처, SQLite/PG 저장 계약, CLI/API Git 경합·응답 유실·재시작, 원자적 충돌·연속 초안, genesis/checkpoint, tenant·Access 격리, 이미지·L 정리·복구와 열린 브라우저 SSE를 함께 검증합니다. outbox를 테스트에서 직접 채운 것만으로 실제 API 캡처를 검증했다고 판단하지 않습니다.

성능은 같은 장비·합성 데이터·동시 세션에서 미연결과 활성 상태를 비교합니다. 초기 목표는 내부 저장 p95 증가 10% 이내와 commit 후 다른 화면 반영 p95 1초 이내입니다. Git/R2/외부 DB 장애 및 대량 수신·백업 중 결과도 따로 기록하며 과거 측정 수치를 현재 릴리스 결과로 재사용하지 않습니다.

`npm run performance:sync`는 기존 대량 처리 측정과 C11 보강 시나리오를 함께 실행합니다. C11만 다시 측정할 때는 `SYNC_PERF_REVIEW_ONLY=1 SYNC_PERF_OUTPUT=docs/validation/sync-review-performance.json npm run performance:sync`를 사용합니다. 코드 변경·다른 성능 검사·브라우저 빌드를 멈춘 상태에서 실행하며, 원시 시간·장비·소스/측정기 해시와 통과 여부를 JSON에 남깁니다.

C11은 연결 유휴 저장(세 번의 순서 교차 비교), 연결·미연결 2,000셀 배치, 연결 DB의 미연결 팀, 사용자 1,000명, 연결 사본 생성·셀 편집, retention 활성 조회, acknowledged outbox 50,000행 상태 폴링, 원격 업무 메타데이터 수신 시 30개 HTTP SSE 클라이언트와 30개 실제 Chromium 앱의 재조회 수를 검사합니다. 사본은 실제 두 사이트의 v1→v2 전환을 거쳐 업무 1,000개·문서 100개를 유지합니다. C11 데이터는 업무당 기본 속성 3셀과 배치로 추가되는 일정 1셀이고, 기존 대량 측정의 업무 10,000개·60주·30% 채움 설정은 그대로입니다. 사본 셀 편집 목표는 모든 측정 요청 100ms 미만입니다. 실제 브라우저 검사는 유휴 저장 측정이 끝난 뒤 실행합니다. 초기 로딩 후 페이지 시계를 멈추고 7초 주기보다 짧게 진행하여 정기 polling과 구분되는 SSE 유발 재조회 수와 화면의 업무 순서를 확인합니다. 별도로 256KiB 문서의 v2 병합 경계에서 Node CPU 시간을 측정하며 실제 Edge 실행 시간으로 해석하지 않습니다.

## PostgreSQL 업무 저장소와 외부 실행 자원 경계

프로토콜의 논리 형식과 별도로 PostgreSQL 팀 업무 저장소는 외부 Edge의 `RequestContext.data`·`capacityLimits(env)`를 통해 업무·충돌·pending 용량과 공유 엔티티 수를 셉니다. 이 둘에는 기본 상한이 없고, 운영자가 `SYNC_MAX_STATE_BYTES`·`SYNC_MAX_ENTITIES`를 지정한 경우에만 검사합니다(2026-11-01 이전 32MiB·50,000개). receipt는 16MiB 별도 예산(12MiB 경고)이며 과거 초과 상태의 조회·반출은 막지 않고 새 저장·게시는 사전에 거절합니다. 내부도 같은 receipt 예산과 명령 상한을 적용하지만 외부 업무 용량 한도는 적용하지 않습니다. 외부 Edge 동기화는 원격 바이트·압축 해제 snapshot·reducer 결과도 검사하며 초과 시 `EXTERNAL_SYNC_CAPACITY`로 마지막 정상 cursor와 불변 outbox를 보존합니다. 거절은 완료·부분 성공으로 처리하지 않습니다. 기본 SQLite 업무 경로의 대용량 성능 결과는 외부 Edge의 지원 규모를 뜻하지 않습니다.

외부 P는 한 가지 경우에만 기존 행을 바꿉니다. v1에서 사본 수정 명령은 사본 전체를 base·desired로 담으므로, 편집 중 자동 저장마다 명령이 쌓이면 저장할 때의 P 재생과 Cron 게시가 쌓인 수만큼 무거워집니다. 그래서 새 저장이 사본 하나만 수정하고, P의 마지막 행이 같은 사본만 수정한 `pending` v1 명령이며, 같은 writer epoch이고, **동기화 lease를 아무도 갖지 않을 때** 그 행을 지우고 그 명령의 base에서 새 결과까지의 명령 하나를 새 opId로 넣습니다(`DataSession.replaceableOperation`). 결과가 그 base와 같으면 명령을 남기지 않습니다. lease 획득과 저장은 같은 팀 advisory lock 안에서 실행되므로, 게시 중인 실행이 읽은 행은 바뀌지 않습니다. lease가 만료된 채 멈췄던 게시가 이전 명령을 이미 Git에 올린 드문 경우에는 교체한 명령이 동시 수정 충돌로 보존됩니다. 이력(`site_audit`)과 재시도 기록은 요청마다 남습니다.

`tests/worker-sync-integration.test.mjs`는 실제 SQLite 앱과 PostgreSQL 외부 API가 같은 bare Git에 CLI와 GitHub Data API로 참여하여 엔진 간 자료·이미지·경합·복구를 검증합니다. 이전 전체 Worker의 workerd 전용 용량 검사는 제거했으며 Cloudflare 전달·자원 경계는 `tests/edge-gateway.test.mjs`로 검사합니다. 이 검사들은 현재 운영 경로인 Supabase/Deno의 성능 측정과는 다릅니다. `tests/team-site.test.mjs`는 Pages → gateway → Edge handler → 실제 PG 경로도 검사하며, Deno 실행은 실제 함수 배포에서 별도로 확인합니다. GitHub/DB/R2/Images의 클라우드 운영 지연을 측정한 것으로 설명하지 않습니다. 제한과 요금제 근거는 [설치 안내의 용량 범위](CLOUD_SETUP.md#15-실행-한도와-검증-범위)에 기록합니다.

## 팀 구성원 단방향 브랜치

계정 권한은 업무 C/P/L에 포함하지 않습니다. 신규 팀 사이트는 `sync-directory/<internalInstallationId>`의 `directory.json` v1로 해당 팀의 `id/name/email/active/role`만 내부에서 게시합니다. 최대 1,000명·512KiB, 팀·저장소·설치 UUID와 허용 필드를 검증하고 CAS로 게시합니다. 외부는 직전 head의 후속 이력만 반영합니다. 계정 승인·Google 신원·선택 세션은 외부에만 저장하며 업무 reducer가 변경할 수 없습니다. 철회는 다음 성공한 구성원 수신 시 적용합니다. [계정 형식](DATA_FORMAT.md#팀별-외부-사이트-계정과-승인)을 참고합니다.

## 버전 전환과 저장 경계

기존 `sync-v1` 브랜치·v1 manifest·명령의 canonical 필드와 해시는 유지합니다. 양쪽에 v2 reader를 설치한 뒤 정확한 v1 head/hash·양쪽 일시정지·미전송과 미해결 충돌이 0인 조건에서만 명시 전환합니다. 전환 이벤트는 검증된 v1 백업 snapshot과 결정적으로 분해한 v2 snapshot을 함께 보존합니다. v2에는 `protocol`/`[]` 표식 `{version:2,reducer:2}`와 `reportTask`·`reportCell`이 추가됩니다. 기존 사본의 모든 행·셀·서식·순서·문서 참조를 보존하고 앱 응답에서는 다시 기존 사본으로 조합합니다. 같은 원본 task ID를 사용해도 사본 ID를 키에 포함하므로 원본 셀과 섞이지 않습니다.

v2 사본의 부모 `report`에는 행 배열을 넣지 않습니다. `reportTask` 키는 `[reportId, taskId]`이고 `{data, index}`에 셀을 제외한 행 정보와 순서를 보관합니다. `reportCell` 키는 `[reportId, taskId, cellKey]`이고 `{data}`에 값·서식·로컬 셀 버전을 보관합니다. 서로 다른 셀 변경은 독립적으로 병합합니다. 행의 `data`는 필드별 3-way 병합을 하고, 두 셀 편집이 함께 바꾸는 `updatedAt`만 두 문자열 중 코드포인트 비교로 큰 값을 선택합니다. 실제 실행 시각이나 locale에 따른 정렬은 사용하지 않습니다. 같은 셀의 다른 변경과 같은 행 메타데이터 필드의 다른 변경은 기존 제출 원문을 충돌로 보관합니다.

삭제된 사본·행의 내용을 조합할 때는 부모와 같은 삭제 명령에서 생긴 자식 tombstone만 포함합니다. 따라서 먼저 삭제한 행·셀은 나중에 사본 전체를 삭제하고 복원해도 다시 나타나지 않습니다. v1에서 이미 삭제된 사본을 전환할 때는 해당 사본에 보존된 본문만 같은 삭제 그룹으로 옮깁니다. 명시 복원은 새 세대를 사용하며 과거 삭제 세대의 지연 편집을 적용하지 않습니다.

v2 부모 `report`의 `data`는 행 배열이 없으므로 평문 그대로이고, `reportTask`·`reportCell`도 행·셀 단위 평문입니다. 행 메타데이터의 `formatting`은 v1과 같이 행마다 들어가므로, v2 전환 전에 행별 서식 중복을 줄이는 방안을 별도로 정해야 합니다. 앱 응답과 논리 이동의 `site_entities`는 기존 `report.data.tasks` 형식을 v1과 같은 공유 사전 형태로 조합합니다. 공유 기준본의 `sync_entities`·receipt·충돌·P는 v2 형식을 그대로 보존합니다. 논리 이동과 백업 v3 복원은 프로토콜을 다시 v1으로 바꾸지 않으며, 복구·재연결·충돌 해결이 만드는 새 명령도 현재 marker의 버전을 사용합니다.

전환 실행권은 기존 lease의 `upgrade:` 소유자로 구분합니다. 이 lease가 유효한 동안 해당 팀의 새 업무 저장은 HTTP 409로 거절하고 입력을 보존합니다. 일반 활성 동기화의 lease는 이 제한을 적용하지 않습니다. 게시 직전과 최종 DB 커밋에서도 기준 head/hash·P/held·미해결 충돌·작업 경계를 확인하며, 전환 수신 후에도 양쪽은 일시정지 상태를 유지합니다.

v1 이력은 기존 차이 탐색 상한 20,000을, v2는 상한 2,000을 사용합니다. 기기 시간으로 병합 여부를 결정하지 않으며 상한을 넘은 base/current/desired를 모두 충돌에 보존합니다. 이전 reader는 v2 전환 이벤트와 v2 checkpoint 모두에서 cursor를 전진시키지 않습니다. 전환 명령과 양쪽이 일시정지한 상태의 수신 절차는 [운영 안내](OPERATIONS.md#동기화-v2-명시-전환)에 있습니다.

이벤트 파일은 32MiB 이내입니다(2026-10-30 이전 4MiB). 사본 복사처럼 나눌 수 없는 명령 하나가 들어가도록 정한 값입니다. 명령 하나는 봉투 여유 1KiB와 구분자 1바이트를 제외한 크기 이내인지 저장 시점에 검증합니다. 사본 명령의 크기는 [공유 범위](#공유-범위)의 공유 사전 형태로 계산하므로 공통 서식 규칙이 업무마다 반복되어 커지지 않습니다. 큰 묶음은 여러 이벤트로 나눠 게시하고, 단일 명령이 상한을 넘으면 업무·감사·outbox를 모두 롤백하고 400으로 거절합니다. snapshot은 압축·해제 각각 64MiB 상한과 해제 후 receipt 예산(업무 상한은 지정한 경우)을 검사합니다. receipt 원문은 checkpoint 후에도 보존하고 stateHash에 계속 포함하므로 전체 해시 계산은 누적 이력에 비례합니다. 외부 Edge는 상대가 `sum-1`을 알리면 전체 해시 대신 바뀐 기록만 갱신하는 상태 합([데이터 형식](DATA_FORMAT.md#상태-합-sum-1))을 씁니다.

상태 조회는 마지막 local_seq 행과 일반 인덱스를 사용합니다. 오래된 acknowledged outbox와 SSE 이벤트 정리는 기본으로 자동 실행하지 않으며 최신 행·pending/held·미해결 충돌·의존성·불일치 hash를 보호합니다. receipt·tombstone·sync_objects·Git 이력은 삭제하지 않습니다. 이전 SSE 커서는 최신 snapshot으로 복구합니다.
