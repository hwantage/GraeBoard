# 데이터베이스 변경 지침

[프로젝트 작업 규칙](../AGENTS.md) · [데이터 형식](DATA_FORMAT.md) · [운영 안내](OPERATIONS.md)

DB 스키마·영속 저장 형식·기존 데이터의 일괄 처리를 변경할 때 이 지침을 따른다. 현재 저장 구조와 지원 버전은 [데이터 형식과 호환성](DATA_FORMAT.md#버전과-운영-호환성)을 확인한다.

## 사용자 승인

변경 계획을 제시하고 **사용자의 명시적 승인을 받은 뒤 관련 구현과 실행을 진행한다.** 일반적인 기능 개선 요청을 DB 변경 승인으로 간주하지 않는다.

승인 대상은 다음과 같다.

- 테이블·컬럼·인덱스·제약조건·트리거 등 스키마의 추가·수정·삭제
- 저장된 JSON·압축 BLOB·문서 및 이미지 참조 등 영속 형식이나 해석 규칙의 변경
- 기존 데이터의 일괄 변환·보정·이관·삭제·초기화
- `SCHEMA_VERSION`·`PRAGMA user_version` 변경, 마이그레이션 도입·수정
- 백업·복구의 지원 버전이나 데이터 보존 방식 변경

승인 요청에는 다음 내용을 포함한다.

1. 변경 이유와 기존 구조를 유지하는 대안
2. 실제 운영 버전과 목표 버전, 변경할 파일·스키마·저장 형식·호출 경로
3. 기존 데이터·권한·이력·사본·문서·이미지에 미치는 영향과 보존 방법
4. 버전별 변환 방법, 배포 순서, 점검 시간과 쓰기 중단 여부
5. 백업·검증·실패 복구 계획과 접속 재개 후 데이터 손실 가능성

승인 전에는 관련 코드·버전 번호를 바꾸거나 변환을 실행하지 않는다. 읽기 전용 조사, 변경안 작성, 임시 DB를 사용하는 기존 테스트는 진행할 수 있다. 승인 요청 시 이 문서의 승인 규칙을 근거로 설명한다.

이미 승인받은 구체적인 범위는 다시 묻지 않는다. 새로운 스키마 변경이나 데이터 삭제 등 범위가 확대되면 추가 승인을 받는다. 구현 승인과 운영 실행 승인은 구분하며, 운영 적용에는 대상 환경·DB 경로·작업 범위가 포함된 승인이 필요하다. 기존 승인이 실행까지 포함하면 재확인하지 않는다.

기존 스키마·저장 형식·데이터 호환성을 유지하는 화면 변경과 기존 API의 정상적인 저장 동작은 승인 대상이 아니다. 작업 중 DB 변경이 필요해지면 해당 부분의 구현 전에 승인을 받는다.

## 마이그레이션

- 실제 운영 DB 버전을 읽기 전용으로 확인한다. 저장소 버전과 같다고 추정하지 않으며, 운영에서 사용하지 않은 과거 개발 버전의 지원 범위는 별도로 정한다.
- 현재 구현의 지원 버전과 변환 경로를 확인한다. 존재하지 않는 업그레이드 명령이나 자동 변환을 전제로 설명하지 않는다.
- 스키마·영속 형식 변경에는 지원 대상 DB를 목표 버전으로 변환하는 코드를 포함한다. 버전 숫자나 검사만 바꾸거나 새 DB·빈 `DB_PATH`로 데이터를 비워서 업데이트하지 않는다.
- 버전별 변환을 순서대로 보관해 중간 릴리스를 건너뛴 DB도 필요한 단계를 모두 거치게 한다. 배포한 변환은 수정·삭제하지 않고 후속 변환을 추가한다.
- 각 단계의 스키마·데이터 변경, 적용 이력, 버전 갱신은 같은 트랜잭션으로 처리한다. 실패한 단계는 롤백하고 재실행 시 완료한 단계는 중복 적용하지 않는다.
- 이력에는 버전·시각·체크섬 등을 기록한다. 변환 누락·이력 불일치·코드보다 새 버전·지원 경로가 없는 구버전은 데이터를 보존한 채 거부한다.
- 신규 설치와 기존 DB 업그레이드를 구분한다. `CREATE TABLE IF NOT EXISTS`가 기존 컬럼을 변경한다고 가정하지 않는다. 버전 0이어도 기존 사용자 테이블이 있으면 빈 DB로 취급하지 않는다.
- 가능한 경우 컬럼·테이블 추가와 기존 값 채우기를 먼저 하고, 삭제·축소는 보존·호환성 검증 후 별도 단계로 수행한다.
- 마이그레이션은 배포의 명시적 단계로 한 번에 하나만 실행한다. 일반 서버 시작에서는 버전·적용 상태를 검사하고 승인받지 않은 운영 DB 변환을 자동 실행하지 않는다.

## 검증

- 합성 데이터를 넣은 이전 버전 DB로 단일·여러 단계 업그레이드, 재실행, 중간 실패·롤백·재시도, 미지원 버전 거부를 검증한다.
- 신규 설치와 변환 결과의 테이블·컬럼·인덱스·제약조건·트리거가 일치하는지 확인한다.
- `PRAGMA integrity_check`와 `PRAGMA foreign_key_check`를 모두 검사한다.
- 영향받는 계정·권한·업무·셀 값과 버전·서식·필터·캘린더·이력·사본·문서·이미지의 보존을 확인한다. 행 개수뿐 아니라 ID·내용·참조와 실제 조회·저장을 검사한다.
- 백업 복구 후 업그레이드와 이전 릴리스로 복구하는 절차를 검증한다.
- 승인된 변경과 함께 [데이터 형식](DATA_FORMAT.md)·[운영 안내](OPERATIONS.md)·[개발 안내](DEVELOPMENT.md) 및 관련 테스트를 갱신한다. 지원 시작·목표 버전, 실행 명령, 점검 시간과 복구 제한을 기록한다.

## 배포와 복구

[운영 안내의 업데이트 절차](OPERATIONS.md#업데이트)와 [백업·복구 절차](OPERATIONS.md#백업과-복구)를 따른다. 별도 사본에서 먼저 검증하고 쓰기 중단 후 최종 DB·이미지 백업을 만든다. 릴리스와 백업을 대응시켜 보관하며, 사용자 접속 재개 후 복구할 때는 백업 이후 데이터의 보존 계획을 먼저 정한다.
