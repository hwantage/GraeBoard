# 그래보드 운영 안내

[처음으로](../README.md) · [구성도](ARCHITECTURE.md) · [개발 안내](DEVELOPMENT.md) · [데이터 형식](DATA_FORMAT.md) · [DB 변경 지침](DATABASE_CHANGES.md)

이 프로젝트는 서버 배포를 마치고 운영 중입니다. 이후 배포는 기존 DB와 문서 이미지를 보존하는 업데이트로 진행합니다. 아래 명령과 호환성 설명은 **현재 저장소의 구현** 기준이며, 실제 운영 서버의 주소·배포 커밋·Node.js 경로·DB 경로를 의미하지 않습니다.

## 실행 환경

이 절의 실행 명령은 내부 Node 서버 기준입니다. 외부 Supabase Edge·Cloudflare 배포는 [클라우드 설치 안내](CLOUD_SETUP.md)를 따릅니다. 내부는 Node.js **22.13.0 이상**과 npm을 사용합니다. Node.js 16.20.2는 지원하지 않습니다. SQLite는 단일 서버의 로컬 디스크에 두고 앱은 단일 프로세스로 실행합니다. 여러 호스트나 NFS 공유 파일을 통한 동시 운영을 전제로 하지 않습니다.

운영용 빌드는 새 릴리스의 작업 디렉터리에서 준비합니다. 빌드에는 TypeScript·Vite 등의 개발 의존성도 필요하므로 `npm ci --include=dev`로 설치합니다. 셸에 `NODE_ENV=production`이 설정되어 있으면 옵션 없는 `npm ci`도 개발 의존성을 생략할 수 있습니다.

```sh
npm ci --include=dev
npm run build
```

운영 설정과 아래 배포 절차를 확인한 뒤 `npm start`로 실행합니다. `npm run dev`는 소스 감시와 Vite 개발 서버를 사용하는 개발 명령입니다. `npm run build`는 프런트엔드를 `dist/`에 만들고, `npm start`는 이미 만든 파일과 API를 Node.js 서버 하나에서 제공합니다. `npm start`는 빌드나 `NODE_ENV=production` 설정을 자동 수행하지 않습니다.

**`dist/`만 복사해서는 이 앱 전체를 운영할 수 없습니다.** 실행에는 `server/`, `shared/`, `package.json`, `package-lock.json`과 운영 의존성이 필요하며, 관리 명령에는 `scripts/`도 필요합니다. 서버에서 소스를 clone하고 빌드하는 방식이면 이 파일들이 함께 준비됩니다. 다른 장비에서 빌드했다면 의존성은 대상 운영체제·Node.js 환경에서 설치합니다. 특히 이미지 처리 패키지의 네이티브 모듈 때문에 다른 운영체제의 `node_modules/`를 그대로 복사하지 않습니다.

### 프로젝트별 Node.js

시스템 Node.js를 사용하는 다른 서비스가 있으면 시스템 바이너리나 기본 버전을 교체하지 않고 이 앱용 런타임을 분리합니다. nvm을 사용하는 경우 별도로 Node.js 22 계열을 설치한 뒤, 다음처럼 해당 셸에서 선택할 수 있습니다. 예시는 nvm이 `$HOME/.nvm`에 설치되어 있고 Node.js 22가 준비된 경우입니다.

```sh
(
  export NVM_DIR="$HOME/.nvm"
  . "$NVM_DIR/nvm.sh"
  nvm use 22
  node --version
  command -v node
  npm ci --include=dev
  npm run build
)
```

배포에 사용한 정확한 Node.js 버전과 실행 파일 경로를 기록하고, 서버 시작·백업·복구·관리 명령에도 같은 런타임을 사용합니다. 서비스 관리자나 예약 작업은 대화형 셸의 nvm 설정을 자동으로 읽는다고 가정하지 않습니다. `node`의 절대 경로 또는 명시적인 런타임 초기화를 서비스 설정에 지정합니다.

## 환경 설정

`npm start`, `npm run dev`, `npm run backup`, `npm run restore`, `npm run admin`은 작업 디렉터리의 `.env`가 있으면 읽습니다. 프로세스에 직접 지정한 환경 변수가 우선합니다.

새 설치에서만 `.env.example`을 `.env`로 복사한 뒤 수정합니다. 예제 파일은 `NODE_ENV=development`이므로 운영에서는 `production`으로 변경합니다. 기존 운영 `.env`를 예제 파일로 덮어쓰지 않습니다.

| 변수                  | 기본값                    | 용도                                                               |
| --------------------- | ------------------------- | ------------------------------------------------------------------ |
| `HOST`                | `127.0.0.1`               | 서버 바인딩 주소                                                   |
| `PORT`                | `4310`                    | API와 정적 파일 제공 포트                                          |
| `DB_PATH`             | `data/weekly-plan.sqlite` | 데이터베이스 위치. 절대 경로 또는 실행 디렉터리 기준 상대 경로     |
| `DOCUMENT_IMAGES_DIR` | `data/document-images`    | 문서 이미지 저장 경로. 절대 경로 또는 실행 디렉터리 기준 상대 경로 |
| `NODE_ENV`            | 미지정                    | 운영에서는 `production`                                            |
| `GRAEBOARD_SITE` | Node: `internal`, Edge: `external` | 내부·외부 배포 역할. 실제 호스트와 다른 값이면 실행 거절 |
| `SETUP_TOKEN`         | 없음                      | 내부 빈 DB의 최초 관리자 생성용 설정 키                                 |
| `APP_ORIGIN`          | 없음                      | 프록시 뒤 실제 서비스 Origin, 예: `https://graeboard.example.com`  |
| `COOKIE_SECURE`       | `0`과 같은 동작           | HTTPS에서는 `1`                                                    |
| `TRUST_PROXY`         | `0`과 같은 동작           | 신뢰하는 프록시가 정확히 하나일 때 `1`                             |
| `GRAEBOARD_INSTALLATION_ID` | 없음 | 내부 설치의 고정 UUID. 복구 사본에 활성 원본 ID를 재사용하지 않음 |
| `GRAEBOARD_SYNC_PROFILES` | `[]` | 팀·프로필·Git 저장소·토큰 환경변수 이름을 연결하는 JSON 배열 |
| `GRAEBOARD_SYNC_DIR` | `data/sync` | 프로필별 bare Git clone 상위 경로. 운영에서는 릴리스 밖 절대 경로 |
| `GRAEBOARD_SYNC_KEY` | 없음 | 암호화용 32바이트 키의 base64 값. DB·백업과 별도 비밀 보관 |
| `GRAEBOARD_SYNC_KEY_ID` | `default` | 암호화 키 식별자 |
| `GRAEBOARD_SHUTDOWN_TIMEOUT_MS` | `30000` | HTTP·동기화 종료 대기 상한(ms), 100~600000. 초과하면 P를 지우지 않고 exit 1 |

내부 Node 서버에는 `GRAEBOARD_SITE=internal`, 외부 Edge에는 `GRAEBOARD_SITE=external`을 지정합니다. 이 값은 `NODE_ENV`의 개발·운영 구분이나 접속 주소와 무관하며 네트워크 방화벽 설정을 대신하지 않습니다. 기존 설치에서 생략하면 호스트의 고정 역할을 사용합니다. Node에 external을 지정하거나 외부 API에 internal을 지정하면 다른 인증 방식으로 전환하지 않고 설정 오류로 중단합니다. 서버는 `/api/setup`·`/api/bootstrap`의 `site`로 화면에 역할을 알립니다. 내부만 초기 게시와 팀장 연결 키 발급을 제공하며 외부의 최초 연결은 서비스 연결의 팀 가져오기를 사용합니다. 외부 `/sync/enable` 요청은 403으로 거절합니다.

내부 Node를 `NODE_ENV=production`으로 루프백 이외 주소에 바인딩하고 계정이 아직 없으면 `SETUP_TOKEN`이 필요합니다. 루프백 주소 뒤에 프록시를 두는 경우에도 첫 설정을 공개하기 전에 토큰을 지정하거나, 로컬에서 먼저 관리자를 생성하세요. 임의 토큰은 `openssl rand -hex 32` 등으로 생성하여 `.env` 또는 서버의 비밀 설정에 보관합니다. 첫 설정 완료 후 제거할 수 있습니다. 외부 Google 계정 연결은 이 토큰 대신 내부 팀장이 화면에서 발급한 일회용 연결 키를 사용합니다.

기본 바인딩은 `http://127.0.0.1:4310`이며 서버 외부에서 직접 접속할 수 있는 주소가 아닙니다. 사용자는 실제 서비스 주소로 접속합니다. **첫 관리자·팀 생성은 빈 DB의 신규 설치에서만** 수행합니다. 기본 계정·비밀번호는 없고 예시 업무 생성은 선택 사항입니다. 예시 담당자는 로그인할 수 없는 비활성 계정입니다. 운영 업데이트 후 최초 설정 화면이 나타나면 계정을 새로 만들기 전에 DB 경로와 실행 디렉터리가 맞는지 확인합니다.

운영에서는 DB와 이미지 폴더를 릴리스 경로 밖에 두고 **절대 경로**로 지정하면 릴리스 교체 시 같은 데이터를 계속 사용할 수 있습니다. 서비스 실행 계정에 해당 디렉터리의 읽기·쓰기 권한을 부여합니다. SQLite는 DB 옆에 WAL·SHM 파일을 만들므로 DB 파일뿐 아니라 상위 디렉터리도 쓸 수 있어야 합니다. `.env`와 `dist/`의 기준이 되는 서비스 작업 디렉터리는 해당 릴리스 루트로 지정합니다.

외부 운영용 `.env.cloud.local` 등 비밀 파일은 인터넷에 연결된 운영자 환경에서만 읽습니다. 내부 Node의 `.env`와 구분하고 서버 실행 시 합쳐 로드하지 않습니다. 내부에는 팀 Git 토큰과 내부 설치 설정만 등록합니다. 시스템 프록시로는 연결되는데 앱 Git이 실패하면 [앱 clone의 프록시 설정](CLOUD_SETUP.md#github-프록시가-필요한-내부-환경)을 확인합니다.

### 운영 기록

각 배포 때 다음 항목을 접근이 제한된 운영 기록에 남깁니다. 비밀번호·토큰·운영 DB는 저장소에 올리지 않습니다.

| 기록 항목   | 확인할 내용                                                              |
| ----------- | ------------------------------------------------------------------------ |
| 릴리스      | 배포 일시, 커밋 또는 태그, 이전 릴리스 경로                              |
| 런타임      | 정확한 Node.js·npm 버전, 실행 파일 경로, 서비스 실행 계정·작업 디렉터리  |
| 접속        | 실제 서비스 Origin, 프록시·바인딩·포트, 서비스 시작·정지·로그 확인 방법  |
| 영속 데이터 | 실제 `DB_PATH`, `DOCUMENT_IMAGES_DIR`, 읽기 전용으로 확인한 DB 버전      |
| 복구        | 백업 시각·DB 파일·이미지 묶음 위치, 복구에 사용할 릴리스, 복구 검증 결과 |

## 사내 서버 배치

```sh
NODE_ENV=production HOST=127.0.0.1 PORT=4310 npm start
```

HTTPS 역방향 프록시가 앱으로 요청을 전달하도록 구성하고 앱 포트의 직접 외부 접근을 제한합니다. `APP_ORIGIN`, `COOKIE_SECURE`, `TRUST_PROXY`는 실제 프록시 구성과 일치시킵니다. 프로세스 재시작 정책과 파일 접근 권한은 운영 환경에서 관리합니다.

브라우저의 셀·문서 본문·문서 목록·원본 및 사본 시트 동기화는 SharedWorker에서 같은 Origin의 `POST /api/events` SSE 연결 하나를 공유합니다. 프록시가 POST 응답도 버퍼링 없이 스트리밍하도록 구성합니다. 개별 GET 경로인 `/api/cells/events`와 리소스별 `/events`도 유지합니다. 집계용 `GET /api/events`는 제공하지 않습니다([경로 명세](DATA_FORMAT.md#실시간-동기화)). 모든 SSE 경로의 프록시 응답 버퍼링·압축을 끄고 15초 heartbeat가 전달되도록 읽기 제한 시간을 60초 이상으로 둡니다. 앱도 `X-Accel-Buffering: no`, `Cache-Control: no-store, no-transform`을 보내며 SSE 응답은 압축하지 않습니다. SharedWorker 연결 공유에는 인증서나 HTTP/2가 필요하지 않으며 기존 `npm run start` 실행 방식을 유지합니다. 미지원 브라우저나 서로 다른 앱 버전의 탭은 연결을 별도로 사용하므로, 이 경우까지 연결 수 여유를 늘리려면 앞단 HTTPS 프록시의 HTTP/2를 추가로 사용할 수 있습니다. SSE 재전송 버퍼는 앱 프로세스별 메모리에 있으므로 앱은 단일 프로세스로 실행합니다. 프로세스 재시작 시 클라이언트는 DB의 최신 셀·문서·시트로 다시 동기화합니다.

비밀번호는 scrypt 해시로 저장합니다. HTTP-only 세션 쿠키는 30일 유지하며 유효한 인증 요청에서 하루에 한 번 만료 시각과 쿠키를 함께 갱신합니다. 기존의 아직 만료되지 않은 세션도 같은 방식으로 연장하며, 만료·삭제된 세션은 복원하지 않습니다. 로그아웃·계정 비활성화와 비밀번호 변경 시 기존 로그인을 무효화합니다. 프로세스와 프록시의 응답 확인은 `GET /api/health`, 오류 확인은 서버 표준오류를 사용합니다. 현재 health 응답의 `version`은 고정된 앱 버전 문자열이므로 배포 커밋이나 DB 무결성 확인을 대신하지 않습니다. 업무 데이터나 로그인 정보를 외부 오류 수집기로 자동 전송하는 기능은 없습니다.

감사 이력과 사본은 자동 삭제하지 않습니다. 보관·반출 기준과 백업 용량을 운영자가 관리합니다. 개발 환경의 검증 결과는 운영 장비·네트워크의 성능 보장을 대신하지 않습니다.

### DB 호환성

현재 저장소의 DB 스키마는 **v31**, JSON 내보내기 형식은 **v6**입니다. 내부 서버는 빈 신규 DB 또는 checksum 이력이 일치하는 v31만 엽니다. 기존 v29·v30은 `npm run migrate -- --engine sqlite --database /절대경로/자료.sqlite`로 명시적으로 변환합니다. 일반 시작·복구는 기존 DB를 자동 변환하지 않으며 실제 운영 DB 버전은 배포 전에 별도로 확인합니다.

스키마·저장 형식·기존 데이터 변환이 필요한 작업은 [DB 변경 지침](DATABASE_CHANGES.md)의 승인·마이그레이션·검증 절차를 따릅니다.

사본은 공통 서식 사전과 필요한 담당자의 ID·이름만 포함한 gzip BLOB이며 아바타를 복사하지 않습니다. 문서는 `document_versions`에 보관하고 원본·사본이 참조합니다. 문서 수정은 해당 원본/사본의 참조만 교체하므로 서로 영향을 주지 않습니다. 사용하지 않는 이전 본문은 정리하며 분기 이력은 별도로 보관하지 않습니다. 백업은 DB의 본문·참조와 외부 이미지 파일을 함께 보관합니다. 저장 구조의 상세는 [데이터 형식](DATA_FORMAT.md)을 참고하세요.

이번 주 기본 테두리의 `currentWeekBorders`는 기존 `teams.settings` JSON의 선택 항목입니다. 당시 DB v29·JSON v6·백업 버전을 유지한 변경이며 기존 팀·사본의 누락 항목은 설정 없음으로 읽으므로, 별도 SQL 변환이나 신규 DB 생성이 필요하지 않습니다. 프런트엔드와 API를 함께 배포하고 실제 운영 버전·백업은 위 호환성 및 업데이트 절차에 따라 확인합니다. 구버전 API는 새 항목을 받지 못하며 설정 저장 시 제거할 수 있으므로, 코드만 되돌린 뒤 새 테두리 설정이 보존된다고 가정하지 않습니다. 운영 적용·복구는 별도 승인한 환경에서 수행합니다.

### 이력 보관과 정리

로그인 성공과 직접 로그아웃할 때 시스템 공통 감사 이력에 한 건씩 기록합니다. 해당 기록은 공통 용량 집계·이력 정리 대상에 포함되며 비밀번호나 세션 토큰은 저장하지 않습니다. 이 기능 적용 전에 저장하지 않은 로그인 기록은 소급 생성하지 않습니다.

**설정 → 시스템 → 감사 로그**에서 시스템 관리자가 공통 감사 이력을 조회합니다. 기본 시작·종료 날짜와 초기화 날짜는 한국 시간 기준 오늘입니다. 기간(한국 시간, 시작·종료일 포함)·수행자·작업 종류를 조합해 검색하고, 최신순 50건씩 이전·다음 페이지로 이동합니다. 상세를 펼치면 당시 변경 전·후 값이 표시됩니다. 목록은 메타데이터만 읽으며 상세 JSON은 해당 항목을 펼칠 때 가져옵니다. 팀 이력과 공통 저장 재시도 메타데이터는 이 감사 로그 목록에 포함하지 않습니다. 이력 정리에서 삭제한 공통 감사 로그는 더 이상 조회되지 않습니다.

**설정 → 시스템 → 변경 이력 정리**에서 시스템 관리자가 팀을 선택해 직접 정리합니다. 자동 삭제나 모든 팀 일괄 삭제는 없습니다.

1. **팀별 저장 용량**에서 전체 데이터·변경 이력·사본 용량을 비교하고 팀을 선택합니다. 선택한 팀의 업무·설정, 가져오기 자료, 셀 저장 재시도 용량도 표시합니다.
2. **30·90·180·365일 전** 버튼이나 바로 옆 날짜 입력란으로 **기준 날짜**를 선택하고 **데이터 용량 확인**을 누릅니다. 처음에는 365일 전 날짜를 제시합니다. 선택한 날짜의 **한국 시간 00:00 이전**만 대상으로 하며 그 날짜 자체는 제외합니다. 날짜는 2000년 1월 1일부터 오늘까지 선택할 수 있습니다.
3. 날짜 이전의 전체 건수·용량, 실제 삭제 가능한 건수·용량을 확인합니다. 팀·날짜를 변경하면 이전 미리보기는 폐기되어 다시 조회해야 합니다.
4. **이전 데이터 삭제**를 누르면 선택한 팀 이름·기준 날짜·삭제 건수·용량을 다시 보여줍니다. 확인한 팀의 변경 이력과 만료된 셀 재시도 기록만 삭제합니다. 현재 업무·계정·사본·가져오기 자료·백업·다른 팀 이력과 최대 50개 실행취소 기록은 유지됩니다.
5. 요청당 최대 500건 또는 JSON 합계 10MiB씩 처리합니다. 한 건이 10MiB를 넘으면 그 건만 처리합니다. **중단**하거나 화면을 닫으면 진행 중인 묶음까지만 처리합니다. 남은 용량을 다시 확인해 계속할 수 있습니다. 최근 실행자·시각·누적 삭제 건수·완료 여부는 팀별로 남습니다.

용량은 업무 셀 값·서식, 공유 문서 버전 본문, 업무 연도·기본 서식, 팀 설정·보기·필터, 압축 사본 BLOB, 가져오기 본문·결과, 변경 이력 전후 JSON, 셀 재시도 메타데이터의 저장 바이트 합계입니다. 계정·인덱스·행 메타데이터·WAL·DB 여유 공간 등은 포함하지 않으므로 물리적 DB 파일 크기와는 다릅니다. 본문을 API에 보내지 않고 DB에서 UTF-8 바이트 수만 집계합니다.

| 대상                               | 정리 기준                                                                                                               |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 팀 변경 이력                       | 선택한 팀·날짜 이전의 전후 데이터와 메타데이터. 아직 유효한 재시도 기록이 참조하는 이력은 보호                          |
| 단일 팀 셀 재시도 기록             | 선택한 팀·날짜 이전이면서 7일+시각 오차 허용분 5분이 지난 기록만 삭제                                                   |
| 시스템 공통                        | 계정 변경 등 팀이 없는 이력과 여러 팀이 공유하는 셀 재시도 기록. 별도 행으로 선택·조회·삭제하며 팀 이력은 포함하지 않음 |
| XLSX 가져오기 재시도·가져오기 자료 | 이 정리에서 제외. 같은 파일의 중복 적용을 방지                                                                          |
| 사본·SQLite 백업                   | 용량을 확인하더라도 이력 정리에서는 삭제하지 않음. 각 기능의 별도 보관 기준으로 관리                                    |

여러 팀이 공유하는 재시도 메타데이터는 **시스템 공통** 용량에 한 번만 집계합니다. 한 팀을 정리해도 이 공유 기록이나 다른 팀 이력은 지우지 않습니다. 날짜 조건에 맞더라도 아직 필요한 기록은 미리보기에서 보호 중인 건수로 안내합니다.

셀 요청은 `operationId`와 최초 `createdAt`(UTC ISO 시각)을 함께 보내며 같은 요청 재시도에서는 둘 다 유지합니다. 생성 시각 누락은 400, 7일이 지난 요청은 410, 서버보다 5분 넘게 미래인 요청은 400으로 거절합니다. 재시도 기록을 삭제한 뒤에도 만료 요청을 다시 실행하지 않습니다.

미리보기 토큰은 관리자 계정·선택 범위·날짜에 묶여 15분간 유효합니다. 새 미리보기를 만들면 이전 토큰을 대체하고 서버 재시작 뒤에는 다시 확인해야 합니다. 실행 중에는 마지막 묶음부터 15분으로 연장합니다. 삭제 기준은 미리보기의 팀·날짜로 고정하며 이후의 새 편집은 포함하지 않습니다. 묶음 삭제와 `history-cleanup` 결과 로그를 같은 트랜잭션으로 기록하므로 실패한 묶음은 함께 롤백합니다. 통신이 끊겨도 이미 완료한 삭제는 유지됩니다. 결과 로그도 해당 팀의 이력으로 남고 이후 날짜 기준 정리의 대상이 됩니다.

팀·날짜 인덱스로 정리 후보를 찾으며 일반 셀 저장에서 용량 집계·정리·과거 이력 비교는 실행하지 않습니다. 용량 조회와 정리는 사용량이 적은 시간에 실행하는 것을 권장합니다.

SQLite의 삭제 공간은 이후 쓰기에 재사용되지만 파일 크기는 바로 줄지 않을 수 있습니다. 실제 파일 축소가 필요하면 백업 후 점검 시간에 서버를 중지하고 `VACUUM`을 수행합니다. 앱의 정리 기능은 `VACUUM`을 실행하지 않습니다. [SQLite VACUUM 문서](https://www.sqlite.org/lang_vacuum.html)는 파일 재구성과 작업 중 필요한 여유 공간을 설명합니다.

## 문서 이미지 저장

이미지는 `DOCUMENT_IMAGES_DIR` 아래 팀별 폴더에 WebP로 저장하며 애플리케이션의 로그인·팀 권한 검사 후 제공합니다. 경로를 바꿀 때 기존 폴더를 새 경로로 함께 이동해야 기존 문서의 이미지가 유지됩니다. 서로 다른 DB를 운영할 때 이미지까지 분리하려면 각각 다른 경로를 지정합니다. 업로드 원본은 PNG/JPEG/WebP 정지 이미지, 파일당 10MiB·4천만 화소 이하이며 최대 4096px로 축소합니다. 이미지 파일 용량은 관리자 화면의 DB 논리 용량에 포함되지 않습니다.

동일 파일은 팀 안에서 재사용합니다. 문서 수정 취소나 이미지 제거 후 사용하지 않는 파일의 자동 정리는 아직 제공하지 않으므로 디스크 용량도 별도로 확인합니다. 백업은 문서에서 참조한 파일만 보관합니다. 팀을 영구 삭제하면 해당 팀의 이미지 폴더도 삭제하며 별도 백업은 유지합니다.

## 백업과 복구

기본 백업은 `backups/graeboard-시각.sqlite`에 생성합니다. 서버와 같은 `DB_PATH`·`DOCUMENT_IMAGES_DIR`을 사용하고, 백업 대상 DB와 호환되는 릴리스의 도구로 실행합니다. `.env`가 자동으로 읽히는지뿐 아니라 서비스에 직접 지정한 환경 변수와 일치하는지도 확인합니다.

**백업 범위:** `npm run backup`은 `DB_PATH`의 SQLite와 그 DB가 참조하는 이미지만 보관합니다. Node의 팀 업무 repository를 PostgreSQL로 선택했다면 PG 자료와 PG에만 참조된 파일 이미지는 포함하지 않습니다. 현재 **SQLite control + PG 팀 업무 + FileImageStore 조합 전체의 일관된 오프라인 백업·복구 절차는 제공하지 않습니다.** `backup:external`·`restore:external`과 PG `transfer --resources`는 R2 설정을 요구하므로 이 파일 이미지 조합의 대체 절차도 아닙니다. 일반 업무 저장 계약의 교체 검증과 이 조합의 운영 복구 준비를 구분하며, SQLite 백업 성공을 전체 사이트 백업 성공으로 기록하지 않습니다. 이 조합을 운영에 사용하기 전에는 control·모든 팀 DB·전체 파일 이미지·동기화 신원/복구 상태를 함께 보존하고 새 격리 자원으로 복원하는 별도 절차와 검증이 필요합니다.

```sh
npm run backup
npm run backup -- backups/manual.sqlite
```

이름을 지정한 백업은 기존 파일이나 이미지 묶음을 덮어쓰지 않습니다. 반복 백업에는 매번 새로운 이름을 사용합니다. 백업에서 이미지가 사용되면 `manual.sqlite.images/`가 함께 생깁니다. **SQLite 파일과 이 폴더를 같은 위치에 함께 보관·이동**해야 합니다. 참조한 이미지가 없거나 해시가 다르면 백업·복구를 실패 처리합니다.

백업은 `VACUUM INTO`로 실행 중인 SQLite의 일관된 사본을 생성하고 `integrity_check`를 수행한 뒤 그 사본에서 참조한 이미지도 모읍니다. 실행 중인 DB 본체 파일만 복사하면 WAL에 남은 변경이 누락될 수 있습니다. 업데이트 직전의 최종 백업은 서버와 다른 쓰기 작업을 중지한 뒤 생성합니다.

동기화 팀의 백업·논리 이관에는 같은 `GRAEBOARD_SYNC_DIR`과 Git CLI도 필요합니다. clone은 `<GRAEBOARD_SYNC_DIR>/<profileId>`이며 `team-a-internal` 프로필의 예는 `/srv/graeboard/data/sync/team-a-internal`입니다. L로 회수한 이미지 바이트는 백업 DB의 고정 Git head를 이 clone에서 읽어 검증합니다. 야간 작업에도 같은 절대 경로·실행 권한·`git` PATH를 설정하고, 캐시라는 이유로 디렉터리를 삭제하지 않습니다. clone·객체·Git 실행 파일 누락은 백업 실패이며 불완전 묶음을 완전 백업으로 취급하지 않습니다.

복구 훈련은 운영 데이터와 분리된 새 경로에서 수행합니다. 다음은 현재 버전의 백업을 임시 DB와 **별도 이미지 폴더**로 복구하는 예시입니다. 실제 운영 복구 경로는 승인된 복구 계획에 맞게 지정합니다.

```sh
DOCUMENT_IMAGES_DIR=data/restore-check/document-images npm run restore -- backups/manual.sqlite data/restore-check/weekly-plan.sqlite
```

복구 명령은 **새 DB 파일**에만 쓰며 기존 대상 파일을 덮어쓰지 않습니다. 이미지 경로를 생략하면 `.env`의 폴더를 사용하므로 훈련에서는 반드시 분리합니다. 복구된 세션은 삭제되어 사용자가 다시 로그인해야 합니다. 복구한 DB로 서버를 확인할 때도 별도 작업 경로·DB·이미지 설정과 로컬 바인딩·별도 포트를 사용합니다.

복구 도구는 v29·v30·v31 백업을 원래 버전 그대로 새 경로에 복원합니다. v29·v30 복구본은 원본을 보존한 뒤 명시적 migration으로 v31을 만들며, v30 이상 연결은 `recovery`로 시작합니다. `npm run sync:recover -- --database /절대경로/복구본.sqlite --team-id 팀UUID --dry-run`으로 대조하고, 원래/복구 서버의 쓰기 중단과 백업을 확인한 후 `--confirm-drained`로 읽기 전용 원격 대조를 완료합니다. 결과는 일시정지 상태이며 관리자가 재개합니다.

운영 복구는 서버와 쓰기 작업을 중지하고 검증된 DB·이미지 묶음을 준비한 뒤 `DB_PATH`와 `DOCUMENT_IMAGES_DIR`을 함께 전환합니다. 해당 DB와 호환되는 릴리스로 재시작하며 이전 DB와 백업은 자동 삭제하지 않습니다. 백업 시점 이후의 변경은 복구본에 없으므로 재개 이후 데이터의 보존 방법을 먼저 판단합니다.

백업을 정기 실행하고 접근이 제한된 별도 저장소에도 보관합니다. 예약 실행은 운영자가 구성하며 앱이 자동으로 수행하지 않습니다. 보관 주기·기간·성공 여부·남은 용량을 관리하고 실제 복구 훈련에서 계정·권한·업무·필터·서식·캘린더·사본·문서·이미지를 확인합니다. JSON/XLSX 내보내기는 전체 운영 DB 백업을 대체하지 않습니다. 팀 영구 삭제는 이미 생성한 별도 백업 파일까지 삭제하지 않습니다.

## 관리자 비밀번호 재설정

서버에 접근할 수 있는 관리자는 표준입력으로 새 비밀번호를 전달합니다. 다음 예시는 Bash/Zsh에서 사용할 수 있습니다.

```sh
read -s GRAEBOARD_RESET_PASSWORD
printf '%s' "$GRAEBOARD_RESET_PASSWORD" | npm run admin -- reset-password 사용자이메일
unset GRAEBOARD_RESET_PASSWORD
```

비밀번호는 10~128자이며 재설정한 계정의 기존 세션을 해제합니다. `npm run admin`도 `.env`의 `DB_PATH`를 사용합니다. 비밀번호를 명령 인자·스크립트·저장소에 넣지 마세요.

## 업데이트

### 배포 전 준비

1. 현재 배포 커밋·런타임·환경 설정·실제 DB 및 이미지 경로를 기록합니다. 실제 운영 DB의 `PRAGMA user_version`을 읽기 전용으로 확인하고 새 릴리스와 비교합니다. 버전 확인을 위해 새 서버를 운영 DB에 먼저 연결하지 않습니다.
2. 스키마·저장 형식·데이터 해석의 호환성 변경을 확인합니다. 변경이 있으면 [DB 변경 지침](DATABASE_CHANGES.md)에 따른 승인·구현·검증을 완료한 뒤 배포합니다.
3. 운영 중인 경로와 분리해 새 소스를 준비하고 해당 런타임으로 `npm ci --include=dev`, `npm run build`, 변경에 필요한 [검증](DEVELOPMENT.md#검증)을 수행합니다. 빌드 도중 기존 서비스의 `dist/`·의존성을 교체하지 않습니다.
4. 현재 버전 도구로 백업한 사본을 별도 DB·이미지 경로에 복구해 새 릴리스를 검증합니다. DB 변경이 있으면 사본에서 승인된 마이그레이션과 이전 릴리스로의 복구를 먼저 검증합니다. 운영 DB를 테스트 대상으로 사용하지 않습니다.
5. 점검 시간, 쓰기 중단 방법, 최종 백업 위치, 이전 릴리스 및 복구에 필요한 환경 설정을 준비합니다.

### 운영 적용

1. 승인된 점검 시간에 사용자 접근을 제한하고 앱과 다른 쓰기 작업을 정상 종료합니다. 시작·정지 명령은 실제 서비스 관리 방식에 맞게 사용합니다.
2. **기존 릴리스의 도구**와 실제 운영 환경 설정으로 최종 DB·참조 이미지 백업을 생성합니다. 완료 여부와 복구 가능 여부를 확인하고 릴리스·DB 버전·백업 묶음을 대응시켜 보관합니다.
3. DB 변경이 없다면 기존 데이터 경로를 유지합니다. 변경이 있다면 승인된 마이그레이션을 한 번만 실행하고 `integrity_check`·`foreign_key_check` 및 데이터 보존 검사를 통과한 뒤 진행합니다. `npm run migrate -- --engine sqlite --database /절대경로/자료.sqlite --dry-run` 후 승인된 대상에 같은 명령에서 `--dry-run`을 빼고 실행합니다.
4. 새 릴리스의 작업 디렉터리·Node.js 경로를 서비스에 지정하고, 기존 `.env` 또는 서비스 환경의 `NODE_ENV=production`, `DB_PATH`, `DOCUMENT_IMAGES_DIR`, 접속·쿠키·프록시 설정을 유지해 시작합니다. 새 DB 생성이나 빈 경로 지정으로 버전 오류를 해결하지 않습니다.
5. `/api/health`와 실제 첫 화면, 기존 계정 로그인·팀 접근, 업무 조회·저장, 필터, 문서·이미지·캘린더·사본의 주요 동작을 확인합니다. 여러 탭에서 셀 수정 동기화도 점검합니다. `dist/`가 없어도 health는 성공할 수 있으므로 화면 확인을 생략하지 않습니다.
6. 검증을 마친 뒤 사용자 접속을 재개하고 배포 결과와 로그·백업 위치를 기록합니다.

### 실패 시 복구

- **사용자 접속 재개 전**: 서비스를 중지하고 이전 릴리스와 최종 백업의 DB·이미지를 함께 새 경로에 복구해 검증합니다. 스키마가 바뀐 DB에 이전 프로그램만 실행하지 않습니다.
- **사용자 접속 재개 후**: 백업 복구는 백업 이후 저장된 변경을 잃을 수 있습니다. 현재 데이터를 먼저 보존하고 수정 배포 또는 데이터 보존을 포함한 복구 계획을 정해 승인 범위에 따라 수행합니다.
- 복구 후에는 세션이 삭제되므로 재로그인이 필요합니다. 이전 릴리스·DB·이미지·백업을 검증 완료 전에 정리하지 않습니다.

## 저장소에 포함하지 않는 파일

`.gitignore`는 DB와 WAL·SHM 파일, 백업, 가져오기·내보내기 파일, 실제 `.env`, 인증서·개인 키, 빌드 결과와 의존성, 테스트 로그·스크린샷을 제외합니다. 원본 시트 링크가 들어 있는 초기 RFP도 로컬 참고 자료로만 보관합니다.

공유할 환경 설정은 비밀값이 없는 `.env.example`을 사용합니다. 테스트 코드의 예시 계정·문구는 임시 DB 검증용이며 실제 운영 데이터는 저장소에 포함하지 않습니다.

## 내부·외부 Git 동기화 운영

외부 API의 기본 실행 환경은 Supabase Edge Functions입니다. Cloudflare gateway는 정적 화면·요청 전달·R2/Images 처리만 수행하며 내부 Node는 `GRAEBOARD_SITE=internal`과 GitHub 접속만 유지합니다. `npm run build:edge`로 만든 함수를 배포하고 Pages binding을 gateway로 연결합니다. 기존 Worker에서의 이전은 동일 DB·계정 세션·설치 UUID를 유지하며 schema migration이 없습니다. 배포 설정·Secret 분리·전환과 복구 순서는 [Edge 배포](CLOUD_SETUP.md#supabase-edge-functions-배포)를 따릅니다. Hyperdrive는 사용하지 않으며 이전 Worker 이름은 gateway 전달용으로만 유지합니다. 업무 요청 외의 자동 동기화는 gateway Cron이 Edge를 호출하며, Cloudflare와 Supabase 양쪽 실행 로그를 확인합니다.

외부 배포 산출물은 다음처럼 구분합니다. Pages 소스의 자동 빌드가 다른 대상까지 배포하지 않습니다.

| 변경 대상 | 반영 방법 |
| --- | --- |
| 화면·정적 자원 | `npm run build` 후 `dist/`를 포함한 gateway 배포 |
| 업무 API·앱 내 설치 안내 | `npm run build:edge` 후 Supabase 함수 배포 |
| gateway 코드·자원·Cron | 팀 gateway 설정으로 Worker 배포 및 설정 반영 |
| Pages Functions·Service binding | Pages 재배포 |

`docs/CLOUD_SETUP.md`는 Edge 함수에 포함되어 **서비스 연결의 설치 안내**로 제공됩니다. 이 문서가 바뀌면 함수도 재빌드·배포한 뒤 `/api/admin/service-connections/guide`의 내용을 확인합니다. 나머지 Markdown 문서는 저장소에서 확인합니다. 배포별 커밋·함수/Worker 버전과 실제 활성 자원을 기록합니다.

리소스 생성, Edge의 PostgreSQL 직접 연결과 gateway의 R2·Images bindings, 전용 Access 앱·Google 로그인, 비밀 토큰, 첫 관리자/팀 가져오기는 [클라우드 설치 안내](CLOUD_SETUP.md)를 순서대로 따릅니다. 내부 `GRAEBOARD_SYNC_PROFILES=[]`이면 기존 SQLite 저장·인증을 유지합니다. 외부 연결 팀마다 Pages/gateway·Git·R2·Supabase 프로젝트와 Edge 함수를 따로 운영합니다. 그 팀의 이름·이메일·활성 상태·팀 역할은 구성원 브랜치로 내부에서 계속 반영합니다. 팀장이 최초 연결하고 다른 사용자의 사내 계정 선택 요청을 승인합니다. 비밀번호·사내 세션·다른 팀 소속·전체 관리자 권한은 전송하지 않습니다.

- 일시정지는 로컬 저장과 미전송 캡처를 유지합니다. 같은 내부 서버에서 연결을 해제했다면 팀 동기화의 **다시 연결**로 미캡처 변경을 보존하고 재개합니다. 기존 프로필·설치 ID·공유 커서를 유지하며 서버를 중지하지 않습니다. DB 복원·설치 ID 변경·복구 상태는 이 버튼의 대상이 아니며 `sync:recover` 점검을 따릅니다.
- SQLite 복구와 외부 PG/R2 복구는 별도 명령입니다. `backup:external`·`restore:external`·`transfer -- --help`의 실제 입력과 제한을 설치 안내에서 확인합니다. 한 프로젝트의 site/team 스키마와 이미지 bundle을 함께 보관합니다. 승인·Google 연결은 복원하고 접속 세션은 새로 만듭니다. 기존 분리형 control/team 백업 v1은 해당 형식으로 계속 복구합니다.
- 동기화된 팀을 영구 삭제하려면 전송·백업을 완료하고 연결을 해제합니다. 미전송 변경이나 실행 중인 정리·백업이 있으면 삭제를 거절합니다. Git 이력은 이 동작으로 삭제되지 않습니다.
- 오래된 원격 반영 상태는 현재 완료로 표시하지 않습니다. Git 게시와 반대편 적용을 각각 확인합니다. 강제 push·브랜치 삭제·저장소 신원 변경은 자동 초기화하지 않고 복구 점검 상태로 중단합니다.
- 로컬 정리는 DB의 전체 공유 본문을 보존합니다. 화면 제외와 실제 이미지 파일 회수 범위는 구분되며 Git의 물리 용량은 줄지 않습니다.

SIGTERM/SIGINT는 새 접속·구독을 차단하고 진행 중 HTTP 요청과 동기화를 기다립니다. 종료 상한을 넘으면 비정상 종료 코드 1을 기록하고 프로세스를 종료하며 미전송 명령을 삭제하지 않습니다. 이때 응답을 못 받은 요청은 결과를 재조회하고, 중단된 동기화·정리·백업의 소유권은 실제 이전 실행 종료를 확인한 뒤 복구 절차로 처리합니다. 초기 게시·수동 실행은 완료까지 HTTP 응답을 기다리므로 프록시 시간 초과를 작업 취소로 해석하지 말고 상태를 다시 조회합니다.


팀장 연결 키 업데이트는 SQLite v30 → v31, 외부 계정 관리 site v1 → v2이며 업무 team v1은 그대로입니다. 기존 계정·승인·업무·문서·이미지를 변환하거나 삭제하지 않습니다. 운영 사본에서 `npm run migrate -- --engine sqlite --database 사본경로 --dry-run`과 실제 변환·무결성·원본 행 보존을 검증한 뒤, 쓰기를 중단하고 현재 버전 도구로 DB/이미지 최종 백업을 만듭니다. 승인된 원본 경로를 변환하고 서버를 재시작합니다. v31에는 두 migration checksum이 필요하며 이전 v30 이력은 수정하지 않습니다.

site v1에서 키 기능을 도입하는 기존 설치에는 먼저 site v1/v2를 모두 읽을 수 있는 외부 API를 배포합니다. 현재 외부 API는 Supabase Edge에서 실행합니다. GitHub만 접속 가능한 내부 서버에서 Supabase 접속 URL을 사용하지 않습니다. 외부 관리 환경의 CLI 또는 `node scripts/site-key-migration-sql.mjs 팀UUID`로 출력한 SQL을 Supabase SQL Editor에서 실행합니다. 실행 전 업무·계정 변경을 잠시 중단하고 현행 외부 백업을 보관합니다. SQL은 팀·버전·checksum을 확인하고 새 두 테이블과 이력을 한 트랜잭션에 추가합니다. 실패하면 롤백하며 재실행은 중복 적용하지 않습니다. 실제 점검 시간은 백업과 검증 시간에 따라 달라집니다.

기존 Google 연결은 유지됩니다. 초기 키 방식으로 되돌리기 위해 예전 API 코드만 배포하지 않습니다. 접속 재개 전 실패는 백업과 대응 릴리스로 함께 복구하고, 재개 후에는 현재 데이터를 보존한 채 수정 배포를 우선합니다. 백업 복구는 백업 이후 저장을 잃을 수 있으므로 재개 후 전체 복구 전에는 그 사이 데이터를 별도 보존해야 합니다. 복구된 미사용 연결 키는 폐기하며 내부에서 재발급합니다.
