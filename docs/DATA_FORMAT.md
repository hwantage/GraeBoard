# 그래보드 데이터 형식과 접근 규칙

[처음으로](../README.md) · [개발 안내](DEVELOPMENT.md) · [운영 안내](OPERATIONS.md)

## 기준

표시 브랜드는 그래보드(GraeBoard)이며 JSON 포맷·세션 쿠키·쓰기 요청 헤더 식별자는 `weekly-plan`/`WeeklyPlan`을 씁니다. 다운로드 파일명은 `graeboard-연도.확장자`입니다. 이 문서는 현재 형식만 설명하며, 이전 형식과의 호환 계층은 없습니다. 셀 재시도 기록은 이력 참조만 사용합니다.

JSON 반출의 `format`은 `weekly-plan`, `schemaVersion`은 `5`입니다. `exportedAt`은 UTC ISO 시각입니다. `year`는 업무 생성과 표 배치 저장의 기준 연도이며 `startMonth`(1~12, 기본 1)부터 연속된 12개월을 표시합니다. 두 해의 현재 보기 파일명은 `graeboard-2026-2027.확장자`처럼 연도 범위를 포함합니다. SQLite 저장 형식 버전(`SCHEMA_VERSION`)은 27입니다. 한편 한 업무는 `years` 배열을 통해 여러 연도에서 같은 ID로 조회할 수 있습니다. 기본 운영 시각은 한국 기준, 날짜 키는 시간대가 없는 `YYYY-MM-DD`입니다.

## 저장 규칙 요약

이 절과 [서식 저장과 전송](#서식-저장과-전송)이 저장 구조 변경 시 지켜야 할 기준입니다. 사용자가 보는 동작은 [사용 안내](USER_GUIDE.md), 구현 경로와 검증은 [개발 안내](DEVELOPMENT.md)에 정리합니다.

1. **빈 주차를 미리 만들지 않습니다.** 값도 개별 서식도 없는 주차는 키 자체를 저장하지 않습니다. 주차 목록은 달력에서 계산합니다. 숫자 `0`, 빈 복수 선택 배열, 상속을 해제하는 서식은 의미를 확인해 보존합니다.
2. **서식은 축약하고 공유합니다.** `backgroundColor`는 `bg`, 네 방향 테두리는 `bt`·`br`·`bb`·`bl`로 저장합니다. 같은 서식은 SQLite의 `styles` 또는 JSON의 `$styles` 사전에 한 번만 둡니다.
3. **전체 행·열 서식은 범위 규칙으로 저장합니다.** 같은 색을 수천 셀에 복사하지 않습니다. 한 셀만 다르게 지정하면 그 차이만 셀에 저장합니다.
4. **우선순위는 기본 서식 → 공통 규칙 → 셀 예외입니다.** 공통 규칙끼리는 속성별로 나중에 적용한 값이 우선합니다. 행·열에 같은 속성을 다시 적용하면 해당 범위의 그 속성에 대한 셀 예외를 제거합니다.
5. **행 규칙은 같은 업무의 미래 주차에도 이어집니다.** 열 규칙과 행의 바깥쪽 끝선은 선택한 실제 키에 연결됩니다. 날짜 키는 `YYYY-MM-DD`를 유지합니다.
6. **수정 번호는 생략하지 않습니다.** 셀의 `version`과 팀 공통 서식의 `revision`은 동시 수정·실행취소 충돌을 판별하는 서로 다른 번호입니다. 데이터 형식 버전과 구분합니다.
7. **이력도 축약 형식으로 저장하고 보여 줍니다.** 변경 이력의 JSON 표시는 `bg`와 사전 참조를 유지합니다. 개별 업무 생성·이동·삭제 이력에는 그 업무에 영향을 주는 규칙만 담습니다.

## 변경이력과 셀 재시도 저장

명시적인 로그인 성공과 로그아웃은 공통 `audit`에 각각 `login`·`logout` 작업으로 저장합니다. 수행자·대상은 해당 사용자 ID이며 `after`에는 당시 `{name, username}`만 담습니다. 세션 생성·삭제와 감사 기록은 같은 트랜잭션으로 처리합니다. 비밀번호·세션 토큰은 기록하지 않으며 세션 확인·비밀번호 변경 후 세션 재발급은 로그인 기록을 만들지 않습니다.

셀 저장은 현재 셀, 팀별 `audit` 전후 JSON, `operations` 재시도 메타데이터를 한 트랜잭션으로 기록합니다. 새 셀 작업의 `operations.response`는 `{kind: "cell-audit", refs, savedAt, updatedAt}`이며 셀 값·서식을 포함하지 않습니다. `refs`는 `{id: 이력 ID, teamId}` 배열입니다. 여러 팀의 셀이 섞인 요청만 각 참조에 원래 응답 배열의 `positions`를 추가합니다. 단일 팀 요청은 셀별 순서 정보도 저장하지 않습니다.

정상 저장은 과거 이력을 조회하거나 과거 본문을 비교하지 않고 새 이력 ID를 연결합니다. 현재 셀과 값·정규화한 서식이 동일하면 쓰기·버전 증가·업무시각 변경·감사 이력을 생략합니다. 모든 항목이 동일하면 빈 `cells`·`before`·`updatedAt`을 반환하고 `refs: []`인 작은 재시도 기록만 저장합니다. 버전·권한 검사는 생략하지 않습니다. 같은 `operationId`가 다시 들어왔을 때만 `audit.id` 기본키로 전후 JSON을 읽어 `cells`, `before`, `operationId`, `savedAt`, `updatedAt` 응답을 복원합니다. 현재 셀을 응답 원본으로 사용하지 않으므로 이후 편집·복원·서버 재시작에도 최초 응답과 순서가 같습니다. 요청자와 현재 팀 접근 권한은 재시도에도 검사합니다. 참조 이력이 없으면 410으로 거절하고 변경을 다시 실행하지 않습니다.

셀 요청의 `createdAt`은 필수 UTC ISO 시각이며 `operationId`와 함께 최초 전송부터 재시도까지 유지합니다. 생성 후 7일이 지나면 기록 유무와 관계없이 410으로 거절하고, 서버보다 5분 넘는 미래 시각이나 누락된 생성 시각은 400으로 거절합니다.

`GET /api/admin/audit`는 `team_id IS NULL`인 공통 감사 로그만 반환합니다. `from`·`to`는 선택적인 `YYYY-MM-DD` 날짜이며 한국 시간 기준 양 끝 날짜를 포함합니다. `actorId`·`action`을 함께 지정할 수 있습니다. 목록은 전후 JSON 없이 `entries`와 `nextCursor: {createdAt, id} | null`을 반환하며 한 번에 최대 50건입니다. 다음 페이지는 `cursorAt`·`cursorId`를 함께 보내고 `(created_at,id)` 내림차순으로 이어갑니다. 상세는 `GET /api/admin/audit/:id`의 `{before,after}`로 별도 조회합니다. 팀 이력·없는 이력·정리된 이력은 상세 API에서 404, 시스템 관리자가 아닌 계정은 목록·상세 모두 403입니다. 공통 범위 전용 날짜·ID 인덱스로 탐색하며 조회 자체는 새 이력을 만들지 않습니다.

`GET /api/admin/history-cleanup/storage`는 시스템 관리자에게 팀별 저장 본문 용량과 최근 정리 결과를 반환합니다. 단일 팀 재시도는 해당 팀에, 여러 팀의 공유 재시도·변경 없는 요청의 재시도 기록과 `team_id IS NULL` 이력은 `system` 범위에 한 번만 집계합니다. 업무·설정·필터·보기 JSON, 공유 문서 버전 본문, 압축 사본 BLOB, 가져오기 본문·결과, 이력 전후 JSON, 셀 재시도 메타데이터의 바이트 수이며 DB 물리적 파일 크기는 아닙니다. 공용 `styles.data`는 `system` 범위에 한 번만 집계합니다. 정수 참조·행 메타데이터·인덱스의 물리 저장량은 포함하지 않습니다.

`GET /api/admin/history-cleanup?scopeId=팀UUID&beforeDate=YYYY-MM-DD`는 해당 범위와 날짜 이전의 전체·삭제 가능 건수 및 바이트 수, 15분 유효 토큰을 반환합니다. `scopeId=system`은 시스템 공통만 의미하며 모든 팀 범위는 없습니다. `beforeDate`의 한국 시간 00:00을 UTC `cutoff`로 바꾸어 `created_at < cutoff`를 적용합니다. 2000년 1월 1일부터 오늘까지 선택할 수 있습니다. `retentionDays` 방식은 지원하지 않습니다.

`POST /api/admin/history-cleanup`에 `{token, confirmed: true}`를 보내면 토큰에 고정된 범위를 최대 500건/10MiB씩 삭제하고 `deleted` 누계·`batch` 건수·`hasMore`를 반환합니다. 셀 재시도는 선택 날짜 이전이면서 7일+시각 오차 5분이 지난 기록만 삭제합니다. 유효한 단일·다중 팀 재시도 참조 이력은 보호합니다. 정리 결과는 선택한 팀(`system`은 NULL)에 기록합니다. 팀별 이력 날짜 인덱스와 셀 재시도의 단일 팀/공유 범위를 구분하는 표현식 날짜 인덱스로 대상을 찾습니다.

XLSX 가져오기 작업은 작은 결과 응답을 직접 저장합니다. 팀 영구 삭제는 셀 재시도 참조의 `teamId`로 연결된 기록을 제거하므로 해당 이력이 먼저 없어졌더라도 정리할 수 있습니다. 보관기간과 정리 절차는 [운영 안내](OPERATIONS.md#이력-보관과-정리)을 참고하세요.

## 서식 저장과 전송

`shared/compact.js`가 화면의 긴 속성명과 저장·전송 형식을 연결합니다. 서식을 포함하는 JSON은 `{ "$styles": [서식 사전], "$data": 본문 }`입니다. 본문의 `style`·`defaultStyle`·`rowStyle`은 `{ "$s": 0 }`처럼 사전의 0부터 시작하는 인덱스를 참조합니다. 참조 객체를 사용하므로 이름이 `style`인 사용자 속성의 숫자 값·열 너비와 혼동하지 않습니다. 빈 서식 `{}`는 참조보다 짧으므로 그대로 둡니다. 공통 행·열 규칙이 있으면 `$formats` 배열도 포함하고 업무의 `formatting`은 `{$f: 인덱스}`로 참조합니다. 여러 업무에 같은 규칙 집합을 반복하지 않습니다. 서식과 공통 규칙이 모두 없는 메시지는 사전 없이 그대로 보냅니다. 사전은 요청·응답·SSE 이벤트·이력 JSON·사본마다 독립적이며 DB의 서식 ID를 외부로 노출하지 않습니다. 클라이언트는 `pack`/`unpack`, 문자열은 `stringify`/`parseCompact`를 사용합니다. 서버는 참조를 풀어 기존 권한·값·서식 검증을 수행합니다.

### 저장 형식과 내부 모델

앱 내부에서 셀을 계산할 때는 `backgroundColor` 같은 긴 이름을 사용합니다. **SQLite·API·변경 이력에 저장한 JSON은 아래처럼 축약합니다.** 변경 이력 화면의 JSON도 동일한 저장 형식으로 표시하며 긴 이름으로 풀어 보여 주지 않습니다. 이력의 작업명·범위·색상 설명은 사람이 읽을 수 있는 요약입니다.

아래는 같은 배경색의 두 셀을 담은 본문 예시입니다. 비어 있고 개별 서식도 없는 나머지 주차는 `cells`에 없습니다.

```json
{
  "$styles": [{ "bg": "#e5effc" }],
  "$data": {
    "cells": {
      "2026-10-19": { "value": "착수", "style": { "$s": 0 }, "version": 1 },
      "2026-11-02": { "value": "검토", "style": { "$s": 0 }, "version": 1 }
    }
  }
}
```

`$s: 0`은 **이 JSON의** `$styles[0]`을 참조한다는 뜻입니다. SQLite에서는 별도의 `styles.id` 정수를 참조합니다. 둘은 같은 번호 체계가 아닙니다. 해당 배경색을 행 전체에 지정했다면 위처럼 각 셀에 넣는 대신 [행·열 공통 서식](#행열-공통-서식)의 규칙 하나에 둡니다.

### 서식 키 대응

| 화면의 이름 | 저장·전송 키 |
| --- | --- |
| `borderTop`, `borderRight`, `borderBottom`, `borderLeft` | `bt`, `br`, `bb`, `bl` |
| `color`, `backgroundColor` | `c`, `bg` |
| `fontFamily`, `fontSize` | `ff`, `fs` |
| `textAlign`, `verticalAlign`, `textMode` | `ta`, `va`, `tm` |
| `bold`, `italic`, `underline`, `strike` | `b`, `i`, `u`, `s` |

테두리 값은 `[선 종류, 색상]` 또는 `null`입니다. 예를 들어 `{"br":["double","#856060"],"bg":"#d1eee6"}`입니다. 동일한 내용의 서식은 키 순서와 관계없이 사전에서 한 번만 기록합니다. gzip 전에도 중복을 제거하며 일반 HTTP 응답의 gzip 압축은 계속 사용합니다.

SQLite의 `styles(id,data)`에는 같은 내용의 축약 서식 JSON을 한 번만 저장합니다. 예를 들어 1,000개 셀이 같은 파란 배경을 쓰면 파란 배경 JSON은 한 행에만 두고, 각 셀은 그 서식 ID를 참조합니다. `cells.style_id`, `tasks.default_style`, `tasks.row_style`, `format_rules.style_id`가 참조하며 0은 빈 서식입니다. 업무 조회는 사용한 서식만 묶어서 읽고 각각 한 번씩 해석합니다. 변경 후 더 이상 참조하지 않는 서식은 제거하며, 이력·사본은 독립적인 사전으로 복원할 수 있습니다.

신규 업무에서는 값이 빈 문자열이고 유효한 개별 서식도 없는 셀을 만들지 않습니다. 누락 셀은 `{value:"", style:{}, version:0}`으로 읽습니다. 셀에는 업무 기본 서식과 행·열 공통 서식을 합친 결과와 다른 항목만 저장하되, 상속 해제용 `null`, `none`, `false`, 숫자 `0`, 주차 경계선보다 우선하는 명시적 테두리는 유지합니다. 이미 편집한 셀을 비워도 버전을 잃지 않도록 최소 셀 레코드를 유지합니다.

### `version`과 `revision`을 남기는 이유

`version: 1`은 서식 버전이나 생략 가능한 기본값이 아니라 **처음 저장된 셀의 수정 번호**입니다. 같은 업무를 만들면서 여러 셀이 함께 생성되면 각 셀의 첫 번호가 모두 `1`입니다. 값·개별 서식이 실제로 바뀔 때 해당 셀 번호를 올립니다. 이미 저장한 셀을 비워도 번호를 유지하며, 이후 다시 쓰면 다음 번호로 증가합니다. 저장 기록이 전혀 없는 셀만 `0`으로 취급합니다.

예를 들어 두 사람이 같은 셀의 `version: 1`을 읽고 편집했다면 먼저 저장한 요청은 `2`가 됩니다. 뒤늦은 요청은 `expectedVersion: 1`과 현재 번호 `2`가 달라 409로 거절합니다. 번호가 없으면 다른 사람의 수정이나 실행취소 이후의 편집을 조용히 덮어쓸 수 있습니다. 따라서 현재 JSON은 `version` 이름과 값을 명시적으로 유지합니다. 서식 키만 축약하며 모든 필드명을 임의로 줄이지 않습니다.

| 번호 | 대상 | 역할 |
| --- | --- | --- |
| 셀 `version` | 개별 셀 | 값·개별 서식 저장, 실행취소, 늦은 응답의 충돌 검사 |
| 문서 `revision` | 업무별 Markdown 본문 | 자동 저장과 동시 문서 수정의 충돌 검사 |
| 공통 서식 `revision` | 팀의 행·열 규칙 집합 | 공통 서식 저장·복원, 셀 예외를 계산한 기준 확인 |
| 팀 설정 `revision` | 팀 설정 | 속성·기본 서식 등 설정의 동시 수정 검사 |
| `schemaVersion` / `SCHEMA_VERSION` | JSON 반출 / SQLite 구조 | 파일·DB 형식 구분; 사용자의 편집 횟수와 무관 |

행 전체의 배경색을 바꿀 때는 공통 서식 `revision`을 올리고, 비어 있는 주차의 셀이나 `version`을 만들지 않습니다. 기존 셀 예외를 제거해야 하는 셀만 개별 번호도 올립니다. 변경이 없는 재적용은 어느 번호도 올리지 않습니다.

### 행·열 공통 서식

행 전체·열 전체 선택은 `/api/cells/batch`의 `format` 요청으로 저장합니다. `format_rules`의 규칙 하나는 `{id, rows, keys, excludeKeys, style, orders}`입니다. `rows`는 업무 ID 배열, `keys`는 실제 열 키 배열입니다. `keys: null`은 해당 업무의 모든 열을 뜻하므로 아직 값이 없는 주차와 앞으로 표시할 주차도 포함합니다. 날짜 키는 계속 `YYYY-MM-DD`를 사용합니다. `format_states`에는 팀별 서식 변경 번호만 저장합니다. 같은 선택 범위를 다시 적용하면 해당 규칙을 갱신하며 셀별 복사본을 만들지 않습니다. 선택 범위 중복 검사용 `selector`는 행·열 목록의 SHA-256 해시입니다.

화면의 선택 범위는 필터를 통과한 업무 ID를 사용하며 숨긴 행·열도 포함합니다. 필터에서 제외한 행은 영향을 받지 않습니다. 열 선택은 선택 당시 업무와 실제 날짜·속성 키에 고정됩니다. 행 선택은 업무 ID에 연결되어 월 이동·순서 변경·다음 연도 표시에도 이어집니다. 예를 들어 행 전체에 배경색을 적용하고 2026년 12월에서 2027년 1월·2월로 이동해도 새 주차의 셀을 추가 저장하지 않고 같은 규칙으로 표시합니다.

표시 순서는 업무 기본 서식 → 공통 규칙 → 셀 예외입니다. 행·열 규칙이 겹치면 `orders`에 기록한 속성별 적용 순서가 최신인 값이 우선합니다. 따라서 행에 배경색을 적용한 뒤 열에 글자 크기를 적용해도 행 배경색은 유지됩니다. 한 셀의 배경색만 바꾸면 그 색만 예외로 저장합니다. 이후 같은 열의 배경색을 다시 지정하면 해당 셀의 배경색 예외만 제거하고 다른 예외는 보존합니다. 상속을 해제하는 속성의 `null`은 필요한 경우에만 저장합니다.

테두리는 선택 영역의 안쪽·바깥쪽이 다르므로 같은 패턴끼리 묶습니다. 행 내부의 공통선은 계속 이어지고, 선택 당시의 왼쪽·오른쪽 끝선은 실제 열 키에 고정됩니다. 이 경우에도 빈 주차별 셀 레코드는 만들지 않습니다. 행을 복사·삽입할 때는 계속 이어질 서식을 `rowStyle` 하나로 복사하고 날짜별 차이만 셀에 둡니다. 원본 행의 이후 수정은 복사한 행에 영향을 주지 않습니다.

`format`은 `teamId`, `expectedRevision`, `scopes`, `expectedTasks`를 받습니다. 범위는 `{rows, keys, excludeKeys?, style, reset?}`이고, `expectedTasks`는 선택한 업무의 `updatedAt`입니다. 편집 권한·팀·속성·업무시각·공통 서식 버전을 모두 확인한 뒤 규칙과 기존 셀 예외를 한 트랜잭션으로 바꿉니다. 일반 셀 서식 수정에도 `expectedFormatRevision`을 보내므로 오래된 공통 서식을 기준으로 만든 예외가 저장되지 않습니다. 값만 바꾸는 요청은 공통 서식 버전과 독립적입니다.

공통 서식 변경 이력은 `action: "format"`, 재시도 기록은 `kind: "format-audit"`로 저장합니다. 감사 이력에 규칙과 실제 변경한 셀 예외의 전후 내용을 보관하고, 재시도 기록은 이력 ID만 참조합니다. 실행취소·재실행은 같은 이력 경로를 사용하며 이후의 공통 서식 변경이나 해당 셀의 후속 수정이 있으면 409로 거절합니다. 동일한 서식을 다시 적용해 실제 변경이 없으면 규칙·셀 버전·감사 이력을 늘리지 않습니다.

다음 사례를 동작 기준으로 삼습니다.

| 순서 / 상황 | 표시 결과 | 저장 결과 |
| --- | --- | --- |
| A·B 업무의 10월 19일 열을 파랑으로 지정 | 해당 두 셀이 파랑 | `rows: [A, B]`, `keys: ["2026-10-19"]` 규칙 하나 |
| A 업무의 그 셀만 빨강으로 변경 | A는 빨강, B는 파랑 | A 셀에 빨강 배경색 예외만 저장 |
| 같은 열을 초록으로 다시 지정 | A·B 모두 초록 | 공통 규칙 갱신, 해당 배경색 예외 제거; 다른 속성 예외는 유지 |
| A 업무 행 전체를 노랑으로 지정 | A의 모든 열이 노랑 | `rows: [A]`, `keys: null` 규칙 하나 |
| 12월에서 다음 해 1월·2월로 달력 이동 | A의 새 주차도 노랑 | 규칙 재사용; 빈 주차 셀 추가 없음 |
| 10월 19일 열만 지정한 뒤 다음 해 같은 주차로 이동 | 다음 해 열에는 그 규칙을 적용하지 않음 | 열 규칙은 `2026-10-19`에 고정 |

행 규칙은 같은 업무 ID를 따라갑니다. 같은 업무를 다음 연도에도 표시하면 서식이 이어지지만, 관계없는 새 업무에 자동 적용하지 않습니다. 업무 복제·행 삽입은 앞에서 설명한 복사 규칙을 따릅니다.

실시간 업무 응답은 팀의 공통 서식 상태를 공유하고 `$formats`로 한 번만 전송합니다. 반면 개별 업무의 생성·이동·삭제 이력은 독립적인 기록이므로 `taskAuditSnapshot`으로 그 업무에 적용되는 규칙만 남기고 다른 업무 ID도 반복하지 않습니다. 해당 규칙이 없으면 이력의 `formatting`을 생략합니다. 공통 서식 변경 이력 자체는 재시도·복원에 필요한 규칙 집합의 전후 상태를 보존합니다.

아래 업무·셀 예시는 압축을 해제한 내부 모델입니다. 실제 JSON API·JSON 반출과 이력·사본 저장에는 위 공통 사전을 적용합니다.

## 업무와 셀

계정의 `username`은 로그인 아이디(이메일)입니다. 생성·수정 요청은 이메일 형식만 받으며 앞뒤 공백을 지우고 소문자로 저장합니다. `PATCH /api/admin/users/:id`에서 `username`을 생략하면 유지합니다. 계정의 `avatarInitials`는 빈 문자열(이름 첫 글자), 영문·숫자 1~3자 또는 한글 1~2자이며 `avatarImage`는 빈 문자열 또는 PNG·JPEG·WebP data URL입니다. `color`는 아바타 배경색(`#RRGGBB`)입니다. 계정 생성·수정 API에 선택적으로 전달하며 생략한 필드는 기존 값을 유지합니다. `PATCH /api/auth/profile`은 로그인한 본인의 `name`, `color`, `avatarInitials`, `avatarImage`만 수정하고 갱신된 `user`를 반환합니다. 아이디·비밀번호·시스템 권한·소속 변경 필드는 받지 않습니다. 이미지는 클라이언트에서 160×160으로 맞추고 서버에서 형식·150,000자 한도를 검사합니다. `users.system_role`은 시스템 권한(`admin`·`user`), `memberships.role`은 팀 내 권한(`lead`·`member`·`viewer`)입니다. 계정 응답은 `systemRole`, `teamIds`, `teamRoles`(팀 ID별 팀 내 권한)를 가집니다. SQLite 스키마는 `server/db.mjs`의 `SCHEMA_VERSION`(`PRAGMA user_version`)으로 표시합니다. v27은 새 DB에서 시작합니다. 이전 버전 DB는 열기를 거절하며 자동 변환·삭제하지 않습니다. `scripts/restore.mjs`는 같은 스키마 버전의 백업만 복구합니다.

`bootstrap.users`에는 접근 가능한 팀에 현재 배속된 계정과 그 팀 업무의 Member 셀에 참조된 이전 팀원의 최신 프로필이 포함됩니다. 표시 목록과 선택 목록을 구분하며 선택·필터에는 현재 팀의 `teamRoles`가 팀장(`lead`)·팀원(`member`)인 계정만 사용합니다. 서버는 해당 셀에 남아 있는 이전 팀원 ID만 보존하도록 허용하고, 제거 후 재배정은 거절합니다. 내보내기와 새 사본에도 이전 팀원의 프로필을 포함합니다.

압축을 해제한 업무 객체는 `id`, `teamId`, `years`, `position`, `defaultStyle`, `createdBy`, `createdAt`, `updatedAt`, `deletedAt`, `cells`를 가집니다. 공통 서식이 있으면 `formatting`을, 복사한 행의 공통 서식이 있으면 `rowStyle`을 포함합니다. 셀 키는 팀 설정에 정의된 활성 속성 ID 또는 주의 월요일 날짜이며, 정의되지 않은 키는 거절합니다. 기본 속성은 `title`, `owner`, `status`이고, 예시 양식(`shared/coreProperties.js`의 `sampleProperties`)은 `category`, `type`, `description`, `supporters`, `progress`, `deadline`, `score`, `current`를 더합니다. 화면에서 추가한 속성은 앱이 만든 짧은 ID(`p` + base36 6자리, 예 `p7k2mq`)를 키로 씁니다. 날짜 키 하나를 두 연도에서 조회하더라도 같은 값입니다. 연말의 일부 주는 앞·뒤 연도에 걸쳐 표시될 수 있습니다.

```json
{
  "value": "검토\n완료 예정",
  "style": {
    "color": "#243642",
    "backgroundColor": "#d1eee6",
    "fontFamily": "Noto Sans KR",
    "fontSize": 11,
    "textAlign": "left",
    "verticalAlign": "middle",
    "bold": false,
    "italic": false,
    "underline": false,
    "strike": false,
    "textMode": "wrap"
  },
  "version": 3
}
```

예시 양식에서 `owner`는 사용자 ID 또는 빈 문자열, `supporters`는 사용자 ID 배열입니다. `score`와 `current`는 숫자 또는 빈 문자열입니다. `progress`는 최대 10,000자의 일반 텍스트로, 백분율·문구·줄바꿈을 그대로 저장합니다. 엑셀 가져오기는 진척률 문구를 다른 필드로 옮기지 않고, 백분율 서식의 숫자는 `37.5%`처럼 변환합니다. `deadline`은 날짜 또는 빈 문자열입니다. `title`·`description`과 주차 셀은 텍스트이며, `category`·`type`·`status`는 선택형으로 값은 옵션 ID입니다. 모든 속성의 값은 아래 종류별 계약을 따릅니다.

주차 셀의 빈 값에도 배경색을 저장할 수 있습니다. 색상은 `#RRGGBB`, 글자 크기는 6~36pt 정수이며 새 팀의 기본 크기는 9pt입니다. 지원 글꼴은 Noto Sans KR·Pretendard·맑은 고딕·Noto Serif KR·Nanum Gothic Coding입니다. `맑은 고딕`은 저장 이름이며 HTML/XLSX 가져오기에서는 `Malgun Gothic`도 같은 이름으로 정규화합니다. 실제 화면은 설치된 맑은 고딕이 없으면 자체 제공 Pretendard로 표시하지만 저장된 글꼴 이름은 유지합니다.

셀·기본 서식의 `borderTop`, `borderRight`, `borderBottom`, `borderLeft`는 선택적인 `{style, color}` 또는 `null`입니다. `style`은 `none`·`solid`·`medium`·`thick`·`dashed`·`double`, `color`는 `#RRGGBB`입니다. 화면의 **점선**은 `dashed`입니다. 누락 값은 업무 기본 서식과 행·열 공통 서식을 상속하며 상속된 선이 없으면 기본 격자선을 유지합니다. `null`은 상속된 선까지 해제해 기본 격자선을 표시하고 `none`은 기본 격자선까지 숨깁니다. 테두리 스타일의 **기본 테두리**는 선택한 위치에 `null`을 요청하며, 테두리 도구의 지우기는 네 방향의 해제를 요청합니다. 저장 시 상속된 선이 없는 방향의 `null`은 생략합니다. 선택 영역의 맞닿은 안쪽 경계는 위·왼쪽 셀의 `borderBottom`·`borderRight`에만 선을 저장하고 아래·오른쪽 셀의 `borderTop`·`borderLeft`는 `null`로 해제합니다. 상속 해제가 필요하지 않은 `null`은 저장하지 않습니다. XLSX는 thin/medium/thick/dashed/double을 대응시키며 `null`은 선 없이 반출하고 대각선은 지원하지 않습니다. 기본 서식이나 가져온 셀 양쪽에 명시된 선이 겹치면 화면과 미리보기에서 더 굵은 선을 한 번만 표시하고, 굵기가 같으면 위·왼쪽 셀의 선을 표시합니다. 저장한 서식은 변경하지 않습니다. HTML·앱 클립보드와 실행취소도 네 방향을 보존하며 HTML의 `data-grid-borders`는 기본 격자선으로 해제한 방향을 기록합니다.

업무의 `defaultStyle`은 일반 생성 시 팀의 기본 서식을, 행 위·아래 삽입 시 기준 행의 기본 서식을 복사한 값입니다. 셀 서식이 이를 덮어쓰며, 빈 일정 셀도 업무 기본 서식을 사용합니다. 텍스트에 포함된 수식이나 HTML을 실행하지 않습니다.

텍스트의 `#` + 여섯 자리 숫자는 화면에서 `http://redmine.somansa.com/redmine/issues/{숫자}` 링크로 표시합니다. 원문·복사·저장 값은 바꾸지 않습니다. 여러 이슈 번호는 각각 연결하며 HTTP(S) URL 안의 `#`는 별도 이슈로 해석하지 않습니다.

`textMode`는 `overflow`(기본)·`wrap`·`clip` 중 하나이며 `verticalAlign`과 독립적입니다. 값이 없으면 오버플로우입니다. HTML 클립보드는 `data-text-mode`로 자르기와 오버플로우를 구별합니다. 오버플로우는 연속된 빈 셀과 같은 고정 영역 안에서만 표시합니다. 줄바꿈 변경은 정렬 값을 덮어쓰지 않으며, 기본 서식과 HTML 복사도 선택한 정렬을 보존합니다. 화면에서는 내용이 셀 높이를 넘을 때만 첫 줄부터 표시하고, 이는 저장된 정렬을 변경하지 않습니다. 새 팀의 기본 세로 정렬은 중간입니다. 기존에 저장한 위 정렬도 자동 변경하지 않습니다.

셀의 `version`은 동시 수정 검사에 사용합니다. 수정 요청은 클라이언트가 읽은 `expectedVersion`을 보내고, 현재 버전과 다르면 HTTP 409를 받습니다. 범위 변경은 한 트랜잭션으로 처리합니다. 같은 사용자·`operationId`의 재시도는 최초 성공 결과를 재사용합니다. 서버에서 수신한 최신 버전을 확인한 뒤 새 `operationId`로 재적용해야 합니다.

여러 영역 선택은 UI 상태의 `areas`와 활성 `anchor`·`focus`로 표현하며 저장 보기에 포함하지 않습니다. 영역이 겹치면 셀 ID를 중복 제거하여 동일 배치에 한 번만 포함합니다. 숨긴 행의 번호·구간은 필터와 정렬을 적용한 결과에서 개인 숨김을 제외하기 전 순서로 계산합니다.

## 업무 문서

업무마다 최대 50개의 문서를 보관합니다. 문서는 `id`(`main` 또는 UUID), `title`(보관 형식 최대 80자), Markdown 본문을 가지며 본문은 UTF-8 256KiB 이하입니다. 새 문서 추가·이름 변경에서 입력하는 제목은 원본과 사본 모두 1~50자로 제한합니다. 기존 보관 제목은 변경하거나 잘라내지 않습니다. 저장 전에는 빈 `main` 문서(문서 1, revision 0)를 표시하며 조회만으로 DB 행을 만들지 않습니다.

`document_versions`는 내용 해시로 중복을 제거하는 불변 본문 저장소입니다. `task_documents`는 `(task_id,id)` 기본키, `title`, `position`, `version_id`, `has_content`, 정수 `revision`, `updated_at`, `actor_id`, 재시도용 `operation_id`·`request_hash`를 보관합니다. 실제 원본 문서 저장은 문서 revision·업무 시각·감사 기록을 같은 트랜잭션에서 갱신합니다. 본문을 비워도 revision을 유지합니다.

사본 BLOB의 각 업무는 `documents: [{id,title,versionId,hasContent}]`로 문서 목록·제목·순서를 보관합니다. 최신 본문 버전의 기준은 `report_documents`의 `(report_id,task_id,document_id)` 기본키와 `version_id` FK입니다. 기존 문서의 본문 자동 저장은 이 참조만 교체하며 표 BLOB을 다시 압축하지 않습니다. 따라서 BLOB에 남은 `versionId`·`hasContent`는 이전 값일 수 있고, 조회·표 편집·복제·반출·이력 복구는 `readReport`로 최신 참조와 내용 유무를 합칩니다. 문서를 추가·삭제하거나 제목을 바꿀 때는 BLOB의 목록과 참조를 같은 트랜잭션에서 갱신합니다. 처음에는 불변 본문을 공유하며 `sourceVersionId`나 최초 분기 참조는 저장하지 않습니다. 어떤 원본/사본에서도 사용하지 않는 이전 버전은 정리합니다. 원본과 각 사본의 문서 목록·제목·내용은 서로 독립적입니다.

일반·삭제 상태 업무 목록과 사본 표 조회에는 본문·문서 목록을 보내지 않습니다. 내용이 있는 문서가 하나라도 있을 때 `hasDocument: true`를 제공하며, `documentCount`는 빈 문서를 포함한 저장된 문서 수입니다. 개수는 기존 문서 목록에서 계산하며 별도 DB 열을 추가하지 않습니다. 문서 목록은 제목 탭을 열 때, 본문은 해당 탭을 처음 열 때 조회합니다. 문서별 편집기는 방문한 탭 안에서 유지해 원문 모드·입력·실행취소를 보존합니다.

| API (원본/사본 각각 동일한 문서 동작) | 의미 |
| --- | --- |
| `GET /api/tasks/:id/documents` | 문서 ID·제목·내용 유무·revision 목록. `?content=1`은 행 복사에 필요한 전체 본문 조회 |
| `POST /api/tasks/:id/documents` | `{id:UUID,title?}`로 추가. 제목 1~50자. 같은 ID의 재시도는 중복 생성하지 않음 |
| `GET/PUT /api/tasks/:id/documents/:documentId` | 조회 / `{markdown,expectedRevision,operationId}`로 독립 저장 |
| `PATCH /api/tasks/:id/documents/:documentId` | `{title,expectedTitle}`로 이름 변경. 새 제목 1~50자, 이전 이름 충돌 검사 |
| `DELETE /api/tasks/:id/documents/:documentId` | `{expectedRevision}`으로 해당 문서만 삭제 |
| `/api/reports/:id/tasks/:taskId/documents` 및 `/:documentId` | 같은 목록·추가·조회·저장·이름 변경·삭제 동작. 문서 revision은 불변 버전 UUID(빈 초기 문서는 0) |
| `POST .../documents/:documentId/images` | multipart 이미지 업로드. 문서 존재 및 편집 권한 확인 |
| `GET /api/document-images/:teamId/:hash.webp` | 로그인·팀 접근 검사 후 이미지 제공 |

`/document`는 기본 `main` 문서의 단일 조회/저장 경로로도 제공합니다. 분기 목록과 `/document-versions/:id` 조회 API는 삭제했습니다. 원본은 해당 업무의 `canEdit`, 사본은 해당 팀의 `canContribute`를 검사합니다. 열람자와 팀 외부 사용자의 쓰기를 차단합니다.

문서와 표의 낙관적 잠금은 독립적입니다. 사본 표 revision은 `documents`·`hasDocument`·`documentCount`를 제외한 JSON의 SHA-256입니다. 압축 BLOB의 해시를 키로 계산 결과 최대 256개를 재사용하며, 이미 해제한 표를 다시 해제하지 않습니다. 문서 저장은 해당 관계형 참조만 교체하고 표 저장은 최신 문서 참조를 보존합니다. 원본·사본 모두 브라우저에서 자동 저장하며, 동일 요청·작업 ID·기준 revision의 응답 유실 재시도는 중복 반영하지 않습니다. 충돌은 409와 최신 문서를 반환하고 브라우저는 입력을 보존합니다.

업무 복제·행 붙여넣기는 `documents: [{id,title,markdown}]` 배열을 포함할 수 있습니다. 빈 행 삽입은 문서를 복사하지 않습니다. 업무 삭제는 문서를 유지하고 팀 영구 삭제는 관련 참조와 본문을 삭제합니다. SQLite 백업은 모든 문서·참조를 포함합니다. JSON 반출 형식은 **v5**이며 원본/사본 문서 참조를 `documents: [{id,title,markdown}]`로 풀어 제공합니다. XLSX·CSV와 셀 클립보드에는 문서 본문을 포함하지 않습니다.

### 문서 이미지 파일

`DOCUMENT_IMAGES_DIR`(기본 `data/document-images`) 아래 `<teamId>/<SHA-256>.webp`에 저장합니다. SHA-256은 변환된 파일 바이트 기준이며 같은 팀에서 중복을 제거합니다. Markdown에는 `/api/document-images/<teamId>/<hash>.webp`를 넣고 표시 너비를 지정하면 `#width=320` 같은 URL fragment를 붙입니다. 허용 너비는 정수 32~4096px이며 이미지 비율은 유지합니다. 이 값은 표준 Markdown 이미지 URL 안에 보존되며 별도 DB 컬럼이나 HTML 태그를 만들지 않습니다. 파일 조회·백업·JSON 이미지 목록은 fragment를 제외한 주소로 중복을 제거하므로 여러 크기도 파일 하나를 공유합니다. 저장할 때 실제 이미지 노드·참조 이미지의 팀과 파일 존재를 검사하고 코드 블록의 예제 문자열은 참조로 취급하지 않습니다. 리치 에디터는 이 관리 주소만 이미지로 표시합니다.

업로드는 10MiB·4천만 화소 이하 PNG/JPEG/WebP 정지 이미지만 허용합니다. 실제 이미지 디코딩, 방향 보정, 최대 4096×4096 안으로 축소, WebP 재인코딩을 거쳐 원본 메타데이터·실행 가능한 파일을 게시하지 않습니다. 비동기 변환 후 세션·권한을 다시 검사합니다. 파일은 변경하지 않으며 완성된 임시 파일을 원자적으로 게시합니다. 문서·사본 복사 때 이미지 바이트는 복사하지 않습니다. 이미지의 크기는 문서 Markdown 256KiB 제한 및 DB 논리 용량 집계에 포함되지 않습니다.

현재 사용하지 않는 업로드 파일은 자동 삭제하지 않습니다. 문서 취소·이미지 제거 후에도 다른 문서/사본·복사한 행에서 재사용할 수 있으므로 남겨 둡니다. 일반적인 미사용 파일 수명 정리는 별도 과제이며, 팀 영구 삭제 시에는 그 팀의 이미지 폴더도 삭제합니다. 백업은 일관된 DB 사본의 모든 문서 버전이 참조하는 파일만 `<백업.sqlite>.images`에 수집하고 해시를 검증합니다. 복구는 이 동반 폴더를 함께 받아 설정한 이미지 경로에 배치합니다. JSON 반출은 내보낸 원본·사본 본문에 필요한 이미지를 `documentImages: [{url, mimeType, base64}]`로 중복 없이 포함합니다. 반출 형식 v4의 선택적 필드이며 JSON 직접 가져오기는 제공하지 않습니다.

## 보기·사본·계정

새 보기의 열 고정 기본값은 `frozenColumns: 0`입니다. 팀 설정의 `defaultDensity`는 `comfortable`(넉넉하게)·`compact`(편안하게, 기본)·`dense`(촘촘하게)이며 기본 서식 화면에서 저장합니다. 설정 저장에서 생략하면 현재 팀 값을 유지합니다. `dense`는 `compact`의 약 2/3(기본 서식에서 26px)입니다. 개별 `rowHeights`는 26~500px을 허용하며 팀 기본 높이보다 우선합니다. 사본은 저장 당시 팀 설정의 높이를 사용합니다.

기간 선택 표는 `weeksForPeriod(year, startMonth)`로 생성합니다. 주차 키는 월요일 날짜이며 주를 한 번씩 생성하므로 연말 중복이 없습니다. 월 배정은 범위 안의 금요일을 우선하고 경계 주는 월요일 또는 일요일로 보정합니다. `fromMonth`·`toMonth`·`collapsedMonths`는 달력에 나열된 12개월 중 1부터 시작하는 위치입니다. 예를 들어 시작 월이 2월이면 12번은 다음 해 1월입니다. 조회 연도는 1월 시작일 때 기준 연도 하나, 나머지는 기준 연도와 다음 연도 두 개입니다. 2100년은 1월 시작만 허용합니다. 월 드래그는 `fromMonth`·`toMonth`를 설정하고 주 범위를 비우며, 주 드래그는 `fromWeek`·`toWeek`와 전체 월 범위를 설정합니다. 두 선택 모두 `hiddenWeeks`·`collapsedMonths`를 비워 연속 범위를 표시합니다. 드래그 중에는 미리보기만 바꾸고 포인터를 놓을 때 한 번 저장합니다.

셀 복사 단축키는 `application/x-weekly-plan-cells+json` (`version: 1`, `rows: {text, style}[][]`)과 `text/html`, `text/plain`을 함께 제공한다. 속성·담당자는 표시명으로 전달하고 대상 열의 옵션·사용자에 다시 연결한다. 출처 셀의 적용된 서식과 기본값을 복사하여 대상 업무의 기본 서식이 남지 않도록 한다. 붙여넣기 시 지원하는 서식 필드만 허용하고 HTML을 화면에 삽입하지 않는다. 일반 텍스트에는 서식 변경을 포함하지 않는다. 행·열 크기와 속성의 칩 정의는 셀 복사 대상이 아니다.

행 번호 메뉴의 복사는 시스템 클립보드와 별개로 메모리에 업무 사본과 개인 행 높이를 보관한다. 모든 셀의 값·서식과 업무 기본 서식·문서 본문을 복사하고 셀 버전·업무 ID는 새로 생성한다. 원본을 이후 수정해도 복사 당시 값은 유지한다. 팀·연도 전환이나 페이지 새로고침 시 초기화한다.

발표 모드는 현재 브라우저 화면 상태이며 DB·개인 보기에 저장하지 않는다. 필터·묶음·숨김·열 너비를 유지하고 메뉴와 편집 도구를 숨긴다.

표 배치는 사용자·팀·기준 연도별 시작 월(`startMonth`), 숨긴 업무 ID, 숨긴 주차, 접힌 월, 표시 열, 크기·묶음·정렬을 `views`의 `__current`에 저장합니다. 필터 조건은 이 저장 대상에서 제외합니다. 개인 보기의 숨김은 원본이나 접근 권한을 변경하지 않습니다. XLSX에서 가져온 숨김·크기도 표 배치에만 반영합니다.

필터는 연도 필드가 없는 `saved_filters`와 `filter_states`로 관리합니다. `saved_filters`는 `id`, `team_id`, `scope`, `owner_id`, `name`, `data`, `updated_at`을 저장합니다. `scope=team`은 `owner_id=NULL`이며 해당 팀에 접근할 수 있는 모든 사용자가 조회하고, 해당 팀의 `lead`만 저장·수정·삭제합니다. 시스템 관리자도 팀장으로 배속되어야 공용 필터를 편집할 수 있습니다. `scope=personal`은 `owner_id`인 본인만 조회·편집합니다. 이름은 팀 공용끼리, 또는 같은 사용자·팀의 개인용끼리 중복할 수 없습니다. 공용과 개인용 사이에는 같은 이름을 사용할 수 있습니다. 공개 범위는 생성 시 지정하며 수정 API에서는 변경하지 않습니다.

`filter_states`는 사용자·팀별 `selected_id`, `data`를 저장합니다. 저장 필터를 선택한 경우 조회 시 해당 항목의 최신 조건을 사용합니다. 항목을 삭제하면 선택만 해제하고 마지막 적용 조건은 유지합니다. 연도 전환은 필터 목록·조건·선택 상태를 조회하거나 저장하지 않습니다. API도 필터의 연도 입력을 받지 않습니다. 이전 저장 방식의 변환·호환 코드는 없습니다.

필터 `data`는 `propertyFilters`, `propertyFilterModes`만 허용합니다. `propertyFilters`는 속성 ID별 선택 값 배열이며, 같은 속성의 값은 OR, 서로 다른 속성은 AND로 평가합니다. 빈 배열은 필터 없음, 빈 문자열은 미지정 업무입니다. `propertyFilterModes`는 속성별 `include`(기본, 일치)·`exclude`(제외)입니다. 복수 Member의 빈 배열도 미지정으로 평가하며 선택 값이 없으면 모드와 관계없이 필터를 적용하지 않습니다. 보관된 속성의 조건은 현재 조건과 개인·공용 저장 필터에서 제거합니다. 필터 적용·해제는 행·열 숨김, 고정·크기·순서, 기간·묶음·정렬을 변경하지 않습니다. 팀원이 공용 필터의 조건을 바꾸면 공용 선택을 해제하여 개인의 현재 조건으로 사용하고 공용 원본은 수정하지 않습니다.

화면의 `View`와 사본은 표 배치와 필터 조건을 합친 사본입니다. JSON 반출은 `views`에 표 배치, `filters`에 조회 가능한 공용·본인 개인용 필터, `currentFilters`에 본인의 조건·선택을 각각 담습니다. 다른 사용자의 개인용 필터는 포함하지 않습니다. 현재 범위 내보내기는 선택한 업무와 열만 포함하며 전체 반출을 대신하지 않습니다.

`fromWeek`·`toWeek`는 월요일 날짜 키 또는 제한 없음을 뜻하는 빈 문자열입니다. 월 범위와 함께 표시할 주차를 제한합니다. `frozenColumns`는 왼쪽에서 고정할 업무 정보 열 수이며, `groupBy`는 묶음 속성 ID입니다. `sortKey`와 `sortDirection`(`asc`·`desc`·`default`)은 업무 정보 컬럼 정렬입니다. 주간 날짜 키는 정렬 대상에서 제외합니다. 그룹 제목은 별도의 업무 레코드가 아닙니다. 새 보기의 주간 열 기본 너비는 40px입니다. 보기의 `knownProperties`는 보기가 마지막으로 본 속성 목록으로, 그 뒤 추가된 속성은 기본 표시 여부(`visible`)에 따라 열에 더합니다.

사본은 보기의 12개월에 해당하는 두 연도 업무도 함께 검증·보관합니다. `tasks`, `users`, `view`, `settings`를 하나의 JSON으로 만든 뒤 gzip(level 1)으로 압축하여 `reports.data`에 BLOB으로 저장합니다. Base64 인코딩은 하지 않습니다. `users`에는 업무의 Member 셀(보관된 속성 포함) 또는 Member 필터에서 참조하는 사용자만 `{id, name}`으로 보관합니다. 아바타 이미지·글자·색상·계정 권한과 관계없는 팀원은 포함하지 않습니다. 업무 내용·셀 서식·보기·속성 정의는 유지합니다. 일반 저장과 XLSX 보고서 가져오기는 같은 저장 함수를 사용합니다. 조회와 JSON 반출은 gzip을 해제한 뒤 공통 서식 사전을 적용해 전송합니다.

`GET /api/reports/:id`는 팀 접근 권한을 확인한 뒤 사본의 사용자 ID로 현재 계정의 아바타를 조회하여 `users`에 `color`, `avatarInitials`, `avatarImage`를 추가합니다. 이름은 저장 당시 값을 유지하며, 이름 첫 글자 아바타는 현재 계정 이름에서 계산합니다. 현재 팀 소속이나 원본 업무에 남아 있지 않은 계정도 조회하고, 계정이 없으면 저장된 이름의 기본 아바타를 사용합니다. 계정 권한·로그인 정보는 응답에 추가하지 않습니다. 이 연결은 조회 시에만 수행하며 저장된 BLOB과 JSON 반출의 사본 데이터는 변경하지 않습니다.

사본 이름은 최대 50자이며 팀 안에서 연도·기준일과 무관하게 유일합니다. 앞뒤 공백을 제거하고 Unicode NFC로 정규화해 저장·비교하며 대소문자는 구분합니다. 일반 생성과 XLSX 보고서 가져오기는 삽입과 같은 `BEGIN IMMEDIATE` 트랜잭션 안에서 기존 이름을 검사하고 중복이면 HTTP 409(`details.code: DUPLICATE_REPORT_NAME`)를 반환합니다. 같은 가져오기 요청의 성공 재시도는 기존 응답을 반환합니다. 같은 기준일에는 서로 다른 이름으로 여러 사본을 만들 수 있으며 삭제한 이름은 재사용할 수 있습니다. 기존 자료의 이름을 일괄 변경하지는 않습니다. 계정 이름 변경이나 원본 업무 삭제가 과거 사본을 수정하지 않습니다. 이전 형식의 DB와 사본의 변환·호환 조회는 제공하지 않습니다. 새 사본은 이후 재시작에도 유지합니다.

팀원·팀장·시스템 관리자는 `PATCH /api/reports/:id`로 사본을 편집합니다. 요청은 `{operationId,revision,operations,view?}`이며 `cells`, `format`, `create`, `delete`, `reorder`, 실행취소용 `restore`를 지원합니다. 최대 1,000개 작업·200,000셀 변경을 허용하며 모든 작업을 같은 트랜잭션에서 검증·저장합니다. 사본의 속성 정의와 업무 ID만 해석하고 원본 업무·서식·보기·필터 테이블은 쓰지 않습니다. 브라우저는 입력을 즉시 표시하고 짧은 지연 후 자동 저장하며 저장 중 새 입력은 다음 요청으로 이어갑니다. 실패한 요청은 같은 ID로 재시도합니다. 저장 후 실행취소·재실행은 보상 작업을 저장합니다. `restore`는 기존 업무의 최신 문서를 유지하며 삭제된 행의 복원은 삭제 전에 읽어 보관한 문서 본문을 포함합니다. 원본으로 돌아가기 전 저장을 완료하며 오류가 있으면 탭 전환을 막습니다.

`POST /api/reports`의 선택적 `sourceId`로 기존 사본을 복제합니다. 클라이언트가 생성한 선택적 `id`(UUID)를 같은 요청의 재시도에 유지하면 최초 성공 결과를 돌려주고 중복 생성하지 않습니다. 요청 내용·수행자가 달라지면 충돌로 거절합니다. 이름 변경은 `PATCH /api/reports/:id/name`의 `{name,expectedName}`으로 처리하고 중복 이름·오래된 이름을 거절합니다. 조회·이름 변경은 별도로 표 revision을 바꾸지 않습니다.

사본 조회에는 현재 업무 화면의 연도 제한을 적용하지 않습니다. 날짜 열과 달력은 저장된 `year`, `view.startMonth`를 사용합니다. 닫을 때 현재 업무 화면의 연도·보기·스크롤을 복원하고 연간 보기나 필터 저장소에는 사본의 조건을 쓰지 않습니다. 선택 삭제는 모든 ID가 해당 팀의 사본인지 검사한 뒤 하나의 트랜잭션으로 삭제하며, 원본 업무를 유지하고 `report-delete` 이력을 남깁니다.

JSON 내보내기는 비밀번호·세션·전체 계정 권한을 포함하지 않습니다. 다른 시스템으로 옮길 때 사용자 ID를 매핑하고, 날짜 키·업무 ID·색상·사본을 유지해야 합니다. 현재 앱의 JSON 직접 재가져오기 기능은 없습니다. 완전 복구는 SQLite 백업으로 수행합니다. XLSX 가져오기는 새 업무 ID를 부여하며, 동일 파일 재시도용 키를 별도로 관리합니다.

## 동적 속성

팀 설정은 `theme`, `properties`, `defaultStyle`, `defaultDensity`, `weekHeader`, `revision`으로 이루어지며 `properties` 배열이 모든 업무 정보 열과 순서를 정의합니다. 속성은 `id`, `name`, `kind`, `display`, `values`, `visible`, 선택적인 `multiple`·`width`(기본 열 너비, 없으면 120px)·`placement`·`archived`를 가집니다. 속성 ID는 영문자로 시작하는 영문·숫자·`_`·`-` 60자 이내입니다. `kind`는 `option`·`text`·`date`·`number`·`member`입니다. Option의 `display`는 `text`·`round`·`square`·`dot`·`emoji`, Member는 `text`·`avatar`입니다. `title`은 항상 활성 Text이며 삭제·숨김·종류 변경을 거절합니다. `owner`는 삭제 불가한 단일 Member, `status`는 삭제 불가하고 활성 값이 하나 이상인 Option입니다. `supporters`는 선택 속성으로 보관·복원이 가능하며 복수 Member와 권한 연계를 유지합니다. 새 팀에는 `title`, `owner`, `status`만 생성합니다. 첫 설정에서 예시 업무를 선택한 팀과 XLSX 가져오기는 예시 양식 속성을 사용합니다. 기본 상태는 예정·검토 중·진행 중·완료·보류이며 옵션 ID는 `status-planned`·`status-review`·`status-progress`·`status-completed`·`status-paused`입니다. `POST /api/admin/teams`의 `templateTeamId`는 원본 팀 설정을 복사하며 새 revision은 0입니다. 속성·값·순서·표시·기본 서식·테마를 포함하고 업무·회원 배정·개인 보기는 복사하지 않습니다. 값 배열의 순서가 선택 목록·묶음 순서이며, 각 값에는 `id`, `label`, `backgroundColor`, `dotColor`, `emoji`, 선택적인 `archived`가 있습니다.

속성·선택값 ID는 팀 안에서 유일하면 되므로 앱이 `p`/`o` + base36 6자리로 만듭니다(기본 속성과 기본 상태값은 `title`, `status-planned`처럼 고정 이름). ID는 셀 키와 셀 값에 그대로 저장되므로 짧게 유지합니다. Option 셀 값은 옵션 ID, Text는 문자열, Date는 유효한 `YYYY-MM-DD`, Number는 유한한 숫자, 단일 Member는 소속 팀의 사용자 ID 또는 빈 문자열, 복수 Member는 중복 없는 사용자 ID 배열입니다. Number는 음수와 소수를 허용합니다. 속성·선택값의 이름을 바꿔도 ID는 유지되므로 셀·필터·사본은 바뀌지 않습니다. 설정의 `revision`을 보낸 수정 요청은 동시 관리자 변경을 검사합니다. 종류 변경 시 기존 값을 새 종류로 변환·검증하고 셀 버전과 이력을 함께 갱신합니다. 하나라도 변환에 실패하면 설정과 셀을 모두 되돌립니다. 제거된 정의는 보관하여 기존 셀을 설명할 수 있게 합니다. 사본은 `settings` 사본도 보존합니다.

새로 추가하거나 이름을 변경하는 속성 값은 최대 15자입니다. 화면의 `maxLength`와 서버의 설정 저장 검사를 함께 적용합니다. 저장 형식은 긴 값(최대 60자)을 읽을 수 있습니다. 기존 옵션 ID와 이름이 같으면 다른 설정 저장·보관을 허용하여 데이터와 과거 기록을 자르지 않습니다. 저장 전 빈 속성·값 초안을 지울 때는 보관 목록에 추가하지 않습니다.

`visible`은 열 표시 기본값입니다. 보기의 `columnVisibility`는 마지막으로 적용한 기본값을 기록하여 변경된 열만 반영하고 다른 개인 숨김은 보존합니다. 팀 설정의 속성 탭에서 현재 보기와 다른 기본값을 가진 열의 체크를 바꾸는 경우 현재 보기에도 직접 적용합니다.

속성의 `placement`는 `beforeWeeks`(기본) 또는 `afterWeeks`입니다. 표의 순서는 날짜 앞 속성 → 표시 중인 주차 날짜 → 날짜 뒤 속성이며, 각 쪽 안에서는 `properties` 배열의 순서를 따릅니다. 속성 탭의 ‘주차 날짜’ 항목은 날짜 묶음을 나타내는 UI 항목으로, 별도 속성이나 셀로 저장하지 않습니다. 설정 저장에서 이 필드를 생략하면 기존 배치를 보존합니다. 팀 양식과 사본 설정 사본에도 배치를 포함합니다. 전체 XLSX·CSV 반출의 열 순서도 이 배치를 따르며, 현재 보기 반출은 요청한 `keys` 순서를 유지합니다. JSON은 팀 설정에 배치 정보를 포함합니다. `frozenColumns`는 표시 중인 `beforeWeeks` 속성에만 적용합니다.

XLSX·CSV 반출에는 속성 표시명과 값 이름을 사용하며, JSON에는 ID와 정의를 함께 반출합니다. 가져오기는 이름이 일치하는 속성 열을 종류에 맞게 해석합니다. 선택형 값은 이름으로 옵션을 찾아 ID로 저장하고, 없는 이름은 새 옵션으로 추가합니다. 예시 양식의 열(분류·유형·설명·지원자·진척률·목표일 등)은 팀에 없어도 연결되며 적용 시 속성 정의를 추가합니다. Member 사용자 매핑은 검증합니다.

팀 설정의 `weekHeader: {color?, backgroundColor?}`는 날짜 열 머리글의 글자색·배경색(`#RRGGBB`)입니다. 이번 주와 선택한 열의 강조색이 우선합니다. 생략하면 이전 설정을 보존하고 빈 객체는 기본 색으로 되돌립니다. 팀 양식·사본·JSON에 포함하며 XLSX는 반출하는 주차 머리글에 적용합니다.

팀 설정의 `weekBorders: {left?: Border, right?: Border}`는 현재 보이는 첫 날짜의 왼쪽과 마지막 날짜의 오른쪽 기본 경계선입니다. `Border`는 셀 테두리와 같은 `{style, color}`이며 설정의 `none`은 별도 경계선을 표시하지 않습니다. 날짜가 하나면 양쪽을 같은 열에, 날짜가 없으면 어느 열에도 적용하지 않습니다. 셀이나 같은 경계를 공유하는 이웃 셀에 별도로 저장한 선이 우선하며, 셀의 `null`·`none`과 업무 기본 서식에서 상속된 테두리는 주차 경계선을 가리지 않습니다. 기간·숨김에 따라 렌더링할 때만 계산하므로 셀 값·서식·버전을 변경하지 않고 셀 복사에도 포함하지 않습니다. 팀 양식·사본·JSON에 보존하며 XLSX는 반출 열의 양 끝에 적용합니다. 필드 생략은 기존 설정을 유지하고 빈 객체는 경계선을 해제합니다.

## 팀 스페이스 테마

팀 설정의 `theme`는 `mint`·`sky`·`lavender`·`rose`·`sand` 중 하나이며 기본값은 민트입니다. 팔레트는 `shared/themes.js`에서 관리하고, 현재 팀의 테마를 메뉴·버튼·선택 강조·팝업에 적용합니다. 셀의 저장된 색상과 속성 옵션·사용자 아바타 색상은 변경하지 않습니다.

시스템 관리자는 팀 생성 API에서, 시스템 관리자와 팀장은 `PATCH /api/teams/:id`에서 `theme`를 보낼 수 있습니다. 수정 요청의 `settingsRevision`은 동시 설정 변경을 검사하며, 테마를 바꾸면 설정 `revision`도 증가합니다. 속성·기본 서식 저장은 테마를 보존하고, `theme`를 생략한 설정 저장은 현재 테마를 유지합니다. 지원하지 않는 테마 ID는 서버에서 거절합니다.

## 주요 API

모든 업무 API는 HTTP-only 세션 쿠키를 요구합니다. 쓰기 요청은 `X-Requested-With: WeeklyPlan`을 포함합니다. 브라우저 외부 출처는 허용하지 않습니다.

정확한 입력 검증은 `server/validation.mjs`, 동작 계약은 `tests/api.test.mjs`를 참고합니다. API를 바꾸거나 직접 DB를 수정하는 도구를 만들 때 충돌 버전, 감사 기록, 팀 접근 검사를 함께 유지해야 합니다.

업무 생성은 `year`에만 등록하며 선택적인 `startMonth`는 삽입 대상의 조회 범위를 지정합니다. 선택적인 `insertAt: {taskId, updatedAt, placement}`는 같은 팀·표시 기간의 기준 행 앞(`before`) 또는 뒤(`after`)에 새 업무를 삽입합니다. 기준 행의 접근 권한·버전을 검사하며 버전 충돌은 409입니다. 일반 삽입은 기준 행의 `defaultStyle`, 행 공통 서식과 활성 속성·주차 셀의 예외를 함께 복사합니다. 삽입 행의 팀원을 포함한 셀 값은 비우고, 작업명 기본값과 요청한 묶음 기준 `fields`만 유지합니다. 빈 복수 팀원 값은 빈 배열로 만듭니다. 팀원은 `createdBy`가 본인이며 담당자가 비어 있는 행을 편집할 수 있습니다. 클라이언트는 기준 행의 개별 행 높이도 현재 보기에 복사합니다. `sourceId`·`copiedRow`를 함께 사용한 복제·붙여넣기는 복사 원본 서식을 우선합니다. 순서 간격이 부족하면 생성 트랜잭션 안에서 순서를 재배정하므로, 생성 실패 시 순서 변경도 함께 취소됩니다. 행 붙여넣기는 `copiedRow: {cells: {[key]: {value, style}}, defaultStyle, rowStyle?, documents?: [{id, title, markdown}]}`를 보내며 속성값·서식을 검증합니다. 일반 팀원의 담당자는 본인으로, 지원자는 빈 목록으로 생성하며 열람자는 생성할 수 없습니다. 기존 `sourceId` 복제도 유지하고 `copiedRow`와 동시에 보낼 수 없습니다. 관련 계약은 `tests/row-menu.test.mjs`에서도 검증합니다.

행 이동은 `tasks: [{id, updatedAt}]`(최대 20,000행), `targetId`, `targetUpdatedAt`, `year`, 선택적인 `startMonth`(기본 1), `placement`(`before`·`after`), 선택적인 `groupBy`를 받습니다. 기존 단일 행 요청의 `taskId`·`updatedAt`도 지원합니다. 이동할 행은 현재 수동 순서를 유지하며 한 트랜잭션으로 저장하고, 하나라도 권한·버전·팀·연도·묶음 검사를 통과하지 못하면 모두 취소합니다. 기준 행은 이동 대상에 포함할 수 없습니다. 응답의 `tasks`는 이동한 모든 업무이며, 단일 행 클라이언트를 위한 `task`도 유지합니다.

### XLSX 분석 범위

`POST /api/import/preview`의 multipart 항목은 `file`, `teamId`, `year`, 선택적인 JSON 문자열 `sheetOptions`입니다. `sheetOptions`는 시트 이름별 설정으로, `headerRow`(1~20), `startRow`·`endRow`(1~20,000), `columns`(속성 ID → 1부터 시작하는 원본 열 번호)를 받습니다. 행 범위는 양 끝을 포함하며 시작 행은 헤더 뒤여야 합니다. 예를 들어 `{"연간 업무":{"headerRow":3,"startRow":5,"endRow":400,"columns":{"type":2}}}`는 제목 없는 B열을 유형으로 연결하고 아래쪽 참고 표를 업무에서 제외합니다. 이 설정은 API로 제공하며 일반 가져오기 화면에는 별도 범위 입력 UI가 없습니다. 범위 밖의 표는 자동 이관되지 않으므로 따로 보존해야 합니다.

기본 분석은 위쪽 헤더 영역의 진척도·목표일도 연결합니다. 연도가 없는 월/일 주차 헤더는 마지막 날짜를 선택 연도에 맞추고, 오른쪽에서 왼쪽으로 12월→1월 경계를 따라 이전 연도를 계산합니다. 명시된 연도는 유지합니다. 날짜가 역순이거나 여러 해가 불규칙하게 섞인 원본은 연도까지 포함한 헤더로 정리한 뒤 이관하는 것이 안전합니다. 동일 주에 속한 열이 여러 개면 경고하고 첫 열을 보존하므로, 나머지 열은 `columns`로 별도의 Text 속성에 연결하여 보존해야 합니다.

담당자 없는 행은 미지정으로 유지하고 로그인한 관리자로 대체하지 않습니다. 수식은 저장된 계산 결과를 가져오며 재계산하지 않습니다. 부분 글자 서식, 대각선 테두리, 조건부 서식 등 지원 범위 밖의 표현은 원본 파일과 예외 목록을 함께 확인해야 합니다.

상단 상태 통계는 `status` 속성의 활성 옵션 ID에 셀 값을 연결해 이름·점 색상·순서를 따릅니다. 미지정과 보관된 값도 별도 집계해 합계가 전체 업무 수와 같도록 합니다. 필터·숨김과 무관하게 달력에 해당하는 최대 두 연도의 업무 목록에서 ID 중복을 제거한 뒤 계산합니다.

서식 메뉴의 재선택은 값 변경 여부와 관계없이 선택 범위의 `/cells/batch` 서식 변경을 요청합니다. 글꼴·크기·세로 정렬·텍스트 표시가 대상이며 내용은 보존하고 기존 원자적 저장·버전 검사·실행취소를 사용합니다.

팀 영구 삭제는 시스템 관리자만 `DELETE /api/admin/teams/:id`에 `{confirmed: true}`로 요청한다. 확인 누락은 400, 권한 부족은 403, 이미 없는 팀은 404이다. 시스템 관리자는 팀 소속 없이도 모든 팀에 접근하므로 소속 팀이 없어지는 삭제도 허용한다. `tasks`(모든 연도·삭제 상태 포함)·`cells`·`format_rules`·`format_states`·`views`·`reports`·`imports`·`audit`·`memberships`·`team_revisions`·팀 설정과 해당 변경/가져오기 작업의 재시도 캐시를 하나의 트랜잭션으로 제거한다. 공용 사용자·세션과 다른 팀의 독립적인 작업 기록은 유지한다. 삭제 내용 없이 `team_id: null`, `action: team-delete`, `target: 삭제한 팀 ID`인 관리자 이벤트를 남긴다. 별도 저장된 백업 파일은 변경하지 않는다.

### 시트별 이관·삭제 이력

사본의 XLSX 미리보기는 `reportId`를 포함하여 해당 사본의 속성으로 파일을 해석합니다. 반영 요청의 `mode: "copy"`, `reportId`, `revision`으로 기존 사본에 추가합니다. 미리보기와 대상 시트가 다르거나 revision이 변경되었으면 거절합니다. 중복 방지 키도 사본별로 구분합니다. 원본 업무·팀 설정·다른 사본은 수정하지 않습니다.

`POST /api/export`에 `reportId`, `revision`을 전달하면 해당 사본의 값·설정·사용자 이름·문서를 반출합니다. `scope: "all"`도 해당 사본 전체만 포함하며 JSON에 다른 사본이나 원본 필터를 넣지 않습니다.

`GET /api/audit?teamId=…&sheetId=original`은 원본, `sheetId=<사본 ID>`는 그 사본의 기록을 반환합니다. 각 항목은 `sheet: {id,name}`과 `restorableTaskIds`를 포함합니다. 삭제 복구는 `POST /api/audit/:id/restore`를 사용하며 사본에는 현재 `revision`이 필요합니다. 이미 존재하는 행을 덮어쓰지 않고, 이후 다시 삭제한 행은 최신 삭제 이력에서만 복구합니다. 사본 삭제 이력의 `before.deletedTasks`는 복구용 문서 본문을 포함하며 `deletedUsers`는 담당자의 저장 당시 이름을 보존합니다. 이력 정리 시 해당 복구 자료도 정리됩니다.

## 캘린더 일정

`calendar_entries`는 개인 일정과 팀 공용 일정을 연간 업무와 별도로 저장합니다. `user_id`(API의 `userId`)는 개인 일정의 소유자이며 `NULL`이면 해당 팀의 공용 일정입니다. 공용 일정은 작성자의 탈퇴와 무관하게 팀에 남습니다. `GET /api/calendar`의 `scope=team`은 공용 일정만 반환하며 `userId`와 함께 지정할 수 없습니다. 기본값인 `scope=personal`은 활성 팀원의 개인 일정만 반환하고 `userId`로 한 사람을 선택할 수 있습니다. 공용 조회의 `weekly`는 빈 배열입니다. 생성 요청의 `userId: null`은 팀 공용 일정, 사용자 ID는 개인 일정을 뜻합니다. `date`는 시작일, `end_date`(API의 `endDate`)는 종료일이며 양 끝을 포함하는 `YYYY-MM-DD` 날짜입니다. 하루 일정은 두 날짜가 같습니다. 기간과 겹치는 일정만 조회하고, 월간·팀 주간 목록에는 본문 대신 제목과 짧은 미리보기를 반환합니다. 본문은 공통 `document_versions`에서 참조하며 이미지 검증과 SQLite 백업·복구에 포함됩니다. 연간 업무 JSON/XLSX 반출 형식은 바꾸지 않습니다.

`lane`은 0부터 시작하는 카드의 현재 행 위치입니다. 생성할 때 기간이 겹치지 않는 첫 행을 배정합니다. 기간 변경 시 겹치는 카드의 상대 순서를 유지하고, 이동·축소·삭제로 생긴 빈 공간은 카드의 날짜 구간 전체가 들어가는 위쪽 행으로 채웁니다. 명시적 순서 변경은 사이의 카드를 빈자리 쪽으로 이동하며 새 순서를 보존한 채 빈 행을 정리합니다. `PATCH /api/calendar/entries/:id`의 `{lane, expectedLane, expectedDate, expectedEndDate}`로 순서만 변경합니다. 기간·순서 저장과 일정 삭제 응답의 `placements: [{id,lane}]`는 같은 팀·소유자의 변경 전후 구간에 겹침으로 연결된 일정의 현재 위치 정보이며 재시도 복구와 화면 캐시 병합에 사용합니다. 무관한 기간의 일정은 조회·재배치·응답에서 제외합니다. 제목·본문을 다시 조회하지 않습니다. 충돌 시 서버 기간을 선택하는 조회는 `GET /api/calendar/entries/:id?placements=1&from=…&to=…`로 현재 위치도 함께 받아 주변 카드의 행을 동기화합니다. 선택적인 `from`·`to`는 화면이 알고 있던 이전 기간이며 현재 기간과 함께 배치 조회에 포함합니다. 개인 소유자를 지정한 조회와 공용 조회의 `layout: [{id,date,endDate,lane}]`에는 화면 밖 연결 일정과 드래그로 닿을 수 있는 기간의 좌표도 포함합니다. 조회 범위는 최대 62일이며 카드 길이와 실제 표시 범위를 기준으로 이동 가능한 좌표를 미리 조회합니다. 하루 일정은 조회 범위를 넓히지 않고, 긴 일정은 양 끝에서 최대 61일 이동할 수 있는 좌표를 포함합니다. 제목·본문은 포함하지 않습니다. 위치 저장·삭제·복구 응답의 `layout`도 같은 좌표 형식이며 기존 캐시에 병합합니다. 활성 일정의 소유자별 시작일·종료일 부분 인덱스로 연결 구간의 새로 확장된 날짜 띠만 조회합니다.

제목 변경은 `expectedTitle`, 기간 변경은 `expectedDate`·`expectedEndDate`, 순서 변경은 `expectedLane`·기존 기간, 본문 변경은 `expectedRevision`, 태그 변경은 순서가 있는 `expectedTagIds`로 각각 충돌을 확인합니다. 삭제는 제목·기간·본문 버전·태그·체크 상태(`expectedCheckedTagIds`)를 모두 확인합니다. 같은 팀의 활성 구성원이 일정을 조회할 수 있고, 일정 소유자 중 기여 권한이 있는 구성원 또는 해당 팀장·관리자만 수정할 수 있습니다. 팀 공용 일정은 열람자를 포함한 해당 팀의 모든 활성 구성원과 관리자가 추가·수정·삭제·복구할 수 있습니다. 개인 일정의 편집 권한은 그대로 유지합니다. 기간 이동은 소유자를 변경하거나 날짜별 복사본을 만들지 않습니다. 공용·각 개인의 카드 배치는 서로 영향을 주지 않습니다.

일정 삭제는 `deleted_at`·`deletion_id`를 기록하는 복구 가능한 삭제입니다. 목록·상세·수정·이미지 업로드에서는 삭제된 일정을 제외하고, 본문 참조와 태그·체크 상태는 백업 및 실행취소를 위해 보존합니다. 삭제 요청은 고유 `deletionId`와 조회 시점의 `expectedUpdatedAt`도 전달합니다. `POST /api/calendar/entries/:id/restore`는 `{deletionId,previousRange?: {date,endDate}}`로 해당 삭제만 취소하며 기존 수정 권한을 검사합니다. 삭제·복구 재시도는 중복 실행하지 않고, 복구 응답에는 현재 일정과 `placements`를 반환합니다. 복구된 카드가 이전 행에서 우선 배치되며 겹친 일정은 순서를 유지해 아래로 배치됩니다. 응답 유실 후 다른 기간으로 이동한 상태에서 복구를 재시도하면 `previousRange`와 현재 기간의 위치를 함께 반환합니다. 복구 뒤 다시 삭제한 경우 이전 삭제의 실행취소는 거절합니다. 태그 사용 수에는 활성 일정만 포함합니다. 팀 영구 삭제 시 보존된 일정도 함께 제거합니다.

`calendar_tags`는 태그의 ID·팀·소유자(`user_id`, API의 `userId`)·이름(1~40자)·고정 색상 ID·유형(`kind`: `label` 또는 `check`, 기본 `label`)·수정 번호를 저장합니다. 사용자 ID가 있으면 해당 팀·개인의 태그이며 `NULL`이면 팀 공용 태그입니다. 같은 팀·소유자 목록 안에서만 이름 중복을 금지하고 목록별 최대 200개입니다. 서로 다른 개인과 공용 목록은 같은 이름을 사용할 수 있습니다. 개인·공용 이름 중복은 각각의 부분 고유 인덱스로도 검증합니다. `calendar_entry_tags`는 일정·태그 ID와 순서·체크 상태(`checked`: 0 또는 1)를 저장하며 이름·색상을 일정마다 복제하지 않습니다. API의 `tagIds`는 중복 없는 최대 20개 ID 배열이며 첫 태그가 카드 배경색을 결정합니다. 태그가 없으면 기존 테마 배경을 유지합니다. 색상은 `shared/calendar-tags.js`의 기본·회색·갈색·주황색·노란색·초록색·파란색·보라색·분홍색·빨간색 10종입니다.

태그 목록 조회·생성은 `/api/calendar/teams/:teamId/tags`, 수정·삭제는 `/api/calendar/tags/:id`에서 처리하며 수정·삭제에는 `expectedRevision`이 필요합니다. 목록 조회의 기본값은 본인의 개인 태그이며 `userId`로 다른 팀원의 목록을 조회하거나 `scope=team`으로 공용 목록을 조회합니다. 생성 시 `userId`를 생략하면 본인, 사용자 ID면 해당 개인, `null`이면 공용 목록입니다. 개인 태그 관리는 해당 개인 일정의 편집 권한을 따릅니다. 공용 태그는 열람자를 포함한 모든 팀원이 추가·수정·삭제할 수 있습니다. 일정에 태그를 지정할 권한은 기존 일정 편집 권한을 따릅니다. 일정과 팀·소유자가 모두 같은 태그만 연결할 수 있으므로 다른 개인·공용 목록 사이의 태그 연결은 거절합니다. 태그 삭제는 연결만 제거하고 일정·본문은 유지합니다. 팀 삭제와 SQLite 백업·복구에는 태그와 연결도 포함합니다. 연간 업무 속성·JSON/XLSX 반출과는 별개입니다.

`calendar_preferences`의 표시 요일은 로그인 사용자별로 저장하며 숨긴 날짜의 일정은 보존합니다. `calendar_rules`는 팀별 속성 ID(`property_id`)·필터 값 배열(`filter_values`, JSON)·일치/제외 방식(`filter_mode`: `include`/`exclude`)·수정 번호를 보관합니다. `PUT /api/calendar/teams/:teamId/rule`은 `{propertyId,values,mode,expectedRevision}`를 받으며 팀장·관리자만 변경합니다. 작업(`title`)·팀원(`owner`)을 제외한 활성 옵션·텍스트·날짜·숫자·팀원 속성을 지원하고, 옵션·팀원은 안정적인 ID, 텍스트·날짜·숫자는 화면 필터와 같은 문자열 값으로 비교합니다. 빈 문자열은 미지정이며 셀 자체가 없거나 복수 팀원 배열이 빈 경우도 포함합니다. 여러 값은 OR로 일치 여부를 판단하고 `exclude`는 그 결과를 반전합니다. 값 배열이 비어 있으면 두 방식 모두 전체를 포함합니다. 작업·팀원 속성은 저장을 거절하며 기존 기준이 두 속성이나 보관된 속성·옵션을 참조하면 기준을 다시 설정할 때까지 가져오기를 차단합니다. 기준 변경은 기존 주간 목록에 영향을 주지 않습니다. `calendar_weekly_items`는 사용자가 가져오거나 직접 선택한 연간 업무 ID를 팀·사용자·일요일 주 키별로 중복 없이 보관합니다. 조회 시 활성 원본의 최신 제목을 사용하므로 과거·미래 목록도 제목 변경을 따릅니다. 원본을 삭제한 경우 저장 당시 제목과 조회 불가 상태를 반환합니다. 월간 화면은 이전 달 마지막 날과 다음 달 첫날이 속한 주까지 표시합니다.

`GET /api/calendar/tasks?teamId=…&userId=…&weekStart=…&q=…&offset=…`는 주간 목록에 추가할 같은 팀의 활성 업무를 연도·상태·담당자 제한 없이 검색합니다. 제목·연도·해당 주 추가 여부를 50개씩 반환하며 `nextOffset`이 `null`이면 마지막 페이지입니다. `POST /api/calendar/weekly`는 `{teamId,userId,weekStart,taskIds}`로 최대 100개 업무를 과거·현재·미래의 주에 연결합니다. 대상 개인 일정의 수정 권한과 모든 업무 ID를 한 번에 검증하며 중복 연결·재시도는 기존 기록을 유지합니다. `POST /api/calendar/import`는 서울 날짜 기준 이번 주에만 허용하고, 팀원(`owner`) 값이 대상 `userId`인 업무 중 설정한 기준에 맞는 업무를 추가합니다. 지원자·검토자로만 참여한 업무는 제외합니다. 두 저장 경로는 `{added,existing,weekly}`를 반환하므로 해당 소유자·주의 목록만 병합하며 전체 캘린더를 재조회하지 않습니다. 두 경로 모두 원본 업무를 복제하거나 수정하지 않습니다.

체크 태그의 상태는 태그 정의가 아닌 일정별 연결에 저장합니다. 일정 응답의 `checkedTagIds`는 체크된 태그 ID이며 생성 시에도 지정할 수 있습니다. 지정되지 않은 태그나 일반 태그의 체크는 거절합니다. `PATCH /api/calendar/entries/:id/tags/:tagId`에 `{checked, expectedChecked}`를 보내면 해당 체크만 저장하고 `{tagId, checked, updatedAt}`를 반환합니다. 같은 값의 재시도는 중복 변경 없이 처리합니다. 태그 순서·색상·이름 변경 시 체크는 유지하며, 일정에서 제거했다 다시 지정하거나 유형을 일반 태그로 바꾸면 체크는 해제됩니다. 체크는 일정 수정 권한을 따르고 제목·기간·본문 저장과 독립적으로 병합합니다.
